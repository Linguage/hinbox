3:T37c4,<p>解决混乱的周一例会，也改变了我们交付给客户的产品</p>
<p>作者：<a href="https://every.to/@stella.f.garber">Stella Garber</a></p>
<p><a href="https://every.to/@stella.f.garber">Stella Garber</a> 在 Trello 工作多年，观察了哪些因素能让软件留住用户，随后共同创立了 Hoop——一款帮助订阅制品牌降低客户流失率的 AI 智能体（AI agent）。当团队的客户需求探索访谈（customer discovery calls）变成一堆散落各处的笔记，而且各人对访谈的解读也相互冲突时，他们遵循 Every 的<a href="https://every.to/guides/agent-native">智能体原生架构（agent-native architecture）</a>理念，从零开发了一款内部 AI 分析工具。它重塑了他们开发实际产品的方式。——<a href="https://every.to/@kate_1767">Kate Lee</a></p>
<p>那是一个周一的早晨，我的联合创始人 Brian 正在朗读智能体对客户需求探索访谈的每周分析。“订阅留存，”他说，“有五个不同的品牌把它列为头号优先事项，而且没有一家信任现有的 AI 工具，愿意让这些工具插手这件事。”</p>
<p>就在几周前，挖掘出这样的洞察还几乎是不可能的。</p>
<p>我的初创公司还没有找到产品与市场契合点（product-market fit）。我们一直都在与潜在客户交谈，试图摸清产品的定位，但要记录所有收获，却是一团乱麻：信息分散在不同创始人、平台和媒介之间。为了在周一例会上分享我们的发现，Brian 会阅读 Slack 里的笔记，从 Granola 收集转录文本，再尝试用 Claude Code 理清这一切。</p>
<p>我们承受不起这种混乱。我们最近刚推出 <a href="http://hoop.app">Hoop</a>，这款智能体帮助订阅制品牌减少客户流失，我们需要尽快学习。所以，我们必须与尽可能多的潜在客户交谈，然后严谨地记录每次通话并为其评分，把礼貌性的兴趣和真正的需求区分开来。五人团队里的每个人都很努力，但我们各自有自己的流程、自己的工具，也各自对每次客户通话有自己的解读。</p>
<p>于是，我和另外两位联合创始人——我们的职位名称里都没有“工程师”——开发了一款内部工具来解决这个问题。我们没有想到，这款工具也会改变我们为客户开发实际产品的方式。</p>
<h2>“我应该为这件事做个工具”</h2>
<p>我们的周一例会之所以毫无章法，是因为客户通话的信息放在哪里，取决于谁接了这通电话，以及对方的笔记来自 Granola 还是另一款转录工具。我们无法看出规律，也无法据此得出结论，了解潜在客户想要什么。</p>
<p>Justin 是我的联合创始人，也是团队里的产品专家。他用几天时间，在其他优先事务的间隙，总共花了不到 10 个小时，开发出一款工具的第一版，把这些笔记汇集到一起。</p>
<p>它的工作方式是这样的：你上传一份 Zoom 转录文本，工具会依次用四五个提示词（prompts）处理它，然后给你一份结构化分析，并按照 <a href="https://thephysicsofstartups.substack.com/p/the-pull-framework">PULL 标准</a>打分。PULL 是哈佛商学院开发的一套框架，用于帮助早期初创公司找到产品与市场契合点。工具还会把与某个潜在客户进行的所有对话汇总成一份摘要，让你看到这段关系的完整发展过程，而不是某次通话的单一切片。我们不必再埋头翻找笔记和转录文本，工具每周都会给我们汇总分析，帮助我们看清什么有效、什么无效。</p>
<p>Justin 使用了一些我们以前没有用过的工具来搭建应用：<a href="http://next.js">Next.js 框架</a>配合 <a href="https://ui.shadcn.com/">ShadCN 组件</a>来做用户界面，用 Supabase 数据库汇集所有笔记，再用 Claude 的 API 进行分析。</p>
<p>Justin 学过计算机科学，但已经不怎么写代码了。对他来说，这是一个重拾技能、增强 AI 原生编程信心的机会。他从设计和开发可视化界面开始，因为他是那种即使软件功能正常，只要样子不对就会感到烦躁的人。他确保工具的外观和使用感受与我们的品牌一致，先把组件——按钮、标签、菜单——做得整洁漂亮，之后才去碰数据。</p>
<p>直到这时，他才直接着手处理数据。他必须确保工具对客户对话的分析，比大家各自用 Claude 做出来的分析更好。否则，我们永远无法说服整个团队使用同一款工具。于是，他写了一个提示词，人工审阅了几次输出，再参考 <a href="https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices">Anthropic 的 Claude 提示最佳实践</a>，不断调整。</p>
<p><img src="https://d24ovhgu8s7341.cloudfront.net/uploads/editor/posts/4303/optimized_c2a92b37-2617-401c-828f-28ac7a13de67.png" alt="电商客户的当前假设：PULL 标准"></p>
<p><em>图中文字翻译：当前假设——电商——启用——创建于 2026 年 1 月 19 日。项目（Project）：更快处理客服工单，同时不牺牲质量或品牌表达风格。不可回避（Unavoidable）：工单量已超出小团队的处理能力，创始人不得不亲自做客服。正在寻找（Looking For）：他们试过客服系统的智能体，也试过 ChatGPT，以及在 n8n 中拼接工作流。现有方案欠缺（Lacking）：只要问题稍微复杂，准确性就会崩溃。企业级工具又过于庞大，价格也过高。</em></p>
<h2>阻力仍然太多</h2>
<p>第一版工具能生成高质量的分析，但流程中仍有太多环节需要手动操作。你必须从 Zoom 下载通话转录文本，手动上传到工具，填写客户名称和通话类型，然后等待几分钟，直到处理完成。接着，你还要创建链接，把分析分享到 Slack。</p>
<p>团队可以在工具里搜索转录文本和分析，但搜索结果并不好。例如，我搜索曾对 AI 客服工具有过糟糕体验的潜在客户，结果什么也没找到，尽管我明明知道，有一位客户体验负责人曾花了五分钟，讲述他们的 AI 向客户发送不符合品牌风格的回复，让他们多么尴尬。工具只能匹配查询中的原词，无法理解词语背后的意思。</p>
<p>此外，还有那个经典的使用推广问题。我们以前都在效率工具 Trello 工作过，对此再熟悉不过。Justin 的工具又成了一个大家必须记得去访问的地方，与 Slack 和 Notion 争夺我们的注意力。</p>
<h2>转向智能体原生</h2>
<p>后来，我们找到了困境的解法。Justin 一直在 Every 阅读关于<a href="https://every.to/guides/agent-native">智能体原生架构</a>的文章。你不再硬编码一串按固定顺序运行的提示词，而是给模型一组工具，让它自行推理该如何使用它们。你也不再开发一款要求人们主动前来访问的应用，而是把工具带到人们已经在工作的地方，比如 Slack。</p>
<p>Justin 把文章链接给了 Claude Code，告诉它，自己想开发一个符合这些架构原则的系统。智能体需要两款工具：一款用于上传和读取转录文本，另一款用于添加和编辑合作方资料。有了这些，用户只需在 Slack 中向应用发送转录文本。智能体会确认合作方名称和通话详情，随后上传转录文本、运行分析、创建摘要页面，并将其发到我们的用户反馈频道。</p>
<p>Justin 开始用智能体原生架构指南检查自己开发的所有东西，不只是这款寻找产品与市场契合点的工具。他会进入 Claude Code 的规划模式，列出一个新功能，再把它连同 Every 的文章一起发回给 Claude Code，问道：“哪些地方符合这些原则，哪些地方不符合？”</p>
<p>有时，如果他认为用户完成某项任务不需要 AI，他也会偏离指南。例如，工具会跟踪大语言模型（LLM）的 token 用量和成本。这些信息很有用，但用户没有必要去查询。把它们暴露给智能体，只会造成困惑。</p>
<h2>轮到我进入代码库</h2>
<p>我遇到的是另一个问题。我需要一眼看清销售流程（pipeline）：该跟进谁、每段对话进行到了哪一步。我想按人员和阶段来组织，而不只是看按时间排列的通话日志。</p>
<p>我打开了 Ghostty 这个简洁的终端应用，复制了工具的代码，这样就能在自己的笔记本电脑上本地修改。想到自己要直接编辑代码，我的手还有些发抖，但还是启动了 Claude Code。</p>
<p>我让 Claude Code 开发的第一项功能，是一个轻量的数据视图，让我能够一眼看到销售流程的各个阶段。讽刺的是，我让 Claude Code 做的，是一个像 Trello 一样的信息看板，这样我就能移动代表通话的卡片。旧习难改。</p>
<p>我一点点地开发。我发现，如果每张卡片正面都能显示交易状态，会很有用，于是我给 Claude Code 提示：“确保每张卡片都有一行摘要，这样我一眼就能知道进展到了哪里。”部署之后，新进来的交易就带上了状态。每次想做些不同的东西，我只要开口提出就行。</p>
<p>在 Justin 的鼓励下，我开始直接把代码合并到共享仓库。有时会弄坏一些东西，但没人因此挨批，因为这件事的风险很低，大家也都这样看待它。</p>
<h2>Brian 在晚上 10 点学会智能体原生</h2>
<p>接下来是我们的另一位联合创始人 Brian。他负责每周的用户发现报告（user learnings report）。在有这款新工具之前，他经常会忘记这件事，最后只能翻阅 Notion，或者凭记忆即兴讲述脑海里最新鲜的那些对话。我们的发现偏向最近发生的事情，而不是最有意义的事情，也错过了那些只有把所有通话放在一起看才会显现的规律。</p>
<p>于是，Brian 开发了一项功能，自动生成这份报告。他的第一版是自己电脑上的一个链接，能吐出一份 Markdown 文件，再由他粘贴到 Notion 里。它能用，但只有他能用。第二版在工具中添加了一个 Learnings 标签页，上面有个按钮，点一下就能生成同样的 Markdown 输出，现在任何人都可以生成报告。</p>
<p>这解决了访问问题，但又冒出了一个新问题：如果团队想调整报告的格式或重点，就得请 Brian 编辑代码。Brian 想让报告的提示词可以编辑，这样团队就能调整报告而不必动代码。晚上 9 点 25 分，Justin 在 Slack 里提议：“你应该把提示词做成一个可编辑字段，再把它传给智能体。”</p>
<p>Brian 不明白这是什么意思，于是把 Justin 的消息粘贴进 Claude，请它解释。Claude 带他理解了智能体原生架构的理念，Brian 开始明白：与其给人一个用来编辑提示词的文本框，不如给智能体一款工具，让它自己读取和修改提示词。这样，任何人都可以在 Slack 里和工具对话，告诉它该改什么。</p>
<p>到晚上 11 点 15 分，Brian 已经把功能做出来了。他让 Slack 智能体把 Learnings 的提示词改写成克林贡语，借此测试它。果然，每份报告都变成了克林贡语。从头到尾，只花了两个小时。</p>
<p>更实际的例子是，最近的一份报告指出，在最近六次通话中，有四次提到了同一个痛点：品牌正在流失一些起初根本没意识到自己订阅了服务的客户。客户往往为了获得折扣而订阅，忘记了这是定期续费，等扣款发生时又惊讶地取消订阅——恰好在这个时刻，我们的产品可以介入，提供优惠，或者推荐更适合他们的选择。我们每个人单独都没有把这些线索联系起来；只有当工具同时查看所有通话时，这个规律才浮现出来。</p>
<p>随后，又发生了一件意想不到的事。Learnings 标签页里出现了重复记录，Brian 在 Slack 里向机器人提起了这件事。机器人查看了两条记录，判断其中一条是空的，然后把它删掉了——这就成了一个“查找并删除重复记录”的功能。他给了智能体编辑数据库的权限，模型自行推理并解决了问题。就在那一刻，Brian 真正理解了：如果给推理模型简单而强大的工具，它就能处理你从未想过要为之编写代码的情况。</p>
<h2>我们把哪些经验带回了产品</h2>
<p>这款工具最重要的作用，是改变了我们开发面向外部客户的产品的方式。Justin 把在内部测试过的智能体原生模式用来开发了多款销售工具，其中包括客服系统审查工具。我们可以与潜在客户一起运行它，在他们注册前就展示 Hoop 的价值。</p>
<p>Brian 从开发 Learnings 标签页，转向开发类似内部销售智能体的东西。这个住在 Slack 里的机器人，我们叫它“Benny”。它能调用我们的销售工具，按指令执行任务：筛选潜在客户、根据我们的理想客户画像（ideal customer profile）为他们评分，以及更新 Attio——我们的客户关系管理系统（CRM）。而我，则从给客户关系管理工具开发功能，进展到能够对产品架构提出有依据的看法。</p>
<p>它也让我们保持诚实。当每次通话都自动打分、自动总结时，你无法再回避数据告诉你的事实。当五位不同的业务负责人在同一周告诉我们，定价不合理时，我们必须面对事实，调整定价，才能赢得更多交易。在大公司里，会有一支分析师团队依据这些数据撰写季度报告。我们只有五个人，却用自己开发的工具，每周做一次。</p>
<p>再过一个月，这款工具可能又会变个样子，这没关系。更重要的是我们获得的熟练程度：知道什么时候该给模型一款工具，什么时候该把工作流硬编码下来，也能坦然面对交付和失败——然后再试一次。</p>
<p>Stella Garber 是 Hoop 的联合创始人兼 CEO。</p>
