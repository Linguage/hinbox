3:T47f2,<p>即使模型和硬件都没有变化，为什么向模型发送一个10万词的提示词，会比发送一个短提示词贵那么多？</p>
<p>答案的一个关键部分，在于一块叫作键值缓存（KV cache）的工作内存。</p>
<p>模型生成回答时，会逐步建立这块内存。它与模型权重中存储的知识相互独立，保存着为输入中的每个词元（token）计算出的键向量和值向量。每增加一个词元，缓存都会增长；在长上下文中，它可能占用相当大的GPU显存空间。</p>
<p>例如，对于一个700亿参数的模型，当上下文达到128,000个词元时，缓存大约占40GB。这是一笔很大的显存开销，而且每增加一个用户，开销还会继续增长。</p>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/b58a06ab-fca6-4467-8c9e-c87a046fe08c_2578x1652.png" alt="KV缓存随上下文长度增长"></p>
<p><em>图中文字译文：纵轴为GPU显存（GB），横轴为上下文长度（词元）。模型权重占用固定；KV缓存随上下文增长。700亿参数模型在128K上下文时，KV缓存约为40GB；图中标出了缓存占用超过权重占用的位置。</em></p>
<p>上图引出了一个显而易见的问题：为什么需要缓存，它又为什么这样增长？在本文中，我们将了解大语言模型（LLM）如何使用内存、内存成本为何上升，以及如何解决这些问题。</p>
<p>免责声明：本文依据多个来源公开分享的信息写成，参考资料列于文末。如果发现不准确之处，请留言指出。</p>
<h2>重复计算</h2>
<p>先从模型生成一个词元时要做的工作说起。</p>
<p>为了选择下一个词，模型会执行一次注意力计算，让最新的词元与之前的每个词元进行比较。这种比较需要每个历史词元的两个向量：键（key）和值（value）。它们就是模型在每一层为该词元计算出的数值摘要。如果模型每一步都重新构建所有历史词元的键和值，那么输入越长，生成每个词元所需的工作就越多。这种重复完全是浪费，因为一个词元一旦处理完，它的键和值就不会再变。</p>
<p>KV缓存消除了这种浪费：第一次计算键向量和值向量时，就把它们存起来。到了下一步，模型只计算新词元的键和值，其余内容直接从缓存中读取。</p>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/9004337a-8b6b-42e7-a074-015d1ba74691_2796x1396.png" alt="重复计算与缓存复用的流程对比"></p>
<p><em>图中文字译文：左图每一步都重新构建所有词元的键和值。右图读取词元1至4已有的键和值，只计算新词元5的键和值。</em></p>
<blockquote>
<p>译注：原图左右两侧的标题都写作“Without a cache”（不使用缓存）。右侧所画的读取已有键和值、只计算新词元的流程，实际对应本文所述的缓存复用；此处保留<a href="https://blog.bytebytego.com/p/why-an-llms-memory-gets-expensive">原图</a>。</p>
</blockquote>
<p>总体而言，这是一个很好的解决办法。不过，缓存解决了速度问题，也带来了一个新问题：现在每一步都必须读取缓存，而这恰恰是成本增加的真正来源。</p>
<p>这里有个细节需要理解：缓存保存的是向量，并非原始文本。这也解释了一类看起来令人困惑的内存不足错误：模型本身明明装得下，而且还有不少余量。</p>
<h2>解码</h2>
<p>词元生成分为两个阶段，它们给硬件带来的压力不同：</p>
<ul>
<li>第一阶段是预填充（prefill），模型一次读入整个输入。它并行处理所有输入词元，在一次遍历中计算它们的键向量和值向量，并建立缓存。预填充会让GPU的运算单元充分忙碌，因此我们称它受算力限制（compute-bound），也就是说，瓶颈在于芯片做算术运算的速度。</li>
<li>第二阶段是解码（decoding），模型每次生成一个输出词元。每个新词元都要对整个缓存执行一次注意力计算，这意味着模型必须先从GPU显存中读出所有存储的键和值，才能输出下一个词元。它每生成一个词元，都要重复这种读取。这里的瓶颈在于缓存从显存传到计算单元的速度，因此我们称解码受内存带宽限制（memory-bound）。</li>
</ul>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/0c824716-f233-4d9d-9892-4427a75d7e66_2374x1318.png" alt="预填充与解码的硬件瓶颈"></p>
<p><em>图中文字译文：预填充受算力限制，一次处理所有输入词元，并在一次遍历中建立KV缓存。解码受内存带宽限制，每个新词元都要读取整个缓存。</em></p>
<p>长上下文生成的开销，更多来自每生成一个词元都要遍历整个缓存，而非单纯保存缓存。</p>
<p>缓存越大，每个词元通过内存总线传输的数据就越多，这会直接表现为生成更慢、成本更高。这也解释了为什么一个请求即使远未占满内存，仍可能运行得很慢。</p>
<p>如果成本随每一步读取的缓存量而变化，那么下一件需要弄清楚的事，就是缓存的大小。</p>
<h2>规模增长</h2>
<p>缓存大小由几个数相乘得到：</p>
<ul>
<li>系数2对应键和值两部分。</li>
<li>层数要算进去，因为每一层都有自己的缓存。</li>
<li>键值头数决定每一层存储多少组键和值。</li>
<li>头维度表示每个向量的大小。</li>
<li>每个数的字节数，表示存储一个数值所占的空间。</li>
<li>词元数就是上下文长度，每个词元对应一个条目。</li>
<li>批大小（batch size）是同时服务的请求数。</li>
</ul>
<p>概括起来，缓存大小等于2×层数×键值头数×头维度×每个数的字节数×词元数×批大小。</p>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/1312f6a3-d96d-42b5-91c0-136a0443ae24_2702x1256.png" alt="KV缓存大小的乘积公式"></p>
<p><em>图中文字译文：2×80层×8个KV头×128维×2字节×128K词元×批大小1，得到每个请求约40GB的缓存。图中把GQA/MQA对应到KV头数，把潜在注意力（MLA）对应到头维度，把量化对应到每个数的字节数，把逐出对应到词元数。</em></p>
<p>这里有两点需要注意：</p>
<ul>
<li>缓存随词元数线性增长，因此上下文翻倍，缓存也翻倍。</li>
<li>缓存随批大小同样线性增长，因此同时服务更多用户，缓存也会以同样的速度扩大。</li>
</ul>
<p>举一个近似的例子：Llama 3 70B模型有80层、8个键值头，头维度为128，每个数存储为2字节。对于单个请求，若上下文为128,000个词元，这些数相乘后得到大约40GB。这就是为什么仅一个长请求，就可能占据一张80GB显卡的大部分空间。</p>
<p>现在来看看帮助LLM管理内存的优化技术。每种技术都试图降低公式中的某个数。</p>
<h2>注意力</h2>
<p>前两种技术会改变注意力本身的构造方式，也就是说，模型在训练时就要采用它们。两者都会缩小每个词元在缓存中的占用。</p>
<p>分组查询注意力（grouped-query attention，GQA）针对的是键值头数。在标准注意力层中，每个查询头都有自己的键头和值头，因此一个有64个查询头的模型会存储64组键和值。分组查询注意力允许多个查询头共享一个键值头，从而大幅减少需要存储的组数。例如，700亿参数的Llama 2和Llama 3，以及Mistral 7B，都通过共享把键值头数降到了8；相对于完整的多头注意力（multi-head attention），缓存因此大约缩小到八分之一。这也解释了为什么较新的700亿参数模型，其缓存可能比旧的70亿参数模型还小。</p>
<p>还有一种更激进的版本，叫作多查询注意力（multi-query attention，MQA），所有查询头都共享同一个键值头。在各种头共享方案中，它最节省内存。不过，共享做到这个程度时，质量往往会下降，训练也会变得不稳定，因此大多数方案选择分组这一折中做法，认为它的权衡更合适。</p>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/a98fbe56-ad88-4275-810e-cfcfbab32229_2608x1886.png" alt="多头、分组查询、多查询与多头潜在注意力"></p>
<p><em>图中文字译文：示例中的多头注意力使用8个KV头，缓存占用为1倍；分组查询注意力使用4个共享KV头，缓存约为二分之一；多查询注意力使用1个共享KV头，缓存约为八分之一，最省内存，但质量可能下降。蓝色圆点表示查询头，黄色圆点表示存入缓存的键值头。多头潜在注意力将完整的K、V压缩为潜在表示并缓存，读取时展开、重建K、V；缓存更小，但每次读取都需要额外计算。</em></p>
<p>第二种办法保留各个头，同时压缩每个头存储的内容。</p>
<p>DeepSeek模型引入的多头潜在注意力（multi-head latent attention，MLA），会先把键和值投影到一个更小的潜在表示中，再缓存起来；读取时，再把它们展开。节省的空间很大：DeepSeek-V3每个词元大约占70KB，而可比的分组查询模型介于192KB和328KB之间。代价体现在推理服务中：压缩会给每次读取增加工作，与某些标准注意力实现的配合也不顺畅。因此，当模型和上下文大到缓存传输成为主导因素时，它往往才最划算。</p>
<p>如前所述，头共享和潜在注意力都要求能够控制模型架构，因此它们适用于选模型或训练模型的阶段。接下来的办法，则可以用于我们手头已有的模型。</p>
<h2>量化</h2>
<p>量化（quantization）针对的是每个数的字节数。</p>
<p>键和值通常各以16位存储，量化会将它们舍入到更小的格式，例如8位或4位。由于每个数的字节数直接出现在公式里，从16位改为8位会让整个缓存减半，改为4位又能再减半。它的吸引力在于：已有模型就能使用，而且完全不需要重新训练。</p>
<p>质量方面的代价，取决于量化做到什么程度。</p>
<p>8位存储带来的准确率损失，通常远低于1%，对大多数工作负载来说，这处于噪声范围内。4位存储节省更多，但在多针检索（multi-needle retrieval）等要求较高的任务中，会开始出现可测量的损失；这类任务要求模型从长上下文中找出多个指定事实。</p>
<p>专门的方法比简单舍入效果更好，因为缓存中的少数数值值得保留比其他数值更高的精度。不过，简单舍入就已经能取得大部分收益。</p>
<h2>逐出</h2>
<p>逐出（eviction）针对的是词元数：删掉模型不太可能需要的条目。</p>
<p>常见的做法是保留由最近词元构成的一个窗口，因为近期上下文通常最重要，同时再保留序列开头的少数词元。这些开头词元的作用出奇地大：不管它们实际说了什么，都会吸收很大一部分注意力，像锚点一样帮助模型保持输出稳定。</p>
<p>见下图：</p>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/f85ec96c-a439-48b5-a014-d98c80053d35_2578x1396.png" alt="保留开头锚点与最近窗口、逐出中间词元"></p>
<p><em>图中文字译文：保留序列开头的锚点，逐出中间部分，保留由最新词元构成的近期窗口。模型后来需要的某个事实，可能恰好位于被删掉的区域。</em></p>
<p>逐出的难题是结构性的。</p>
<p>一个词元是否重要，取决于一个尚未出现的问题。现在删掉的词元，可能恰好是后续生成所需要的；一旦它消失了，模型生成时就会表现得仿佛这个词元从来没有出现过。检索任务会暴露这个问题：经过激进裁剪的缓存，在随意聊天时表现不错，却可能漏掉藏在长文档中间的某个事实。</p>
<p>更精细的方案会为每个词元的重要性打分，并尝试预测哪些词元可以安全删掉。这有所帮助，不过核心问题仍然存在。</p>
<h2>推理服务</h2>
<p>即便缓存的内容不变，推理服务系统的内存管理方式仍会浪费不少资源。两种技术可以提供帮助。</p>
<p>第一种是分页注意力（paged attention）。</p>
<p>较旧的推理服务系统会为每个请求预留一大块连续内存，大小按它可能生成的最长输出确定。大多数请求在远未达到这个长度时就结束了，预留空间闲置不用，碎片也不断积累。分页注意力借用了操作系统的一个思路：把内存分成固定大小的小页，按需分配。缓存被拆成可以放在内存任意位置的小块，再用一张查找表跟踪每个请求对应的内存块。结果是，原本因碎片而浪费60%至80%缓存内存的系统，把这个比例降到了4%以下，吞吐量提高到原来的2至3倍。这些收益全部来自把同样的数据放得更紧凑。</p>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/124d4aee-491f-4b2d-a20d-6c517f46bb4c_2578x1708.png" alt="分页缓存与共享前缀的物理内存布局"></p>
<p><em>图中文字译文：请求A和请求B共享同一份前缀，随后各自保留独有的延续。绿色表示只存一份的共享前缀，蓝色表示请求A独有的块，紫色表示请求B独有的块，灰色表示空闲块；这些块可以分散放在GPU物理内存中。</em></p>
<p>第二种技术由第一种衍生而来。由于缓存位于可共享的内存块中，两个开头文本相同的请求可以指向同一批物理内存块，同时各自保留自己的私有延续。这就是前缀缓存（prefix caching）的基础；主流API将其产品化后，称为提示词缓存（prompt caching）。</p>
<p>对于任何会重复前缀的工作负载，这种收益都很大，例如一个智能体每次调用都发送相同的、长达数千词元的系统提示词。OpenAI和Anthropic都报告称，在缓存命中时，成本和延迟能降低50%至90%；缓存词元的收费只是新词元的一部分。</p>
<p>不过，有一点需要注意：跨用户共享缓存状态，已经产生了可泄露其他人提示词信息的计时侧信道（timing side-channel）。这是一个仍受到关注的问题，本文暂不展开。</p>
<h2>权衡</h2>
<p>我们讨论的这些技术，在节省内存方面看起来相似，但为此付出的代价差异很大。</p>
<p>有些几乎不需要付出代价。例如：</p>
<ul>
<li>分组查询注意力的质量代价很小，已经成为安全的默认选择，这也是几乎所有当前模型都采用它的原因。</li>
<li>分页注意力和前缀缓存几乎不影响质量，因为它们改变的是缓存如何存储和共享，没有改变缓存里的内容。</li>
</ul>
<p>另一些技术要求付出更多。例如：</p>
<ul>
<li>8位量化的代价较低，进一步降到4位及以下时，风险就会增加，因此合适的设置取决于任务有多敏感。</li>
<li>在各种架构方案中，潜在注意力节省的内存最多，但要把它用于高效的推理服务，需要实实在在的工程投入。</li>
<li>逐出会释放大量内存，也可能丢失后续生成所需的信息，因此这确实是一场冒险，不能算毫无代价的收益。</li>
</ul>
<p><img src="https://substack-post-media.s3.amazonaws.com/public/images/55198691-ef0b-4887-8ef7-18f523ca8145_2472x1566.png" alt="不同缓存优化方案的内存收益与质量、复杂度风险"></p>
<p><em>图中文字译文：横轴表示节省的内存，从少到多；纵轴表示质量或复杂度风险，从低到高。低风险区包括8位量化、分页注意力、分组查询注意力和前缀缓存；中等风险区包括4位量化和潜在注意力；逐出位于高风险区。</em></p>
<p>对于短上下文，缓存很小，大部分技术解决的是尚未出现的问题。在长上下文和高并发情况下，缓存成为主导成本，这些技术才有用武之地。合适的组合要随工作负载而定：智能体循环倾向于复用，长文档检索则倾向于避免逐出。</p>
<h2>结语</h2>
<p>长上下文推理的成本，归结于一个缓存，而它的大小由一个简短的公式决定。</p>
<p>由于解码每生成一个词元都要读取整个缓存，缓存带来的既是存储成本，也是带宽成本。这也是为什么缩小缓存能够提速。我们讨论的每种优化，都针对公式中的某一部分，或削减与缓存有关的浪费。</p>
<ul>
<li>分组查询注意力和潜在注意力降低每个词元的成本。</li>
<li>量化用更少的位存储每个数。</li>
<li>逐出保留更少的词元。</li>
<li>分页注意力和前缀缓存更高效地管理、共享缓存。</li>
</ul>
