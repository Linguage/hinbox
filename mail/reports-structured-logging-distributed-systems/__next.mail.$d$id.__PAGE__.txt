<h2>我为什么写这篇文章（以及它为什么与你有关）</h2>
<p>过去几个月，在审查多个服务的拉取请求时，我注意到一种反复出现的情况：开发者这样写日志 👇</p>
<pre><code class="language-csharp">_logger.LogError($"Exception during Order Service call for OidcScheme: {ex.Message}");
</code></pre>
<p>乍看之下，似乎没什么问题。但这一行代码悄悄违背了可观测性（observability）的一项核心原则：结构化日志（structured logging）。</p>
<p>在不同服务中，我不断看到团队使用字符串插值、拼接变量，或者毫无结构地记录整个对象。结果呢？这些日志在控制台里看着还行，可一旦进入生产环境，就无法查询、关联或分析了。</p>
<p>这就是我写这篇文章的原因：解释结构化日志究竟是什么意思，为什么值得在每个服务中采用，以及几项好做法如何把日志变成强大的调试和分析工具。</p>
<p>⚠️ 提醒：这篇文章会很长，请耐心读下去。读完后，你就会清楚地知道怎样正确记录数据，让日志有结构、可搜索，并能应对真实世界的系统规模。</p>
<p>它不会教你如何设计 Kafka 集群、构建 Uber 规模的系统，或者为十亿用户的平台设计架构，但会帮助你深入理解每位优秀系统架构师都需要掌握的一件事：如何让系统可观测、可解释，并能自我描述。</p>
<p>如果你曾在生产事故中被数百行日志淹没，或者追着一个关联 ID（correlation ID）穿过十个微服务，那么这篇文章就是为你写的。</p>
<h2>什么是结构化日志？</h2>
<p>传统日志把日志当作纯文本。你可能这样写：</p>
<pre><code class="language-csharp">_logger.LogError($"Error processing order {orderId} for user {userId}");
</code></pre>
<p>它会产生这样的输出：</p>
<pre><code class="language-text">Error processing order 1024 for user 888
</code></pre>
<p>看起来没问题，直到你需要：</p>
<ul>
<li>查找 <code>userId=888</code> 的所有错误。</li>
<li>按某个特定的 <code>orderId</code> 筛选所有日志。</li>
<li>在多个微服务之间关联这个事件。</li>
</ul>
<p>日志查看器看到的只是一团文本。它没有结构，没有可搜索的字段，也没有能帮助你从不同角度切分和分析数据的元数据。</p>
<p>现在，让我们用结构化日志重写它：</p>
<pre><code class="language-csharp">_logger.LogError("Error processing order {OrderId} for user {UserId}", orderId, userId);
</code></pre>
<p>这个简单的变化，把日志从文本变成了数据。</p>
<p>一条结构化日志在底层可能是这样的：</p>
<pre><code class="language-json">{
  "Timestamp": "2025-10-21T08:33:12Z",
  "Level": "Error",
  "MessageTemplate": "Error processing order {OrderId} for user {UserId}",
  "Properties": {
    "OrderId": 1024,
    "UserId": 888
  }
}
</code></pre>
<p>突然之间，你就可以查询：</p>
<ul>
<li><code>OrderId = 1024</code></li>
<li><code>UserId = 888</code></li>
<li>甚至创建“触发错误最多的前10位用户”仪表盘。</li>
</ul>
<p>结构化日志把文本流转化为可查询、可分析、机器可读的事件。</p>

<h2>为什么结构化日志很重要</h2>
<p>结构化日志不只是一种语法风格，它关系到大规模系统的可观测性。我们来看看它如何帮助真实系统。</p>
<h3>1. 可搜索性与筛选</h3>
<p>日志有了结构，你就能提出很有用的问题，例如：</p>
<ul>
<li>显示所有 <code>status='timeout'</code> 的失败支付。</li>
<li>按地区或 <code>tenantId</code> 对错误分组。</li>
<li>显示过去24小时内 <code>OrderFailed</code> 事件的变化趋势。</li>
</ul>
<p>在纯文本日志中，如果没有脆弱的正则表达式搜索，几乎不可能做到这些。在结构化日志中，这只是一条筛选查询。</p>
<h3>2. 性能与效率</h3>
<p>当你使用结构化模板时，大多数日志框架（例如 Serilog、NLog、Microsoft.Extensions.Logging）会推迟字符串格式化。</p>
<p>因此，不再使用：</p>
<pre><code class="language-csharp">$"Error processing order {orderId}"
</code></pre>
<p>这种字符串会立即格式化。结构化模板则像这样：</p>
<pre><code class="language-csharp">"Error processing order {OrderId}"
</code></pre>
<p>只有启用了相应日志级别，才会对它进行惰性求值（lazy evaluation）。<sup><a href="#user-content-fn-template-evaluation" id="user-content-fnref-template-evaluation" data-footnote-ref aria-describedby="footnote-label">1</a></sup></p>
<p>这能避免不必要的 CPU 消耗和内存分配，尤其是在日志量很大的情况下。</p>
<h3>3. 与可观测性工具集成</h3>
<p>结构化日志是以下平台的支柱：</p>
<ul>
<li>Elastic Stack（ELK）</li>
<li>Seq</li>
<li>Splunk</li>
<li>Azure Application Insights</li>
<li>Datadog</li>
<li>Grafana Loki</li>
</ul>
<p>这些工具依靠结构化字段（<code>{UserId}</code>、<code>{OrderId}</code>）来支持仪表盘、告警和异常检测。</p>
<p>没有结构，日志就是静态文本；有了结构，它们就成为指标、维度和洞察。</p>
<h2>两种日志的故事：文本与结构化日志</h2>
<p>设想一个处理交易的支付服务。</p>
<h3>❌ 传统日志</h3>
<pre><code class="language-csharp">_logger.LogError($"Payment failed for user {userId}. Amount: {amount}, Reason: {reason}");
</code></pre>
<p>输出：</p>
<pre><code class="language-text">Payment failed for user 101. Amount: 249.99, Reason: insufficient funds
</code></pre>
<p>要查找所有 <code>Reason = insufficient funds</code>（余额不足）的支付，你得搜索原始文本，还得寄希望于每位开发者的拼写都一致。</p>
<h3>✅ 结构化日志</h3>
<pre><code class="language-csharp">_logger.LogError("Payment failed for user {UserId}. Amount: {Amount}, Reason: {Reason}", userId, amount, reason);
</code></pre>
<p>现在你可以查询：</p>
<pre><code class="language-text">Reason = "insufficient funds"
</code></pre>
<p>并立即获得指标、趋势和汇总。</p>
<p>这篇文章原本是一篇仅供付费会员阅读的文章。但我看到，即使经验很丰富的开发者，也会犯这些错误，所以决定向所有人免费开放它。</p>
<h2>系统设计视角：日志架构模式</h2>
<h3>三层日志架构</h3>
<p>在生产系统中，结构化日志通常遵循三层架构：</p>
<p><img src="https://substackcdn.com/image/fetch/$s_!YhWH!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F0ed490ab-9381-4c60-a356-9006affae63d_541x432.png" alt="三层日志架构"></p>
<p>图中从上到下依次为：应用服务 → 日志聚合器（Fluentd／Logstash）→ 存储与查询引擎（Elasticsearch），分别对应生成层、收集与传输层、存储与分析层。</p>
<h3>第1层：生成层</h3>
<ul>
<li>应用程序输出结构化日志。</li>
<li>在这一层富化上下文（请求 ID、用户 ID、追踪 ID）。</li>
<li>通过本地缓冲提升性能。</li>
</ul>
<h3>第2层：收集与传输</h3>
<ul>
<li>日志采集代理从多个来源收集日志。</li>
<li>协议归一化（syslog、JSON 等）。</li>
<li>筛选和路由逻辑。</li>
<li>背压（backpressure）处理。</li>
</ul>
<h3>第3层：存储与分析</h3>
<ul>
<li>带索引的长期存储。</li>
<li>面向日志分析的查询优化。</li>
<li>保留策略和归档。</li>
<li>实时告警和仪表盘。</li>
</ul>
<h3>真实系统示例</h3>
<h3>Stripe 的支付处理日志</h3>
<p>Stripe 的支付基础设施依靠结构化日志进行合规管理和调试：<sup><a href="#user-content-fn-logging-templates" id="user-content-fnref-logging-templates" data-footnote-ref aria-describedby="footnote-label">2</a></sup></p>
<pre><code class="language-csharp">_logger.LogInformation(
    "Payment intent {PaymentIntentId} transitioned from {OldState} to {NewState}",
    new {
        PaymentIntentId = "pi_123",
        OldState = "requires_confirmation",
        NewState = "processing",
        Amount = 5000,
        Currency = "USD",
        Customer = "cus_abc",
        Merchant = "acct_xyz",
        PaymentMethod = "pm_card_visa",
        // Audit trail fields
        IpAddress = request.IpAddress,
        UserAgent = request.UserAgent,
        ApiVersion = "2024-11-01",
        IdempotencyKey = request.IdempotencyKey
    });
</code></pre>
<p>👉 JSON 日志很好用，直到你不小心把整个 <code>HttpContext</code> 都记了下来——于是，1 GB 可用磁盘空间突然变成0 GB，再加一肚子后悔。</p>
<h4>为什么这很重要</h4>
<ul>
<li>合规：每一次状态转换都可以追踪。</li>
<li>调试：可以重建准确的支付流程。</li>
<li>分析：了解各状态的转化率。</li>
<li>欺诈检测：结构化数据会显现出规律。</li>
</ul>
<h2>分布式系统的进阶模式</h2>
<p>分布式系统，例如微服务架构，会增加跨多个服务跟踪、调试和监控用户交互的复杂性。进阶日志模式利用结构化日志提供可追踪性、业务洞察和运行效率，从而应对这些挑战。</p>
<h3>模式1：关联 ID 与请求跟踪</h3>
<p>在分布式系统中，一次用户操作往往会触发跨多个服务的一连串请求，例如 API 网关、身份认证服务、订单服务。如果没有统一的方法来跟踪这些交互，调试几乎不可能进行。关联 ID 为每个用户请求分配一个唯一标识符，并在该请求生命周期所涉及的所有服务之间传递它，从而解决这个问题。各服务的日志都包含该标识符，因此可以进行端到端追踪。</p>
<pre><code class="language-csharp">var correlationId = context.Request.Headers["X-Correlation-ID"] .FirstOrDefault() ?? Guid.NewGuid().ToString();
</code></pre>
<p>现在，请求管道中的每条日志都会自动包含关联 ID：<sup><a href="#user-content-fn-correlation-context" id="user-content-fnref-correlation-context" data-footnote-ref aria-describedby="footnote-label">3</a></sup></p>
<pre><code class="language-json">{
  "CorrelationId": "abc-123-def",
  "Service": "api-gateway",
  "Message": "Request received"
}

{
  "CorrelationId": "abc-123-def",
  "Service": "auth-service",
  "Message": "User authenticated"
}
</code></pre>
<p>按 <code>CorrelationId = "abc-123-def"</code> 查询，就能看到完整的故事。</p>
<h4>为什么这很重要</h4>
<ul>
<li>可追踪性：关联 ID 把不同服务的日志串在一起，形成请求历程的完整叙述。例如，可以从前端开始，经过支付和库存服务，追踪用户的结账操作。</li>
<li>调试效率：出现问题时，通过关联 ID 查询日志，可以揭示准确的事件顺序，确定故障发生的位置。</li>
<li>用户体验洞察：跟踪完整的请求路径，团队就能找出瓶颈，或影响性能的服务。</li>
</ul>
<h4>实现时的考虑</h4>
<ul>
<li>在入口处（例如 API 网关）生成或提取关联 ID，通过 HTTP 请求头或消息元数据传递它。</li>
<li>确保链条中的每个服务都在日志中包含关联 ID，通常将其作为结构化属性。</li>
<li>使用集中式日志聚合工具（例如 ELK Stack、Splunk），按关联 ID 查询日志，获得统一视图。</li>
<li>对 ID 缺失或重复等边界情况，通过生成备用 ID 或验证输入来处理。</li>
</ul>
<h4>可进一步增强的方面</h4>
<ul>
<li>嵌套关联：对于复杂工作流，例如父请求生成子请求，可使用层级 ID 来跟踪子流程。</li>
<li>跨系统传递：在发出的请求中包含关联 ID，将其扩展至外部系统，例如第三方 API。</li>
<li>超时跟踪：把关联 ID 与时间戳结合，检测超过预期时长的请求。</li>
</ul>
<h4>适用场景</h4>
<ul>
<li>包含相互依赖服务的微服务或分布式架构。</li>
<li>为调试或合规而需要端到端请求追踪的系统。</li>
<li>请求量很高、无法实际进行人工日志关联的环境。</li>
</ul>
<h3>模式2：以领域事件实现语义日志</h3>
<p>语义日志（semantic logging）把关注点从技术追踪记录（例如“收到 API 调用”）转向与业务相关的事件（例如“订单已下单”）。</p>
<pre><code class="language-csharp">public class OrderEventLogger
{
    public void LogOrderPlaced(Order order)
    {
        _logger.LogInformation(
            "OrderPlaced event",
            new {
                EventType = "OrderPlaced",
                OrderId = order.Id,
                CustomerId = order.CustomerId,
                TotalAmount = order.TotalAmount,
                ItemCount = order.Items.Count,
                PaymentMethod = order.PaymentMethod,
                ShippingAddress = order.ShippingAddress.ToLogSafeFormat(),
                Timestamp = DateTimeOffset.UtcNow
            });
    }
}
</code></pre>
<h4>为什么这很重要</h4>
<ul>
<li>与业务对齐：日志反映业务领域的语言和概念，让产品经理等非技术相关人员也能理解。</li>
<li>支持分析：可以查询结构化领域事件（domain events），获得转化率、平均订单金额或履约时间等指标。</li>
<li>事件溯源基础：语义日志可以充当轻量的事件存储，支持事件驱动架构或审计需求。</li>
<li>减少噪声：聚焦有意义的事件，排除价值较低的技术日志，使信息更清晰。</li>
</ul>
<h4>实现时的考虑</h4>
<ul>
<li>与业务相关人员共同定义领域事件，确保日志捕获相关属性。例如，记录 <code>OrderShipped</code> 事件时，包括追踪号、承运商和预计送达信息。</li>
<li>使用 JSON 等结构化日志格式，确保机器可读且可查询。</li>
<li>在各服务间统一事件命名和属性，以支持一致的分析。</li>
<li>平衡细节与日志量：只包含必要属性，避免日志膨胀。</li>
</ul>
<h4>可进一步增强的方面</h4>
<ul>
<li>事件版本管理：包含版本元数据，以应对事件模式随时间发生的变化。</li>
<li>业务规则验证：只有满足业务规则时才记录事件，例如，仅对有效订单记录 <code>OrderPlaced</code>。</li>
<li>实时洞察：把领域事件流式发送到分析平台，立即提供业务报告。</li>
<li>跨领域关联：使用共享标识符关联相关事件，例如 <code>OrderPlaced</code> 和 <code>PaymentProcessed</code>。</li>
</ul>
<h4>适用场景</h4>
<ul>
<li>业务流程复杂、需要了解领域活动的系统。</li>
<li>采用数据驱动决策或事件溯源（event sourcing）模式的组织。</li>
<li>需要把技术日志与业务结果连接起来的团队。</li>
</ul>
<h3>模式3：日志富化管道</h3>
<p>日志富化（log enrichment）是在请求生命周期的不同阶段，自动为日志添加上下文元数据。这些元数据，例如环境详情、用户信息或基础设施上下文，可以增强日志，而不需要开发者在每条日志语句中手动加入它们。富化通过管道进行，通常发生在应用入口或日志处理过程中。</p>
<pre><code class="language-csharp">public class LogEnricherMiddleware
{
    public async Task InvokeAsync(HttpContext context)
    {
        // Enrich with deployment context
        using (LogContext.PushProperty("Environment", _environment.EnvironmentName))
        using (LogContext.PushProperty("MachineName", Environment.MachineName))
        using (LogContext.PushProperty("AppVersion", _appVersion))
        
        // Enrich with request context
        using (LogContext.PushProperty("ClientIp", context.Connection.RemoteIpAddress))
        using (LogContext.PushProperty("UserAgent", context.Request.Headers["User-Agent"]))
        
        // Enrich with user context (if authenticated)
        using (LogContext.PushProperty("UserId", context.User?.Identity?.Name))
        using (LogContext.PushProperty("TenantId", context.User?.FindFirst("tenant_id")?.Value))
        {
            await _next(context);
        }
    }
}
</code></pre>
<h4>为什么这很重要</h4>
<ul>
<li>一致性：富化确保所有日志都包含关键上下文，例如用户 ID、应用版本，而不需要开发者干预。</li>
<li>调试效率：客户端 IP、租户 ID 或机器名称等上下文数据，有助于缩小问题范围，无须与外部系统交叉核对。</li>
<li>可扩展性：自动富化减少开发者的负担，让他们可以专注于业务逻辑。</li>
<li>合规与审计：富化后的日志完整呈现谁在何时、何地做了什么，从而支持监管要求。</li>
</ul>
<h4>实现时的考虑</h4>
<ul>
<li>确定富化数据的来源，例如 HTTP 请求头（如 User-Agent）、身份认证令牌（如用户 ID）或系统元数据（如环境名称）。</li>
<li>在请求管道的早期应用富化，例如通过中间件，确保下游的所有日志都继承这些上下文。</li>
<li>使用支持动态属性或作用域的日志框架，传递富化数据。</li>
<li>避免过度富化，它可能增加日志量或暴露敏感数据，例如，应清理用户输入。</li>
</ul>
<h4>可进一步增强的方面</h4>
<ul>
<li>动态富化：根据请求类型或用户角色调整富化，例如，为管理员用户添加详细上下文。</li>
<li>外部富化：使用外部系统的数据补充日志，例如，从客户端 IP 推导的地理位置。</li>
<li>集中式富化：在日志聚合过程中进行富化，添加应用层无法获得的上下文，例如集群节点详情。</li>
<li>隐私合规：在富化期间掩码处理敏感数据（例如个人可识别信息，PII），或将其匿名化，以满足 GDPR 或 CCPA 的要求。</li>
</ul>
<h4>适用场景</h4>
<ul>
<li>各服务或团队的日志需求多样的系统。</li>
<li>需要租户专属上下文的多租户应用。</li>
<li>日志用于审计、合规或详细调试的环境。</li>
</ul>
<h3>模式4：结构化异常日志</h3>
<p>分布式系统中的异常包含关键诊断信息，但非结构化的异常日志，例如纯文本堆栈跟踪，很难查询或分析。结构化异常日志把异常捕获为结构化数据，其中包括异常类型、消息、堆栈跟踪、错误码和自定义数据等属性。这种方法让异常变得机器可读，并能据此采取行动。</p>
<pre><code class="language-csharp">public static class ExceptionLoggingExtensions
{
    public static void LogStructuredException(
        this ILogger logger, 
        Exception ex, 
        string message,
        params object[] args)
    {
        var exceptionData = new
        {
            ExceptionType = ex.GetType().Name,
            ExceptionMessage = ex.Message,
            StackTrace = ex.StackTrace,
            InnerExceptionType = ex.InnerException?.GetType().Name,
            InnerExceptionMessage = ex.InnerException?.Message,
            HResult = ex.HResult,
            Source = ex.Source,
            TargetSite = ex.TargetSite?.Name,
            CustomData = ex.Data.Cast&#x3C;DictionaryEntry>()
                           .ToDictionary(e => e.Key.ToString(), e => e.Value)
        };
        
        logger.LogError(ex, message + " {ExceptionData}", 
                       args.Append(exceptionData).ToArray());
    }
}

// Usage
try
{
    await ProcessPayment(orderId);
}
catch (PaymentGatewayException ex)
{
    _logger.LogStructuredException(
        ex,
        "Payment processing failed for order {OrderId}",
        orderId);
}
</code></pre>
<h4>为什么这很重要</h4>
<ul>
<li>可查询性：结构化异常数据让团队可以按类型、来源或影响筛选和分析错误。</li>
<li>根因分析：捕获内部异常或错误码等细节，有助于找出跨服务问题背后的原因。</li>
<li>主动监控：结构化日志让告警系统能够检测反复出现的异常或错误模式。</li>
<li>开发者效率：标准化的异常日志减少了解析非结构化堆栈跟踪所花的时间。</li>
</ul>
<h4>实现时的考虑</h4>
<ul>
<li>捕获一致的一组异常属性，例如类型、消息、堆栈跟踪、内部异常和错误码。</li>
<li>包含与异常相关的上下文数据，例如触发异常的请求或用户。</li>
<li>使用结构化日志格式，确保可以在日志聚合工具中查询异常。</li>
<li>谨慎处理敏感数据，除非必要，否则避免记录支付详情等机密信息。</li>
</ul>
<h4>可进一步增强的方面</h4>
<ul>
<li>异常分类：按严重程度或影响标记异常，例如关键异常与暂时性异常，以便确定响应优先级。</li>
<li>与事件关联：把异常与领域事件或关联 ID 连接起来，追踪其业务影响。</li>
<li>自定义元数据：允许开发者为异常附加领域相关数据，例如支付失败时的订单 ID。</li>
<li>聚合与去重：在日志分析中对相似异常分组，减少噪声，并识别趋势。</li>
</ul>
<h4>适用场景</h4>
<ul>
<li>异常频繁，或异常对可靠性至关重要的系统。</li>
<li>需要详细错误分析或自动告警的应用。</li>
<li>错误可能源自下游服务的分布式环境。</li>
</ul>
<h3>模式5：性能指标日志</h3>
<p>性能指标日志把请求延迟、状态码或资源使用量等运行指标嵌入结构化日志。这些日志有两个用途：既提供诊断信息，也充当监控系统健康和性能的轻量指标系统。通过对指标分类，例如延迟分桶、错误标志，日志成为性能分析的有力工具。</p>
<h4>为什么这很重要</h4>
<ul>
<li>统一可观测性：将指标与日志结合，减少对单独遥测系统的需求，简化基础设施。</li>
<li>细粒度洞察：可以按端点、服务或用户查询请求时长、错误率等指标，识别瓶颈。</li>
<li>趋势分析：结构化指标支持计算 P95／P99 延迟，或错误率随时间变化的趋势。</li>
<li>成本效率：对于较小的系统，基于日志的指标可以避免专用指标平台的开销。</li>
</ul>
<h4>实现时的考虑</h4>
<ul>
<li>记录关键性能指标，例如请求方法、路径、状态码、时长和响应大小。</li>
<li>对指标分类以方便分析，例如标记慢请求，或将延迟分为“快”“中等”“慢”几个桶。</li>
<li>确保日志保持轻量，避免性能开销，聚焦高价值指标。</li>
<li>与日志聚合工具集成，将指标可视化，或在达到阈值时触发告警。</li>
</ul>
<h4>可进一步增强的方面</h4>
<ul>
<li>百分位分析：聚合日志，计算延迟百分位，例如 P95，用于性能基准比较。</li>
<li>错误关联：标记发生错误或延迟较高的请求，关联性能与故障。</li>
<li>动态阈值：根据服务或一天中的时段调整性能阈值，例如高峰时段采用更严格的阈值。</li>
<li>跨服务指标：借助关联 ID，结合多个服务的指标，分析端到端性能。</li>
</ul>
<h4>适用场景</h4>
<ul>
<li>需要轻量性能监控、没有专用指标基础设施的系统。</li>
<li>有严格性能 SLA，需要详细跟踪延迟或错误的应用。</li>
<li>性能问题可能跨越多个服务的分布式系统。</li>
</ul>
<p>👉 没有结构化日志就去调试生产环境，就像戴着连指手套，在夜里的大海中找钥匙。</p>
<h2>应避免的常见错误</h2>
<h3>❌ 1. 使用字符串插值或拼接</h3>
<p>这是最常见的反模式（anti-pattern）：</p>
<pre><code class="language-csharp">_logger.LogError($"Exception during Order Service call: {ex.Message}");
</code></pre>
<p>为什么它不好：</p>
<ul>
<li>丢失结构化数据（<code>ex.Message</code> 变成纯文本）。</li>
<li>即使不输出日志，也会立即格式化。</li>
<li>使查询和分析无法进行。</li>
</ul>
<p>✅ 正确做法：</p>
<pre><code class="language-csharp">_logger.LogError(ex, "Exception during Order Service call: {ErrorMessage}", ex.Message);
</code></pre>
<h3>❌ 2. 记录过多日志，或日志过于冗长</h3>
<p>结构化日志赋予你能力，但不要把眼前的每个变量都记下来。</p>
<p>避免这样做：</p>
<pre><code class="language-csharp">_logger.LogInformation("User {User} logged in with token {JwtToken}", user, jwtToken);
</code></pre>
<p>该令牌可能暴露敏感数据或个人可识别信息（PII）。</p>
<p>👉 记住：如果你在日志里记录密码，你不是在调试，而是在为数据泄露留档。</p>
<p>✅ 最佳实践：对敏感字段进行删隐或掩码处理：</p>
<pre><code class="language-csharp">_logger.LogInformation("User {UserId} logged in successfully", user.Id);
</code></pre>
<h3>❌ 3. 使用不一致的字段名</h3>
<p>属性名称不一致会破坏分析。一个开发者可能用 <code>{UserId}</code>，另一个用 <code>{UserID}</code>，第三个用 <code>{user_id}</code>，于是仪表盘就失去了作用。</p>
<p>✅ 最佳实践：在整个代码库中采用标准化命名约定（PascalCase 或 snake_case），并通过日志中间件或 lint 规则强制执行。</p>
<h3>❌ 4. 把所有日志都记录为 Error 级别</h3>
<p>有些团队为了“保险”，把所有内容都记录为 <code>Error</code>。但这违背了日志级别的用途，会淹没你的告警系统。</p>
<p>✅ 使用合适的日志级别：</p>
<ul>
<li><code>Trace</code>：深入调试。</li>
<li><code>Debug</code>：开发者诊断。</li>
<li><code>Information</code>：应用的高层流程。</li>
<li><code>Warning</code>：出现意外，但可以恢复。</li>
<li><code>Error</code>：操作失败。</li>
<li><code>Critical</code>：应用或系统故障。</li>
</ul>
<p>这样可以帮助可观测性平台筛出真正重要的信息。</p>
<h3>❌ 5. 没有记录足够的上下文</h3>
<pre><code class="language-csharp">// Too little context
_logger.LogError("Payment failed");

// Better - includes context
_logger.LogError(
    "Payment failed for order {OrderId}, user {UserId}, reason {FailureReason}",
    orderId, userId, failureReason);
</code></pre>
<h3>❌ 6. 直接记录大型对象</h3>
<pre><code class="language-csharp">// Bad - logs entire object, could be massive
_logger.LogInformation("Processing request {Request}", complexRequest);

// Good - log only relevant fields
_logger.LogInformation(
    "Processing request {RequestId} for user {UserId}",
    complexRequest.Id, complexRequest.UserId);
</code></pre>

<h2>架构师的看法</h2>
<p>日志不只是记录发生了什么，还要帮助理解为什么会发生。</p>
<p>结构化日志填补了这道鸿沟。它让架构师看清复杂系统的动态行为，支持更好的根因分析、运行洞察和主动告警。</p>
<p>随着系统规模扩大，结构化日志会变得与指标或追踪同样不可或缺。它们是代码与可观测性之间的连接组织，是一种你能够分析、可视化并从中学习的真实记录。</p>
<p>所以下次写日志时，不要只写文本。写数据。因为总有一天，未来的你会在凌晨3点调试一个生产问题，而结构化日志将是那束引你回家的手电光。</p>
