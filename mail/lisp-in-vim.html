在 Vim 中写 Lisp：Slimv 与 Vlime 的实践比较

摘要

本文介绍如何在 Vim 中搭建 Lisp 开发环境，并重点比较 Slimv 与 Vlime 两个插件。文章从 Lisp、Emacs 的 SLIME 传统讲起，说明 Vim 如何借助 Swank、REPL、调试器、补全、宏展开、交叉引用等能力，获得接近交互式 Lisp 编程的体验。作者最后更推荐 Slimv，因为它安装简单、功能覆盖更广，且支持 Common Lisp、Scheme 与 Clojure。

内容框架与概述

文章先交代背景。Lisp 是一种历史悠久、语法独特、以括号和前缀表达式著称的语言，拥有强大的宏系统和自省能力。许多 Lisp 程序员习惯使用 Emacs，因为 SLIME 提供了 REPL、调试器、交互式求值等能力。Slimv 和 Vlime 可以看作 Vim 世界中对这套工作方式的回应，它们都通过 Swank 服务器连接编辑器与 Lisp 运行环境。

接着文章分别演示 Slimv 和 Vlime 的安装与基本使用。Slimv 安装相对直接，但需要带 Python 接口的 Vim，并且在自动启动 Swank 时依赖 tmux、GNU Screen 或桌面环境。Vlime 不要求 Vim 支持 Python，也能自行启动服务，但需要安装 Quicklisp，并且目录结构与 Vim 原生 package 机制不完全匹配。文章还介绍了 Paredit，它负责结构化编辑 Lisp 表达式，避免括号失衡，是写 Lisp 时非常关键的辅助工具。

后半部分集中比较两者的功能细节，包括调试器、对象检查器、函数追踪、顶层表达式求值、彩虹括号、参数提示、补全、符号说明、宏展开和交叉引用等。Slimv 的 REPL 可直接交互，默认键位更顺手，支持 Common Lisp、Scheme 和 Clojure。Vlime 的交叉引用跳转体验更好，但 REPL 不可直接编辑，很多结果会打开额外分屏。作者最后建议优先尝试 Slimv，同时也鼓励读者根据自己的使用习惯比较两者。

核心概念及解读

Lisp：一种程序语言家族，特点是大量使用括号、前缀表达式和代码即数据的思想。它看起来古怪，但强在表达力和可扩展性，尤其适合理解语言设计、宏系统和交互式编程。

SLIME：Superior Lisp Interaction Mode for Emacs，是 Emacs 中经典的 Lisp 开发环境。它把编辑器、REPL、调试器和运行时连接起来，让程序员可以一边写代码一边即时求值、调试和检查对象。

Swank：SLIME 背后的服务器组件，用 Common Lisp 编写。编辑器插件把请求发给 Swank，Swank 再在 Lisp 运行环境中执行代码、返回结果。Slimv 和 Vlime 都依赖这种客户端与服务器分离的结构。

Paredit：一种结构化编辑工具，专门处理 Lisp 的括号表达式。它会自动补全括号、阻止破坏表达式结构的删除操作，并提供 slurp、barf 等编辑动作，让 Lisp 代码更容易保持合法形态。

REPL：Read Eval Print Loop，读取、求值、打印、循环。它是 Lisp 交互式开发的核心。普通语言常常是写完文件再运行，Lisp 的典型体验是随写随试，函数、表达式、宏都可以直接在运行环境中验证。

Lisp 开发的核心体验：交互式编程

Lisp 的开发方式很依赖交互。写代码、发送表达式、立即求值、查看结果、继续修改，这一套流程和很多常规语言的写完文件再运行差别很大。

这种体验的中心是 REPL，也就是读取、求值、打印、循环。程序员可以直接把一个表达式送进 Lisp 运行环境，马上看到结果。函数可以局部测试，宏可以展开检查，错误可以当场进入调试器。编辑器在这里不只是写文本的地方，还要能连接运行时。

在 Emacs 里，SLIME 很早就把这套体验做成熟了。Vim 用户想获得类似能力，就需要 Slimv 或 Vlime 这样的插件，把 Vim 和 Lisp 运行环境接起来。

Lisp 的语言特征决定了编辑器需求

括号表达式需要结构化编辑

Lisp 代码由大量 s-expression 组成，括号层级很深。如果编辑器只提供普通文本编辑，写起来容易出现括号不配对、表达式结构损坏等问题。

Paredit 的价值就在这里。它会自动补全括号，阻止一些破坏结构的删除动作，还提供 slurp 和 barf 这类专门移动表达式边界的操作。对 Lisp 来说，这类工具不是锦上添花，而是让代码保持可编辑、可运行的基本设施。

宏系统需要即时展开与检查

Lisp 的宏可以把代码转换成另一段代码。写宏时，程序员需要频繁查看宏展开结果，确认生成的表达式是否符合预期。

Slimv 和 Vlime 都支持宏展开。一次展开可以看到当前宏展开后的形式，递归展开可以继续展开到不再是宏为止。这样写宏不会完全依赖脑补，运行环境会把转换结果直接展示出来。

Emacs 的 SLIME 是 Vim 插件的参照系

SLIME 提供了 Lisp 开发环境的一个标准样子：REPL、调试器、对象检查器、交互式求值、补全、参数提示和源码跳转。

Slimv 和 Vlime 的很多设计都在回应 SLIME。它们也采用客户端与服务器结构，让编辑器通过 Swank 服务器和 Lisp 运行环境通信。编辑器负责发送命令，Swank 负责执行 Lisp 表达式、返回结果和调试信息。

所以理解 Slimv 和 Vlime，不能只把它们看成普通 Vim 插件。它们承担的是把 Vim 改造成 Lisp 交互式开发环境的任务。

Swank 是编辑器和 Lisp 运行时之间的桥

Swank 是一个 Common Lisp 后端服务。编辑器插件把命令发送给 Swank，Swank 在 Lisp 运行环境里执行，再把结果传回编辑器。

Slimv 内置了一个略作修改的 Swank，因此安装 Slimv 后就可以比较直接地启动和连接。Vlime 不内置 Swank，而是通过 Quicklisp 在需要时安装和加载。

这个差异带来了两个后果。Slimv 的安装和启动链条更短，依赖更少。Vlime 的方案更依赖 Quicklisp，第一次启动时可能会慢一些，但它自己能启动服务，不需要 tmux、GNU Screen 或桌面环境配合。

Vim 8 的 package 机制让插件安装更简单

过去安装 Vim 插件通常要手动复制到 ~/.vim 目录，或者依赖 Pathogen、Vundle、vim-plug 等插件管理器。Vim 8 提供了原生 package 机制，插件放进 ~/.vim/pack/plugins/start 就能自动加载。

Slimv 的目录结构符合 Vim package 的预期，所以可以直接放进这个目录。Vlime 的目录结构比较特殊，真正的 Vim 插件目录在 vim 子目录中，因此还要手动把路径加入 runtimepath。

这也是 Slimv 在安装便利性上的优势之一。目录结构越符合 Vim 的默认习惯，维护成本就越低。

Slimv 的上手路径更直接

安装依赖较少

Slimv 需要带 Python 接口的 Vim，比如 Debian 下的 vim-nox。它还常常配合 SBCL、tmux 和 git 使用。

安装 Slimv 本身比较简单，克隆仓库到 Vim package 目录，再生成 help tags 即可。由于 Slimv 自带 Swank 和 Paredit，用户不需要额外安装太多东西。

REPL 可以直接输入表达式

Slimv 的 REPL 是可交互的。切换到 REPL 窗口后，可以直接输入表达式并求值。这一点很接近传统 Lisp REPL 的使用习惯。

这种交互对学习和调试很友好。想试一个表达式，不必回到源文件里写临时代码，也不用额外打开终端，直接在 Vim 里完成。

自动启动 Swank 依赖运行环境

Slimv 可以自动启动 Swank，但前提是 Vim 运行在 tmux、GNU Screen 或桌面环境里。如果没有这些条件，就需要手动启动 Swank。

这不是特别大的问题，但对纯终端环境用户来说，需要提前知道这个限制。

Vlime 的启动机制更独立

不要求 Vim 支持 Python

Vlime 可以在 Debian 默认的 vim.basic 中运行，不要求 Vim 编译 Python 接口。对一些轻量环境来说，这是明显优势。

依赖 Quicklisp

Vlime 需要安装 Quicklisp。第一次启动 Vlime server 时，会通过 Quicklisp 安装 Swank，所以第一次连接可能比较慢。后续启动会快一些。

Quicklisp 是 Common Lisp 生态里的库管理工具。Vlime 借它管理 Swank，带来一定灵活性，也增加了初始配置步骤。

REPL 不可直接编辑

Vlime 的 REPL 窗口设置为不可修改，不能像普通 REPL 一样直接输入表达式。它提供 interaction mode 作为补救：开启后，在源码缓冲区里按回车就可以求值当前表达式。

这种设计能完成工作，但少了一点直接感。对习惯交互式 REPL 的 Lisp 用户来说，会显得不太顺手。

Paredit 是 Lisp 编辑体验的基础工具

自动保持括号平衡

Paredit 会在输入左括号时自动补全右括号，输入引号时也会自动补全匹配引号。删除时，它会避免用户随手删掉某个括号导致整个表达式结构损坏。

这类行为刚开始可能有点反直觉，但熟悉后会明显降低 Lisp 编辑成本。编辑器从普通文本处理器变成了表达式结构编辑器。

electric return 改善换行体验

electric return 会在某些位置自动插入额外换行，方便用户在括号内部写新的表达式。完成表达式后，输入右括号又会把多余换行收回来，使代码符合 Lisp 常见的括号排列习惯。

Slimv 对 Paredit 的 electric return 支持较好。Vlime 因为重映射回车键来显示参数列表，没有很好保留这个功能。

slurp 和 barf 调整表达式边界

slurp 可以把相邻表达式吞进当前括号里，barf 可以把内部表达式吐出去。它们解决的是 Lisp 编辑中很常见的问题：表达式边界要调整，但不想手动剪切粘贴括号和代码。

这类操作体现了 Lisp 编辑器的特殊性。编辑对象不是字符，而是表达式。

调试器和对象检查器提升排错效率

错误会直接进入 SLDB

当 Lisp 代码出错，比如把字符串传给需要数字的函数时，Slimv 和 Vlime 都会打开 SLDB 调试窗口。里面会显示错误信息、可用的 restart 选项，以及调用栈。

这让错误现场保留下来。用户可以查看是哪一层调用出了问题，也可以检查局部变量，而不是只看到一条错误消息。

Slimv 的调试操作偏快捷

Slimv 中可以展开调用栈帧，查看局部变量，再用快捷键进入 inspector。退出调试器也很快，常用 ,q 或 ,a 就能回到正常编辑状态。

这种体验适合频繁试错。写 Lisp 时经常会边写边求值，错误不一定是灾难，更多是反馈。

Vlime 的调试信息展示更分散

Vlime 也能查看调用栈和局部变量，还能打开 inspector 检查对象。但它更常使用额外 split window 展示结果。

好处是不同信息有自己的窗口，坏处是窗口切换变多，使用 Vim 的 ctrl 加 w 加 w 循环窗口时会更繁琐。

函数追踪用于观察调用过程

Slimv 的追踪结果直接进入 REPL

Slimv 可以对某个函数开启 trace。函数被调用时，参数和返回值会显示在 REPL 里。

比如 square 被嵌套调用时，可以看到第一次输入 2，返回 4；第二次输入 4，返回 16。调用链很清楚。

Vlime 需要额外启用 trace 模块

Vlime 的函数追踪需要加载 SWANK-TRACE-DIALOG 模块。配置完成后，可以打开 trace dialog，再手动刷新和获取结果。

功能能用，但步骤较多。对初学者来说，Slimv 的方式更直接。

顶层表达式求值是 Lisp 工作流的常用动作

Lisp 代码常常是嵌套表达式。光求值光标下的小表达式不够，还需要一键求值包住当前光标的顶层表达式。

Slimv 用 ,d 求值顶层表达式，Vlime 用 \st。这个功能适合测试一个完整函数定义、一个宏调用或一个较大的表达式块。

它的价值很简单：光标在哪里不重要，编辑器能识别当前所在的完整表达式范围，然后把它送给运行时。

补全、参数提示和符号说明降低记忆负担

参数列表即时显示

输入函数名后继续输入空格或回车，插件会显示函数参数列表。Slimv 通常在底部状态栏或消息区显示，Vlime 会打开分屏显示。

参数提示对 Common Lisp 很有用。标准库函数多，参数形式也不总是好记，有即时提示会减少查文档的频率。

omni-completion 支持模糊补全

输入部分函数名后按 Tab，可以触发补全列表。即使用 wl 这样的缩写，也可能匹配 write-line。

这类模糊补全让写 Lisp 更快，也更适合探索标准库。用户不需要完整记住函数名，只要记得一部分线索。

describe symbol 查看文档

Slimv 可以用快捷键查看光标下符号的说明，Vlime 也提供类似功能，但展示方式不同。Slimv 更偏底部消息区，Vlime 更偏分屏窗口。

这又一次体现二者的风格差异：Slimv 尽量把信息放在现有工作区里，Vlime 更倾向于为信息打开单独窗口。

宏展开让 Lisp 的代码转换过程可见

宏是 Lisp 的强能力之一，但宏也容易让代码行为变得不直观。展开宏就是把看似高级的表达式还原成它生成的低层表达式。

一次宏展开可以看到第一层转换。递归宏展开可以继续向下，直到表达式不再包含宏调用。

Slimv 把展开结果放到 REPL，Vlime 放到新分屏。两者都能完成核心任务，但 Slimv 的信息流更集中。

交叉引用用于理解函数调用关系

交叉引用可以找出谁调用了某个函数。比如 square 被 square-of-sum 和 sum-of-squares 调用，xref 命令可以列出这些调用点。

Slimv 会把结果显示在 REPL 中，但不能直接跳到列出的函数位置。Vlime 会生成 xref buffer，光标移动到结果上按回车，可以直接跳转到对应源码位置。

这是 Vlime 的一个明显优势。对于阅读和维护较大 Lisp 项目，能从引用结果直接跳转很有价值。

Common Lisp 之外的方言支持差异明显

Slimv 支持 Common Lisp、Scheme 和 Clojure

Slimv 不只支持 Common Lisp，也支持 MIT/GNU Scheme 和 Clojure。虽然 Scheme 和 Clojure 的配置有一些限制，比如 MIT/GNU Scheme 在 Linux 下版本要求比较明显，Clojure 的 jar 路径也可能需要处理，但至少有可用路径。

这让 Slimv 更适合想在 Vim 中同时写多种 Lisp 方言的人。

Vlime 只支持 Common Lisp

Vlime 聚焦 Common Lisp，不支持 Scheme 和 Clojure。对只写 Common Lisp 的用户来说问题不大，但如果要跨方言使用，Slimv 更合适。

不同 Common Lisp 实现的兼容性有差别

SBCL 是两者最稳妥的选择。Slimv 和 Vlime 对 SBCL 的支持都比较成熟。

CLISP 和 ECL 也能使用，但会遇到一些额外问题。Slimv 对这些实现的自动检测和启动支持更成熟。Vlime 使用 CLISP 时需要额外写 Vimscript 告诉它如何启动服务，还可能遇到 SOCKET-STATUS 相关错误，需要用 -repl 绕过。

这说明 Lisp 插件的实际体验不只取决于插件本身，也取决于 Common Lisp 实现、Swank、Quicklisp、Vim 配置和系统环境之间的配合。

Slimv 与 Vlime 的核心取舍

安装与依赖

Slimv 的安装路径更顺，目录结构符合 Vim package 习惯，内置 Swank 和 Paredit。但它要求 Vim 支持 Python，并且自动启动 Swank 时常依赖 tmux、GNU Screen 或桌面环境。

Vlime 不要求 Python 接口，也能自行启动服务。但它需要 Quicklisp，目录结构也需要手动处理 runtimepath。

REPL 体验

Slimv 的 REPL 可直接交互，更接近 Lisp 程序员熟悉的工作方式。

Vlime 的 REPL 不可直接输入，需要通过源码缓冲区和 interaction mode 间接完成求值。

信息展示

Slimv 更倾向于把结果放在 REPL、状态栏或消息区。窗口数量少，操作流比较集中。

Vlime 更倾向于通过分屏展示结果，比如参数提示、宏展开、交叉引用、trace 信息。信息分区更明确，但窗口管理成本更高。

功能覆盖

Slimv 覆盖范围更广，支持 Common Lisp、Scheme 和 Clojure，也自带 Paredit和彩虹括号支持。

Vlime 在 Common Lisp 内部有一些不错的功能，比如交叉引用跳转体验更好，但整体覆盖范围较窄。

更推荐 Slimv 的理由

Slimv 的优势集中在几个地方：历史更久、安装更自然、默认键位更顺手、REPL 可以直接交互、内置 Paredit、支持更多 Lisp 方言。

对初学者或日常使用者来说，这些都很实用。工具链越少折腾，越容易把注意力放回 Lisp 本身。尤其是交互式 REPL 和结构化编辑，这两点会直接影响每天写代码的手感。

Vlime 依然值得尝试。它不需要 Vim Python 接口，自动启动服务更独立，xref buffer 的跳转能力也不错。但如果只选一个作为起点，Slimv 的综合体验更稳。
