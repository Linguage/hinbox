<h2>摘要</h2>
<p>常驻智能体要在用户离开后继续工作，依靠的不只是更强的模型，还需要能够保存状态、恢复执行、响应事件并控制成本的完整系统。Lee Robinson 以 Grok Bot 的开发实践为例，介绍如何把“模型循环调用工具”扩展为可长期协作的数字同事：将智能体服务与云端电脑分离，用持久化工作流应对故障，通过子智能体和文件减轻主对话负担，并用提示词缓存、上下文压缩与分层记忆维持长时间运行。讲座最后讨论产品迭代与模型训练的双重循环，以及长期评测、安全、通知时机和推理效率等尚待解决的问题。</p>
<h2>内容概述</h2>
<ul>
<li><strong>产品与交互</strong>：从复制代码、终端智能体和并行编程助手，走向能够主动工作、接受中途引导并适时保持安静的常驻智能体。</li>
<li><strong>系统与执行</strong>：拆分客户端、服务端和云端电脑，结合事件唤醒、消息优先级、Firecracker 虚拟机与 Temporal 持久化工作流，保存任务状态并支持恢复。</li>
<li><strong>工具与上下文</strong>：按需发现工具，优先选择可靠且成本较低的操作路径；通过子智能体、文件、提示词缓存和上下文压缩，管理有限的上下文窗口。</li>
<li><strong>记忆、安全与演进</strong>：分层保存用户事实、历史日志和临时信息，防范不可信输入与提示词注入，并通过评测反馈持续改进运行框架和模型。</li>
</ul>
<h2>讲座全文</h2>
<h3>从终端里的智能体，到能够长期工作的常驻智能体</h3>
<p><strong>Lee Robinson：</strong></p>
<p>刚才已经介绍过了，我是 Lee。今天我们来聊聊一种新类别的智能体：它们始终待命、主动行动，而且能够持续工作。我会介绍它们是如何运作的，也会带大家了解构建这类系统所需的一些基础组件。</p>
<p>先说明一下，今天要讲的有些东西仍在开发中，是我们目前在 SpaceX 正在做的工作。第一周，你们已经搭建过一个非常简单的运行框架（harness），借此理解最核心的想法：有一个模型，它能够在循环中调用工具。这其实非常强大，为模型解锁了许多新能力。不过，这种方式也有一些缺点。</p>
<p>一个很明显的问题是，你把笔记本电脑合上，进程就停了，不再继续运行。</p>
<p>所以我想讲讲，如何把这个简单、却能充分发挥模型能力的思路，进一步扩展成一种新的智能体，也就是常驻智能体。它不只是运行在你的终端里，而是可以运行在服务器上、运行在云端。你可以关上电脑；它能够重新启动，也能够在崩溃之后恢复。这种智能体有自己的电脑，不是只依赖你的笔记本，而是在云端拥有一台 Linux 机器，有自己的桌面、文件、浏览器，以及其他东西，甚至可能还有一些 3D 应用。</p>
<p>它可以把文件保存在这台机器上，随着时间推移，更加了解你的工作进展，并积累关于你如何与它合作的记忆。终端里的运行框架通常会回应你发出的每一条消息，但这种常驻智能体更像一位同事，不会总是立刻给你发消息。它知道什么时候应该保持安静。有时，它只是想先在后台做一会儿工作，等有了重要进展再来找你。而且，触发它的方式不只是你打字，也不只是你在终端里给它一条提示。</p>
<p>也许是一条 Slack 消息、一封邮件，或者其他某种事件，唤醒这个智能体，让它去工作。我们对这类常驻智能体的理想期待，是它们能够持续工作很长时间，不只是几个小时、几天，甚至可能是几周、几个月。要做到这一点，需要一种稍有不同的架构，后面我们就会讲到。</p>
<p>接下来，我们会比较深入地介绍这套架构是怎么搭建的、运行框架是怎么构建的，以及我们是如何走到今天这一步、未来又准备走向哪里。我们还会谈到一些具体的工程设计，看看如何让系统具有主动性、能够持续工作，并且很好地遵循指令。最后当然也会留出提问时间，大家可以问今天的内容，也可以问今天没有涉及的其他问题。首先，我们来看看是怎么走到这一步的。</p>
<h3>开发者与 AI 协作的四个阶段</h3>
<p>到目前为止，开发者使用 AI，大致经历了四个阶段。我认为第一个阶段，就是从 ChatGPT 里复制代码，再粘贴到自己喜欢的编辑器里。这件事现在感觉像是几十年前发生的，但实际上也不过是几年前。</p>
<p>随后，随着模型能力提升，它们开始能够配合我们上一讲谈到的那种简化运行框架，编辑文件、运行 shell 命令，并通过一种非常简单的终端界面与你协作。这种方式很快流行起来，因为模型突然有了一项新能力：它能更主动地替你完成工作，也更有效率了。</p>
<p>第三个阶段，是给这些起初比较简单的编程智能体配上专门的应用。这时，人们开始并行运行许多个智能体；它们也许运行在云端，而不只是在自己的电脑上。</p>
<p>但即便到了这个阶段，你仍然是瓶颈，因为你要审查它们运行的每一条命令。你想确保每条 shell 命令都准确无误，因此会密切关注它们，参与每一个环节。现在，随着模型、运行框架和产品不断改进，我们进入了一个新的阶段：常驻智能体开始出现，它们可以在后台默默运行，拥有自己的电脑和记忆，在工作中学习新技能。即使你去睡觉，或者转去做其他事情，它们也会继续工作。</p>
<p>一个很好的例子是，我们已经逐渐不再需要每天都给智能体下达提示。</p>
<p>当然，有时我们仍然会这么做，但现在你可以把智能体设置成在后台自行运行。过去的流程可能是：给智能体一个提示，等它完成；再给一个提示，再等待。如果它请求运行一条 shell 命令，你还得批准或拒绝。现在，你可以随时引导智能体，而不只是把一条条命令排进队列。比如，你可以说：“去看一下这个讨论串。”紧接着又补一句：“对了，还是等周四再做这件事吧。”</p>
<p>对于早几代模型，如果你立刻打断它，又给出另一条指令，它可能就会困惑。但现在，它们能够理解这种情况，就像你和朋友说话时随口补充几句，对方也能分辨出这两件事是相关的一样。如今的模型和运行框架已经能够处理这样的互动。如果你说：“去发这封邮件，去发这条 Slack 消息。”系统还会设置额外的安全检查。很多公司把它叫作自动审查，也就是 autoreview。本质上，是让一个独立的 AI 模型检查所有即将执行的命令。</p>
<p>有意思的是，这其实比让人盯着几百条 shell 命令、逐一批准，最后疲惫不堪，要更安全。我们已经走到了这样一个阶段：如果做一次盲测，比较 AI 模型检查命令的结果与人类检查命令的结果，大多数时候，模型实际上做得更好。</p>
<p>这看起来有点矛盾，但随着模型越来越强，交互界面反而变得简单了很多。我们把这种常驻智能体称为 bot。不过，你们也会注意到，现在有不少这类新产品陆续出现，而且受到了很多关注和使用。</p>
<p>我认为，主要原因在于我们都知道怎么发消息，大家对使用手机也都很熟悉。我们把与 AI 协作的方式提炼得像是在给朋友发消息，但它真的可以替你完成工作。它不再只是以问答形式回答问题，而是会去执行耗时更长的任务，就像你把工作交给同事一样。有几项具体的模型能力变化，使这一切成为可能。</p>
<h3>让常驻智能体成为可能的模型能力</h3>
<p>我会介绍其中六项，当然，实际的变化远不止这些。第一，过去一两年里，模型在长时间遵循指令方面确实进步很大，更不容易陷入混乱或犯错。如今，只要配合适当的上下文压缩与精简，模型就已经能够比较可靠地运行几个小时，甚至几天。关于压缩，我们稍后会讲。第二，模型现在可以把工作交给助手子智能体，也就是 subagents。</p>
<p>助手子智能体之所以有用，是因为主模型会为当前正在执行的过程维护一份工作记忆，而这份记忆迟早会被填满。因此，如果它可以把工作交给拥有全新工作记忆的助手子智能体，就会很有帮助。这样一来，实际上就相当于获得了近乎无限的上下文：助手子智能体可以去执行一些消耗大量 token 或需要调用许多工具的工作，然后回来向主智能体汇报进展。后面我会用几张图来说明。此外，模型现在的进步也不只是更擅长调用工具。</p>
<p>要知道，就在几年前，它们基本上还不太会调用工具，而且经常产生幻觉。有意思的是，现在你已经不太听到大家谈论幻觉了，因为这个问题大体上已经得到了解决。</p>
<p>模型不仅会调用工具，你还可以给它们非常强大的工具，就像给一位新加入团队的同事配置工作条件一样。显然，这包括运行 shell 命令、操作文件，但你也可以给它一整台电脑，一台完整的 Linux 电脑，让它制作演示视频等。它们能像人一样在屏幕上点击操作，而且越来越擅长这么做。这就是所谓的电脑操作能力，也就是 computer use。它基本上意味着，即使某个 SaaS 产品或网站没有提供 API，也没有提供 MCP 服务器，这些模型和 bot 也能够通过操作电脑，在无人值守的情况下自主使用它们。你还可以把所有信息保存在文件里，因为这样一来，模型就很容易找回和搜索这些信息，后面我们也会谈到。最后，你可以直接向 bot 演示某项工作该怎么做，它便能够把这些做法转化成技能、记忆、例行任务，或者其他以后可以复用的内容。</p>
<h3>用文件保存用户画像、工作记录与技能</h3>
<p>以文件为例，下面是一个简化的示意。你可以回想或想象一下，当你与 bot 协作时，它在底层的运作方式，可能大致是这样的。</p>
<p>首先，系统会逐渐建立一份用户画像，或者说形成对用户的理解，而这份信息会被放进每一次提示中。比如，你也许喜欢发消息时全用小写字母，那么每条消息都应该遵循这一偏好。同时，随着你不断与这些 bot 合作，系统也会积累类似工作日志的东西。就像你和一位同事合作，对方每天会记下自己做过的工作。这些内容都会写入文件，模型之后可以自行决定是否搜索或使用它们。如果你问：“我上周都做了什么？”它就可以去查。</p>
<p>模型非常擅长使用 Linux 命令、运行 shell 命令，通过 grep 等工具搜索和查看这些文件。技能也是类似的道理：你把自己完成某项具体任务的知识编码进一个 Markdown 文件，包括完成任务的具体流程，以及你认为决定任务成败的那些要点。而且，这并不只限于你自己的技能。</p>
<p>现在已经形成了一个完整的生态，许多公司和开发者都在编写这样的技能，介绍如何写出一封好邮件、如何构建一个出色的 API，以及许多其他事情。比如，Grok Bot 就有一套完整的插件系统。基本上，无论你想使用什么工具，都可以安装相应的插件；插件会用到技能或服务器。此外还有例行任务。如果你熟悉 cron 定时任务，就会明白，它本质上是按照某种时间表运行一条提示，这也非常实用。所以，说到底，一切都围绕电脑展开。下面进入第三部分。</p>
<h3>“常驻”不意味着始终占用一台运行中的电脑</h3>
<p>接下来，我们再深入一点，看看这个常驻智能体的内部是怎样的，也就是走到幕后。智能体“常驻”，到底意味着什么？</p>
<p>这张图可以从左往右看。起初，服务器处于休眠状态，智能体可以使用的那台电脑也处于休眠状态。无论是你发来一条消息，还是某种触发机制决定启动智能体，系统都会加载并启动这个智能体所需的全部状态。关于触发机制，我们马上会讲。智能体运行在服务器上。如果它判断自己需要使用电脑，比如要打开电脑上的浏览器，或者在电脑界面里进行点击操作，它也可以把电脑启动起来。</p>
<p>等到使用结束，它也能够让这些资源重新进入休眠状态。</p>
<p>为什么这一点很重要？如果要为每个人一直保持一台电脑运转，成本会很高，而且世界上也没有足够多的电脑可供这样使用，同时也会消耗大量服务器资源。因此，系统可以把状态持久化到数据库里，包括对话记录、记忆、例行任务等等。那么，智能体又是如何被唤醒的呢？</p>
<h3>事件唤醒、消息路由与合适的通知时机</h3>
<p>显然，你可以直接给它一条提示。但我觉得越来越有意思的是，还可以让其他东西在后台运行，由它们决定什么时候该去联系你的 bot。可能是有人在 Slack 上 @ 你，而你的 bot 本身就可以待在 Slack 里；也可能是一通电话，或者一场你让 bot 参加的会议。</p>
<p>在 SpaceX，我们越来越常见到这种情况：员工没法参加某场会议，就让 bot 代为参会，只负责记笔记，再回来向自己汇报。这还挺有趣的。另外，也可能是某项例行任务，或者某项需要几个小时乃至几天才能完成的后台工作，等做完之后再回来给你一份总结。这些情况都会发生。随后，系统里会有一个路由器，对这些输入去重，并判断如何把它们放进对话。之后，系统还会根据一些启发式规则判断：“这件事需要打扰用户吗？”毕竟，并不是所有事情都很重要。</p>
<p>就像你有一位同事正在做某项工作，如果他每取得一点进展都来打扰你，说：“你看，我这件事又有进展了。”那会很烦人。你真正需要的状态更新，可能只是每天一次，具体还得看任务是什么。</p>
<h3>云端电脑、虚拟机快照与共享基础设施</h3>
<p>刚才提到，智能体有自己的电脑，也就是一台 Linux 机器。这里运行的是 Firecracker 虚拟机。它非常有用，因为你可以很容易地为机器状态创建快照，再把它关闭，然后重新启动。当然，这台机器上有文件；你也可以连接进去，实时查看它的界面，如果愿意，还能亲自操作。这台机器也可以运行命令，所以如果你需要执行一些 shell 命令，它就很方便。你可能不希望这些命令在自己的笔记本电脑上运行。</p>
<p>你会希望它们运行在另一个受到保护、权限严格限制的环境里。另一个有意思的地方是，它当然有 Chrome，可以使用浏览器，但你还可以为它配置类似虚拟桌面的环境。</p>
<p>比如，你运行了五个、十个 bot，每个都需要自己的浏览器，那就可以让它们分别使用不同的屏幕。这里的所有资源，同样都是这些 bot 之间共享的基础设施，它们可以按需调用这些电脑。</p>
<h3>服务器上的智能体循环</h3>
<p>我们已经讲过唤醒智能体的触发机制，也就是图左侧的部分，包括不同应用、Slack 消息或邮件。中间这一部分是服务器，右边则是刚才讲过的电脑，你可以在上面处理文件、运行命令，以及做其他事情。下面，我们再多讲一点服务器。</p>
<p>刚才已经提到，命令进入系统后，会被放进这个队列，随后调用紫色方框所代表的智能体循环。这就是我们上周讲过的内容：一个模型在循环中调用工具。而当你把它关闭时，就可以把状态保存到数据库或存储系统中。</p>
<p>我觉得，观察这张图时，很有意思的一点是：你会发现核心其实只是这么一个小组件，但可以在它之上构建出这么多层抽象。只要为它提供这些实用的工具，再把它连接到各种不同的服务，就能做出一个非常强大的产品。</p>
<h3>为什么把智能体放在服务端运行</h3>
<p>智能体之所以在服务端运行，是因为我们采用了计算领域一种很常见的做法：薄客户端、厚服务端。多年来，计算架构一直在这两者之间来回摆动。这样做有几个很实际的理由。比如，你需要更新智能体的代码，如果每次都得向应用商店提交一次更新才能把代码发布出去，那就很麻烦；相比之下，你可以很快地在服务端连续部署更新。另外，有时还需要做比较繁重的计算，比如转录、图像生成之类的工作。</p>
<p>这些工作放在服务器上，很可能比在设备本地执行更快，当然也要看具体是什么设备。</p>
<p>而且，我们已经有非常成熟的服务器扩缩容方法，尤其适合应对流量和增长幅度不断变化的情况。不过，这里最关键的一点是：如果把智能体循环放在那台虚拟机里，就无法在不影响智能体服务器的情况下单独关闭虚拟机。所以，我们希望把所有状态都保存在服务端。</p>
<p>这样一来，你随时都可以重建那台虚拟机。比如，假设你需要为虚拟机安装一个修复 Linux 零日漏洞的关键更新。</p>
<p>如果能在重建虚拟机时，既不把整个智能体循环一起清掉，也不让应用停机，那就很好了。接下来讲一下用户点击发送后会发生什么。这部分可能有点深入细节，我就简单带过。如果你想进一步了解分布式系统，可以去研究强一致性和最终一致性，这些都是很有意思的话题。基本上，当你发送一条消息时，你希望客户端立即识别这次发送，并给出确认。</p>
<p>然后进入这一轮处理：让模型与这些工具在循环中交互，把过程保存到数据库。各个客户端则会向服务端建立订阅。</p>
<p>客户端通过监听这些信号，知道是否发生了变化；一旦收到信号，就去服务器获取最新信息。这里还可以做一些巧妙的去重处理，确保即使发生了重试，消息列表里也不会重复显示同一条消息。因此，从底层基础设施的构建模块来看，有一个需要考虑的区别：工作流和任务队列。</p>
<h3>用持久化工作流保留进度</h3>
<p>两者的主要区别是这样的：假设你让智能体完成一个复杂任务，它沿着第一步、第二步、第三步往前执行，但中间因为某种原因，基础设施出了问题。对于普通任务队列，如果执行崩溃了，重启时就得重新执行第一步、第二步和第三步。这显然可能造成很大的麻烦。所以，你真正需要的是持久化工作流，也就是能够安全重试的工作流。</p>
<p>失败后重试，它可以直接从第三步接着做。在某种程度上，这已经是分布式系统和基础设施领域解决过的问题了。因此，我们使用了一个叫 Temporal 的开源工具；如果感兴趣，可以去了解一下。有了它，我们就不用从零开始重新实现一大堆非常复杂的东西。当然，你仍然需要运行支撑它的基础设施。这就是需要组合起来的一部分组件。接下来，假设有一条新消息进来了。</p>
<p>消息的优先级会有所不同：我直接给自己的智能体、自己的机器人发消息，和群聊、Slack 讨论串或后台例行任务里的消息，优先级是不一样的。比如我说：“等等，还是把这个活动的日期改一下。”我们会希望智能体循环停下来，让我的消息优先于其他正在发生的事情，这也很合理。其他人的消息则排到队列后面。</p>
<p>如果智能体在很短的时间内连续收到三四条消息，它可以把这些消息合并起来，作为一轮处理。你可以自行决定采用什么启发式规则。之后，它再按顺序，一次处理一轮。</p>
<h3>运行框架：一个通信工具，多种客户端体验</h3>
<p>好，接下来讲运行框架本身。我们会在上周讨论过的基本运行框架之上，加入一些新工具和新概念。</p>
<p>Grok Bot 的运行框架有一个很大的不同点，市面上一些类似工具可能也是这样：在我们的薄客户端、厚服务端架构里，客户端与服务端之间只有一个通信工具，叫作 send user。这样做的好处是，架构非常简单。从某种意义上说，客户端只是在给服务器发消息，而大量更重的工具都放在服务端。这些工具有很多种。</p>
<p>比如运行 shell 命令、读取文件，也包括调用云端智能体、录制屏幕或演示操作。我觉得这种方式的效果相当不错，因为无论你在哪里启动一个新客户端，无论它是移动应用、服务器、桌面应用、电子邮件还是 Slack，都只需要用这一个工具与服务端双向通信。虽然客户端只有这一个通信工具，但收到工具调用时，它可以自行决定，怎样以最适合用户的丰富、可交互形式来呈现内容。</p>
<p>比如，服务端传回的信息表明用户正在尝试登录某个服务，客户端就可以显示专门的登录表单，并与 1Password 这样的工具连接。它也可以调用 Stripe Link、X Money 或其他服务，让用户支付所需的服务费用。如果你尝试进行某种无法撤回的操作，比如发送邮件或 Slack 消息，它可能会先请你编辑并批准草稿，再把消息发出去。</p>
<p>有时候，如果没有必要发送消息，留一个表情回应就够了。接下来回到刚才说的动态工具发现。每个模型都有一个上下文窗口，你可以把它理解成模型的工作记忆，它有以 token 数量计量的容量上限。如果把所有可能用到的工具都塞进上下文窗口，就不会剩下多少空间了。</p>
<h3>动态发现工具，按需获取上下文</h3>
<p>工具的定义包括工具名称、参数结构以及各种细节。如果你开始安装 Google Drive 连接器、Gmail 连接器、YouTube 连接器，以及其他通过 MCP 服务器提供工具的服务，就会逐渐变成图上方展示的样子：很多格子已经被占满了。问题是，这样一来，模型实际处理对话内容时能用的空间就变少了。</p>
<p>所以，很多流行的运行框架现在都会使用一种上下文工程，或者说运行框架方面的技巧，叫作动态上下文。有些人似乎把它叫作“工具搜索工具”，这个名字挺有意思。它的基本做法是：每次发送给模型的消息里，只放工具名称。然后由模型决定：“好，我现在确实想用这个工具，可以去文件里读取它的相关信息。”</p>
<p>这些东西追根究底，几乎都是文件和文件系统。这样做能减少上下文占用，进而降低费用、节省用量，对各方都有好处。总体来说，这里的原则是：先尝试成本最低或最可靠的方案，然后再沿着这一级级往上走。</p>
<p>最简单的方案，就是利用智能体或机器人根据对话历史已经知道的信息。如果所需信息不在当前上下文里，也许有一个插件、MCP 服务器或某种 API 可以去获取，比如通过 Plaid 读取你的银行信息。如果这条路行不通，也许就得进行网络搜索，比如查一查小熊队昨晚比赛的比分。</p>
<p>如果这些手段还不够，它可能需要到那台电脑上打开浏览器，再进行搜索。最后，也许它需要真正操作整个桌面，在那台 Linux 电脑上运行脚本、执行命令或构建东西。</p>
<p>只有这些方法全都失败了，才去打扰用户，请他们提供输入或批准某件事。这样会让它更像一个与你共事的同事：同事不会每遇到一件事就来打扰你。理想情况下，他们会先尝试其中的很多办法。</p>
<h3>浏览器与桌面：从结构化信息到像素操作</h3>
<p>在智能体可以使用的那台 Linux 电脑上，大致有三种获取信息的方式。当然，它可以直接截取屏幕画面，但也有更高效的办法。它可以查看页面的 HTML，也可以查看无障碍树。无障碍树能大幅减少 token 用量，帮助智能体找到希望浏览器点击的按钮、链接或其他元素。</p>
<p>当然，如果这些方法都行不通，还可以直接按像素坐标点击。比如，有些网站会弹出模态窗口或对话框，需要你点击操作，所以模型、智能体也必须具备这种能力。再往后，也就是这条阶梯上最无奈的一步，才是回头找用户：“这里需要双重身份验证的验证码”，或者“这里有一个 CAPTCHA 验证码”，诸如此类。</p>
<h3>主智能体与助手子智能体如何协作</h3>
<p>把这些组件组合起来，基本思路是：有一个主智能体，它有点像一个协调者。你要尽可能让主智能体的对话上下文保持精简，因为它现在可以调用各种不同的助手子智能体。</p>
<p>所谓助手，就是子智能体。这种安排很有用：如果把任务交给一个助手子智能体，让它运行大量 shell 命令，或者进行许多开销很大的工具调用，那么，无论这些工作最终是为了回答问题还是完成任务，其中的过程都不会挤占主智能体的对话上下文。返回的只有结果。这样做出来的产品，才会让人感觉它拥有无限上下文。当然，真正的无限上下文并不存在。</p>
<p>每个模型都有上下文上限。但通过这些技巧和变通方法，尤其是再通过训练让模型更擅长这样工作，就可以让你不觉得自己总在碰到上下文窗口的边界，也不会随着对话越来越长而感觉模型质量下降。所以，我们有各种不同的助手子智能体，各有所长，而且每一个都对应一个独立的持久化工作流。</p>
<p>回到前面任务队列与工作流的区别：这意味着，如果执行失败，比如视频助手子智能体崩溃了，或者某个进程占用了太多内存，它可以重新启动并继续工作，而不会丢失已经取得的进度。主智能体则像一个管理着待办清单的同事。你可以查看进展、给它发消息，也可以停止助手子智能体。</p>
<p>所以，这里面很多设计，都借鉴了让一个工程师团队共同解决复杂问题时，我们理想中扩展团队协作的方式。接下来分享几个团队在实现过程中发现的小细节。后面我们还会进一步讲提示词缓存，不过先说一点：理想情况下，不要在轮次进行过程中添加或移除工具。</p>
<h3>工具设计的几个工程细节</h3>
<p>就像我刚才展示那些格子的幻灯片时说的，如果工具描述或参数结构特别长，就会占用大量上下文窗口空间，无论从费用还是用量来看都不好。理想情况下，要把它们尽量缩短。在工程层面，有很多优化可以减少这部分体积。另一个有意思的点是，你可能听过有人说：“我们可以做一个运行框架，只给它一个工具，而这个工具就是运行 shell 命令。”</p>
<p>这当然成立，很多事情都可以用这种方式实现。但如果你发现，模型有 90% 的时间都在为某一件事执行 shell 命令，那么，为其中一些操作做一个专用工具，其实可能更高效。对实际检查产品运行情况的人来说，这种方式也更容易看懂。最后一点也挺有意思。显然，给人看的错误信息，最好写得清楚、具体，例如：“这一步失败了，请点击这个链接”，或者“接下来你需要这样做”。</p>
<p>事实证明，这对智能体也非常有帮助。所以，为智能体设计好的错误信息，也有开发者体验，也就是 DX，方面的考量。</p>
<h3>长期运行中的安全边界</h3>
<p>当你把工作交给机器人，让它长时间执行时，非常重要的一点是：你要相信它能够安全地处理你的信息，也能以安全的方式运行。即使它使用自己独立的机器，不会弄乱你的电脑，你仍然会希望每条 shell 命令在执行之前，都先由一个模型审核一遍，也就是自动审核。还有一种很重要的情况：它收到一些不可信的输入，比如你收件箱里的一封邮件，可能是钓鱼邮件，或者某个 webhook 发来的内容。</p>
<p>你肯定不希望把这些内容发给模型之后，就把它们当作用户指令来执行。在防范提示词注入、确保这些边界得到妥善保护方面，整个行业还有很多工作要做。对于发送邮件这类无法撤回的操作，确实应该先征求用户同意。另外，也可以在产品里设计一些工作流程，让密码等信息不进入模型的对话内容。</p>
<h3>提示词缓存与上下文压缩</h3>
<p>好，上下文工程也被称为运行框架工程。我觉得这两者差不多是一回事。</p>
<p>这些概念一直在演变，但归根结底，我们要讨论的是：可以用哪些技巧，尽量减少这些运行框架所使用的上下文。这有助于提高效率、降低成本，也有其他好处。前面提到了提示词缓存，这里有个很好的例子，能说明它为什么如此重要。想想你使用编程智能体或者其他智能体的过程：理想情况下，用到的大多数 token 其实都应该是已缓存的 token，因为你先把一段对话发送过去，然后再作一点改动。</p>
<p>你再增加一条消息，随后基本上又把整段对话重新发送了一遍。如果去看模型定价，就会发现，已缓存 token 的价格通常有很大折扣，所以你希望尽可能长时间地保持缓存命中。一个办法就是，在不同调用之间，尽量让工具定义、系统提示词等信息保持不变，避免缓存失效，导致每一次都得按未缓存 token 的价格付费。</p>
<p>如果把这些固定内容放在最前面，那么到最后面时，只有新收到的那条消息发生了变化。你就只需要为这一小部分新增内容支付未缓存 token 的费用。</p>
<p>这里面也有一整套值得钻研的技巧和方法。</p>
<p>理想情况下，主智能体就是那个会与你进行极其漫长对话的智能体。它会反复进行上下文压缩，也就是对上下文作总结，而有时候你甚至都不会察觉。后面我们会展示一个例子。因此，你确实要尽量让它的上下文保持精简。一个办法是：每当有特别长的输出时，不要直接把它塞进上下文，而是放到文件里。智能体非常擅长读取文件。</p>
<p>这套做法其实效果很好，比如读取一个技能文件，或者读取一段记忆。</p>
<h3>提高提示词缓存命中率</h3>
<p>如果要给模型看一张截图，或者让它处理其他开销很大的工作，就再次把任务交给一个助手子智能体。这样，工作就会转到子智能体那里，不会占用主智能体的上下文。另外，理想情况下，在对话进行的过程中，你应该不断维护和修剪上下文窗口，把不必要的内容清理出去。这既是为了控制成本，也是为了提高信息回忆的效果，确保模型表现良好。</p>
<p>所以，如果出现缓存未命中，其实就有点像系统里出了一个 bug。回头看今年一月，当时 OpenClaw 开始大受欢迎，很多人通过模型提供商的订阅套餐来使用它。这是一种非常新的使用模式，模型提供商此前并没有真正见过，而运行框架也还没有针对这种工作流做好优化，因此出现了大量缓存未命中。</p>
<p>对于这种一直运行的智能体来说，这显然是个问题。所以，必须做很多修复，让系统能够可靠地尽可能保留提示词缓存。这里有个有意思的小技巧：尽量让提示词中的所有内容始终按固定顺序排列。这样，即使部署了一项新改动，想测试系统提示词的新写法，或者增加一个新工具，也可以对各个部分分别计算哈希值，始终维持固定的顺序。</p>
<p>比如，你在做 A/B 测试，想在提示词里插入一段新内容。你肯定不希望这影响到其他所有人的提示词顺序，否则就把缓存弄失效了，这会带来麻烦。另一个有趣的做法是，当你打开聊天界面、开始打字时，服务器就可以提前准备提示词，给缓存预热。这有点像浏览网站时，鼠标悬停在某个链接上，网站就开始预取下一页。</p>
<p>类似这样的小型工程优化非常多，它们的效果会不断累积，影响模型在 token 使用方面能走多远，也影响模型在持续使用很长时间后还能有多聪明。关键在于，工作时间一旦拉长，就必须非常擅长上下文压缩或摘要。假设模型有一个 20 万 token 的上下文窗口，对话一直继续下去，迟早会到必须总结的时候，而所有压缩都会丢失信息。</p>
<h3>在缓存失效前压缩上下文</h3>
<p>所以，你必须找到最好的压缩算法，避免丢失重要细节。我相信，光这个问题就足以支撑很多完整的博士研究，因为它确实非常难。举个例子，你一直在和自己的机器人来回交流，对话已经超过 10 万 token，然后你去做别的事情了。模型提供商会有一段缓存保留时间，在这段时间里缓存仍然是热的，可能是 10 分钟，也可能是 60 分钟。</p>
<p>我们用了一个我觉得很有帮助的技巧：趁缓存还热着，就应该考虑马上进行上下文压缩。因为这时有一段很长的对话，利用仍然有效的缓存来压缩，成本会低很多。所以，直接把压缩做完。等用户过了 30 分钟或更久回来时，就可以从这份摘要接着聊，而在摘要的基础上继续添加消息，成本会低得多。因此，在如何把摘要算法做得足够好这件事上，还有很多工作要做。</p>
<h3>分层组织智能体的记忆</h3>
<p>谈到上下文压缩，以及应该把哪些信息放进智能体的记忆时，我倾向于把它分成几个层次。第一层是关于用户的一些非常重要的事实，每次都需要包含在上下文里。回到前面那个例子：用户总是希望文字使用小写字母。这条信息大概就需要出现在每一条消息对应的上下文里，否则，如果某一条回复突然出现了大写字母，就会很奇怪。</p>
<p>如果你想完全走 Sam Altman 那种全小写风格，就更是如此。此外，你可能还有一些希望放进上下文的提示词或事实。你可以用很多不同的方法来设计算法，判断哪些事实最值得保留。理想情况下，应该对这些事实进行某种垃圾回收。仔细想想，我们的大脑也有点像这样：这条事实现在值得记住，它和今天这段对话有关。比如，你现在大概不会在想着一场足球比赛。</p>
<p>大脑很擅长把当前重要的信息保持在眼前的语境中，同时把其他信息留待以后回忆。我们也试着模拟其中一些机制。运行框架里当然会有那些核心事实，还会有带日期的日志，基本上就是过去的对话记录，以及一些临时便笺。这些便笺记的是你眼下正在处理的小事情，本来就是临时性的，之后会被清掉，但在接下来的半小时或一小时里可能还有用。其他所有信息，都可以通过文件找回来。</p>
<p>这就是文件，以及模型擅长运行命令这两件事的妙处：它们总能自己去查，而且实际上很擅长查找。那么，接下来会往哪里发展？这里存在一个通过训练模型、让它更好地服务于产品的飞轮。先简单回顾一下大语言模型的几个训练阶段。第一步是预训练，模型从大量互联网文本或其他私有数据中，学到对世界的一般性理解。</p>
<h3>产品改进与模型训练的双重循环</h3>
<p>接下来是监督微调，教模型按照某种方式行事，比如成为一个聊天助手，或者一个智能体。最后是强化学习，有点像教模型玩游戏，并让它越来越擅长这些游戏。对于常驻智能体来说，比如在监督微调，也就是 SFT 阶段，让模型看到运行框架的使用示例，学会在运行框架中工作，就很有帮助。这样，它就能理解有哪些工具可以使用。</p>
<p>在强化学习阶段，提高模型遵循指令的能力也很有帮助。比如，面对数百种技能时，怎样判断应该调用哪一种。</p>
<p>又比如，让它操作浏览器、四处点击时，怎样点到正确的位置。重要的不只是训练本身，还包括如何部署模型提供服务，以及如何进行推理。你正在交谈的主智能体，理想情况下应该延迟很低，马上回应，快速给出回复。你可以调整运行框架和推理方式来实现这一点。但如果把任务交给一个助手子智能体，让它工作很长很长时间，那么花 10 分钟还是 12 分钟，到那个时候差别就已经不太重要了。</p>
<p>这就给了你优化不同环节的空间。这个飞轮大致是这样运转的：假设智能体做错了一件事，理想情况下，就应该把这个错误转化成某种评测用例。比如，模型误调用了一个本不该调用的工具。接着，你就可以在后端修复运行框架，修复 bug，修改提示词，也可能发现问题出在推理环节。</p>
<p>然后通过评测检查，确认问题确实已经修好，再把改动发布出去。开发这些产品的团队，基本上每天都在做这样的事情。</p>
<p>他们发现 bug、修复 bug，再用评测来衡量效果。这就是一个持续改进的内循环。外面还有一个外循环：每隔几个月、一个月，或者其他一段时间，你会训练新模型。理想情况下，新模型能从这些 bug 和失败案例中学习，在评测中不断进步，更擅长你关心的事情。然后，你就可以把新版本放进产品里，确认它在这些不同方面都变得更好了。</p>
<p>有趣的是，新模型发布时，能力还会出现新的跃升，让你能够以新的方式使用产品。比如，让机器人参与群聊，目前就还没有太多相关训练数据。这是一种正在出现、仍在探索中的用法，把它做好很重要。</p>
<p>如果你看过像Moltbook这样的例子，或者 Hugging Face 那次事件，显然就知道，这类事情也可能出问题。因此，训练模型在多智能体系统中恰当地行事非常重要，比如不同机器人相互对话的情况。理想情况下，作为一家 AI 公司里开发这类运行框架的产品团队，你们会一直同时运行这些内循环和外循环。</p>
<h3>为下一代模型构建产品</h3>
<p>我们在 Cursor 时有一条原则，现在到了 SpaceX 也一样，叫作“删掉产品”。意思是，你必须真正接受一个前提：今天的模型，是它们此后最差的样子。这意味着，六个月之后，你可能就需要把整个用户界面重做一遍。我今天讲的大部分内容，相比六个月前如果来做同样一场演讲时会讲的内容，都已经有很大的更新；如果和一年前相比，那就更不用说了。因为我们已经学到了很多构建运行框架、做上下文工程的新实践方法。</p>
<p>所以，一个好的策略是：尽量面向下一代模型来构建产品。</p>
<p>也就是说，如何只做尽可能少的东西，就足以支撑产品运行，同时提供一个非常简单的界面，让你能和这些模型协作，让它们替你思考和行动。接下来，我想讲讲未来 6 到 12 个月里可能发生的一些事情。最终如何，还要再看，但我觉得这些判断相当有把握。目前，你的智能体或机器人可能会工作几个小时，也可能工作一天，取决于任务有多难。我认为，很有可能在不久之后，它们就能持续工作几周，甚至几个月。</p>
<p>这也带来了一些有意思的问题：我们该怎样训练和评估这样的模型？我认为，模型会越来越擅长回忆过去对话中的信息。围绕算法类型，以及底层数据应该如何表示，研究中已经有很多不同的思路。可能用图，也可能用文件，还可能用其他方式。理想情况下，如果你有这样一位数字同事，就应该像让一名真人同事入职那样，把你拥有的所有工具都交给它。</p>
<p>当然，我觉得组织和企业仍在逐渐接受这个想法，这方面还有不少工作要做。界面也可能变得更加简单。有些人也许会更愿意以语音到语音的方式，直接和自己的机器人或智能体交谈。也许他们会有一个 Jony Ive 设计的设备，希望它真的很酷，然后就可以整天对着它说话。</p>
<p>我认为，模型和产品会变得非常擅长在工作中学习技能，然后把学到的东西写进文件、指令和技能里，把那种原始的智能转化成对你所要求完成的具体任务真正有用的能力。我也认为，人们和公司会越来越擅长把各种定制化流程的运作方式写下来，让智能体能够理解并使用。</p>
<h3>仍然值得研究的难题</h3>
<p>接下来是几个有意思的问题，也许能给你们一些研究或探索的灵感。第一个，还是回到可以持续运行一个月的智能体：如果你需要评估一个运行一个月的智能体，但模型每个月就发布一次新版本，该怎么办？你根本没法完整评估这个模型，确认它的行为足够符合预期。</p>
<p>所以，要么想办法做出更好的评测，要么就不要那么快发布模型。我觉得，这是整个行业在未来六个月里必须解决的问题。记忆方面，我们已经谈过不同的算法。安全方面也有非常多的工作要做：如何构建安全的运行框架，如何让这些智能体周围的基础设施足够安全，避免被恶意攻击者接管。</p>
<p>还有一点，今天没有展开太多，就是用什么启发式规则来决定智能体什么时候保持安静、什么时候来打扰你。我不觉得我们已经把这件事做得很完美。要在主动提供帮助和打扰之间把握分寸。比如，它主动说：“嘿，我看到你昨天没去上课。我有那堂课的录音，也整理了笔记，给你放这儿了。”这可能很有帮助，也可能挺烦人的。怎样找到合适的平衡，还是个问题。</p>
<p>我还认为，有一个相当稳妥的判断：到了明年这个时候，全世界流转的 token 会比现在多得多。这意味着，优化推理、优化模型、优化运行框架，想办法减少不必要的 token 消耗，提高 token 使用效率，也会变得非常重要。这些都是我们需要思考的新构建模块。我记得是在 X 上看到了 OpenRouter 的 Alex 的一条观点。</p>
<p>他的说法很好。当时有人说：“现在每个应用看起来都一样：有侧边栏、有智能体、有聊天输入框。大家都在做同样的东西。”他的回应是：“是啊，这就像你在 2005 年说，大家都在做同样的东西：有服务器、有数据库，还有一个用来更新、删除数据之类的 CRUD 界面。”</p>
<p>现实是，这已经成了新的常态。每一个新产品都需要具备某种智能体能力，要么把它集成进来，要么成为供另一个智能体使用的无界面数据资源。今天我们已经谈到了很多相关产品和能力：持久化工作流、沙箱、云端计算机、记忆、技能、连接其他服务、语音、支付、身份、评测、可观测性。</p>
<p>这里的每一个框，背后都有数十亿美元的风险投资，没准都要以万亿美元计。</p>
<p>每个领域都有二十家初创公司。所有这些领域里，都有非常多值得探索的事情，因为它们就是下一代公司、下一代产品的新基础构件，而且都必须集成起来，成为运行框架的一部分。所以，这里肯定还有很多事情可做。最后讲几个希望大家带走的要点，然后我们就有时间提问了。</p>
<h3>给工程师的三个建议</h3>
<p>显然，你们都是工程师，都在思考如何编写软件。</p>
<p>现在，比以往任何时候都更需要思考更广泛的系统设计，以及你正在处理的代码架构，因为在这些方面做出的决策，影响会不断累积。所以，我仍然主张看代码。我自己依然会看正在写的代码。有些人已经不看代码了，但我还是觉得这很有帮助，尤其是要理解你最终交付的架构。这短短几年里的变化之大，真的很不可思议。第二点，听起来你们上周已经在尝试构建自己的版本，或者了解运行框架是怎样工作的。</p>
<p>我鼓励你们想一想今天讲到的这些做法，试着运用它们，看看能不能给自己构建一个版本。我记得 GitHub 上应该就有一个叫OpenGrokBot的项目，大概是有人 fork 了我们的代码，做出了一个自己的版本。你们应该可以给它搭个图形界面，再配上某处的沙箱、一台虚拟机，以及其他各种组件。</p>
<p>如果你想进一步了解这些组成部分是如何工作的，这会是个有意思的尝试。最后，不要回避多学一点大语言模型的工作原理。今天我们只是非常简略地介绍了它们如何训练，但你还可以了解很多内容，不一定非要深入机器学习，或者钻进科学研究的细节里。</p>
<p>我认为，理解这些原理是有帮助的，就像你开发 Web 应用时，了解数据库的工作方式也很有帮助一样。因为在产品层面、运行框架层面，你做出的越来越多决策都会受到模型本身的影响。对模型如何工作建立起直觉，无论你担任什么角色，都会让你处于很有利的位置。今天我要讲的就是这些。</p>
<p>谢谢大家。</p>
