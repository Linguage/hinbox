<h2>摘要</h2>
<p>Boris 与 Mark 探讨了 Claude Code 的产品演进、多智能体协作，以及企业如何围绕 AI 重新设计工作流程。Boris 认为，模型能力的持续提升，使 AI 从逐行补全代码走向自主协调任务；真正的生产率提升，则来自逐一消除编码、审查、营销等环节的瓶颈，而不只是把 AI 加在原有流程旁边。对话也讨论了试验文化、投资回报、评估、安全护栏，以及 AMD 如何利用智能体应对芯片设计和规模扩张的挑战。</p>
<p><a id="section-2"></a></p>
<h2>概述</h2>
<p>访谈从 Claude Code 如何为未来模型能力设计产品讲起，依次讨论 Anthropic 的日常使用方式、工程师与管理者所需的新能力、从一个智能体扩展到成百上千个智能体的路径，以及如何用更多推理计算换取更好的结果。后半部分聚焦投资回报与实验自由、评估与直觉的分工、模型对齐和安全机制，最后展望更长时间自主运行、承担更大任务的智能体。</p>

<h2>正文</h2>
<p><a id="section-4"></a></p>
<h3>为模型能力的下一阶段设计产品</h3>
<p><strong>Boris：</strong> 我记得第一次使用这些产品时，感觉非常惊艳。我们当时觉得，模型很快就会达到一个远比那时更强大的水平。对编程来说，它不会只补全一行代码，而是能够编写整个函数、整个文件、整个功能，乃至整个项目。现在我认为，到今年年底，它们将能够构建整个业务。</p>
<p>我们看到了这条曲线。我们把它叫作“指数增长”，模型就是这样发展的。有一些缩放定律，描述模型智能如何随时间提升。这些规律不知为何一直成立，实际上还在加速。这是一种经验性观察：为什么它会持续发生，并不显而易见，但它似乎就是在发生。</p>
<p>我们所做的，不过是顺着这条线往前推：模型现在在这里，将来会到那里。如果产品还停留在现在的位置，就不足以让人们体验模型的力量。因此，我们想要一种完全智能体化的产品。</p>
<p>说实话，Claude Code 在最初六个月里并不好用。它需要时间，模型也需要时间追上来。直到 2025 年 5 月的 Opus 4，我觉得它才真正开始好用。此后，产品的增长也变成了指数式增长。最初并不是这样，是从那时才开始的。</p>
<p>随着模型越来越成熟，我们不断找到新的使用方式，也不断发现怎样在产品中释放这些能力。我们推出了 Quad Tag，这是这种思路的最新一次迭代：一个长时间运行的异步智能体，你可以像对待同事一样与它互动。它有很好的常识，也很懂得什么时候该介入、什么时候不该介入。这种变化会持续发生。我们会不断自我颠覆，不断寻找下一种产品形态。</p>
<p><a id="section-5"></a></p>
<h3>从固定流程走向模型自主协调</h3>
<p><strong>Mark：</strong> 你谈到如何预测这条进步曲线。但我更想知道，你们当时是如何设计多智能体架构的？运行多个智能体，让我们有机会重新思考工作流程的实现方式。令我震惊的是，我们真的有机会重新设计、重新构建每个人完成工作的方式。这是你们一开始就纳入开发设计的目标，还是能力发展之后自然出现的结果？</p>
<p><strong>Boris：</strong> 两者都有。回想几年前，我们怎么用模型？主要是让它做一行代码的自动补全。我们也有所谓的智能体工作流，但本质上是确定性的系统：其中某一步可能调用语言模型，做一点计算，整个流程仍然是预先确定的。</p>
<p>随着模型变得更聪明，我们意识到，让模型本身成为工作流的协调者，效果要好得多。由模型来主导，你给它获取上下文的工具，再给它与外部世界互动的工具，提出任务，然后让它自己决定怎样协调执行。</p>
<p>你不再告诉它：“先做第一步，再做第二步；如果第二步不成立，就这样；否则那样。”现在已经不是这种工作方式了。你给它目标、起点和工具访问权限，它就会自己想办法。</p>
<p>我认为，这种转变最主要的原因就是模型变聪明了。Claude Code 内部也经历了同样的学习过程。最初，我们会把上下文一点一点喂给模型。随着模型更成熟，我们发现，这样也许并不是最佳方式，于是逐渐减少这种做法。</p>
<p>例如，我们有一个每次会话都会加载的 CLAUDE.md 文件。现在，我们越来越多地看到客户转向技能、工具和 MCP，因为这样一来，模型在决定如何加载所需信息时，就有了更多控制权。</p>
<p><a id="section-6"></a></p>
<h3>Claude 如何成为 Anthropic 工作的中心</h3>
<p><strong>Mark：</strong> 我得问问，你们 Anthropic 的员工每天都在用 Claude。你们是第一批客户，在其他人看到产品之前，你们就已经在确保它能完成自己的任务。说说你典型的一天吧。你在创造工作成果时，Claude 是不是已经像身体的延伸一样？</p>
<p><strong>Boris：</strong> 这是 Anthropic 工作方式中很特别的一点：Claude 是我们所做一切事情的中心。每一个业务流程，每个人一天中的每一部分工作，都围绕 Claude 展开。</p>
<p>我有时会这样描述：假设你是刚加入 Anthropic 的新员工，正在办理入职。你想知道办公室在哪里、地址是什么。在大多数公司，你会去搜索内部知识库，或者问同事。在 Anthropic，你会问 Claude。你想知道代码库在哪里、怎样获得访问权限，也不是去查知识库，而是问 Claude。你出差回来，有一笔费用要报销，想知道报销单怎么提交，同样从问 Claude 开始。</p>
<p>而当你真正深入工作以后，Claude 仍然是中心。它写代码，做代码审查和安全审查，参与头脑风暴，提出新产品想法，汇总用户反馈，分流处理故障事件。工程软件开发生命周期的每一个环节，都以 Claude 为中心。</p>
<p>现在，不只是工程，产品、设计、营销、市场拓展，以及每一个职能部门，都在发生这样的变化。工具的样子可能不同：未必是终端里的 Claude Code，也可能是 Cowork 这样的工具，但中心仍然是 Claude。</p>
<p>在那些最成功的 Claude 使用者身上，我看到的也是这一点：把它放到每个流程的中心。</p>
<p><strong>Boris：</strong> 我们之前聊到过，我特别喜欢一篇上世纪九十年代的《哈佛商业评论》文章，大概是 1992 年或者 1996 年。题目类似于“计算机已经来了，为什么我们还没有看到生产率收益？”当时很多人都在争论这个问题。</p>
<p>文章的大意是，企业分为两类。第一类把计算机放在办公室角落里，原来所有纸笔流程、文件柜都保留，一切照旧，只是角落里多了一台电脑。这些企业看不到生产率改善。</p>
<p>第二类则把文件柜扔掉，把纸笔烧掉，让计算机成为每一个流程的中心。正是这类企业释放出了生产率提升。</p>
<p>从今年年初到现在，Anthropic 每位工程师的代码产出增长到了原来的八倍。这在行业里几乎闻所未闻。通常企业每年看到的只是几个百分点的提升。现在，我们使用 Claude Code 的一些最大客户，也开始看到类似的变化：50%、100%、150% 的改善。</p>
<p>我们之所以能做到八倍，是因为系统性地一次消除一个瓶颈。起初，瓶颈是写代码，我们让 Claude 来写。下一个瓶颈是代码审查，那就让 Claude 做审查。再下一个可能是为市场拓展制作材料，我们也让 Claude 参与。就这样，一步一步地疏通流程中的每个环节。</p>
<p><a id="section-7"></a></p>
<h3>工程师与领导者需要什么新能力？</h3>
<p><strong>Mark：</strong> 我喜欢这一点，因为你们是用自己的真实需求推动开发。这形成了一个自我强化的循环，让资源投入始终围绕真正的价值。你们是一家 AI 原生公司，接受变化的速度惊人。我很想听听，你如何看待工程师领导者的角色？你们比大多数人更早看到这些变化，也更早开始思考怎样带着大家一起前进。</p>
<p><strong>Boris：</strong> 往后退一步看，工程一直都在变化。作为工程师，我们并不陌生。我祖父当年在苏联用穿孔卡编程。我小时候写 BASIC 和汇编，后来逐渐学习更高级的语言。我也写过一段时间 JavaScript。每个 JavaScript 工程师都知道，框架总是在变，几乎每个月都会出现一批新框架，大家都得学习新技能。</p>
<p>所以，语言一直在变，框架一直在变。现在发生的是，变化正在加速。我们不断提升抽象层级：从硬件到穿孔卡，从穿孔卡到源代码，现在又从操作源代码走向操作智能体。我们还在再上一层，从管理智能体走向管理循环与例行任务。疯狂之处在于，最后这两步只用了两年。我认为，这种加速还会继续。</p>
<p>当我思考哪些工程师、哪些人最成功时，我想到的是那些尊重实证、充满好奇心的人。他们会看数据，会调整方法，不会认定过去一直有效的做法今后也一定有效。他们能够从工作中获得反馈，有了新数据，就能采用新方法。</p>
<p>另一个特质是自主性。当工程实施不再是瓶颈，真正限制我们的，就变成了产生好想法、把想法推向市场，并且安全地做到这一切的速度。</p>
<p>最有效的人，并不是每次把一个想法推向市场都需要庞大流程、必须与十个团队协调的人。他们更像一人军团，像 CEO 型的人：能够提出想法、与用户交流、分析数据、构建产品、反复迭代，然后推向市场。</p>
<p>我们看到，这样的人不只来自工程部门，而是来自各种职能。今天，工程背景仍然有帮助，但我认为，它已经不再是做成这类事情的必要条件。</p>
<p><strong>Mark：</strong> 这确实改变了我们需要强调的技能。你得适应变化，不怕变化。我很喜欢你说的好奇心，以及不断试验。这些新的智能体工作流，确实就是过去七个月到一年间出现的变化，已经改变了迭代的方式。现在，你可以用过去根本做不到的方式开展实验。学习循环大大加快了，不是吗？</p>
<p><strong>Boris：</strong> 完全是这样。而领导者有责任创造空间。如果你不调整，不给大家腾出空间，所有人就会继续沿用旧方法。某种程度上，你必须推动大家采用新方法。</p>
<p>不过，对许多人来说，能够尝试这些工具、开展实验，本身就很令人兴奋。因此，我认为自己很大一部分职责，就是创造空间，让人们敢于尝试，并且感到安全。他们不会因为尝试一个新想法就得到糟糕的绩效评价，因为那个想法说不定真的有效。</p>
<p>我的另一项工作，是给大家提供上下文，包括业务背景和产品背景，让他们能够作出更好的决策。</p>
<p><strong>Mark：</strong> 对于那些不是 AI 原生的公司，你们走过的这些路，需要通过展示最佳实践、培训员工，以及真正推动文化转变，才能学会。</p>
<p><strong>Boris：</strong> 对。我们的职责，就是帮助企业走过这个过程。</p>
<p><a id="section-8"></a></p>
<h3>从一个智能体到成百上千个智能体</h3>
<p><strong>Boris：</strong> 我看到企业会经历一种自然转变：从不使用 AI，到每位工程师运行一个智能体，再到每人十个，然后是一百个、一千个。每个阶段都有不同的特征。</p>
<p>只有一个智能体时，工程师用它写代码，注意力仍然放在它身上。你仍然像单线程一样，一次只做一项任务。到了某个时刻，你开始信任它，觉得：“它也许真的在做对的事情。它工作的时候，我是不是可以再启动一个？”</p>
<p>工程师会自然摸索出这种方式。你可能对同一个代码仓库建立多个检出目录，或者使用同一份代码的多个视图。一个智能体工作时，你去做另一件事，逐渐扩展到十个左右。</p>
<p>此时，你本质上是在不同智能体之间轮流切换：在第一个那里启动工作，再去第二个那里做一点，然后到第三个。我们现在的桌面应用已经很好地支持这种工作方式。无论 Claude Code 还是 Cowork，你都可以启动一个会话，再启动另一个，让多项工作同时进行。</p>
<p>但当规模继续扩大，事情就更有意思了。我观察到，大多数企业仍处在第一阶段和第二阶段之间。Anthropic 平均大概处在第三阶段，多数工程师正在运行几十个乃至几百个智能体。</p>
<p>实现方式，是让一个智能体启动另一个智能体。我们为此提供了很多工具。</p>
<p><strong>Mark：</strong> 所以是子智能体？智能体运行子智能体，你是这么理解的吗？我们也用了这个词，只是不知道它是不是行业标准。</p>
<p><strong>Boris：</strong> 对，就是这样。智能体拥有子智能体，子智能体还可以再启动子智能体。层级可以很深。Claude Code 现在支持最多五层这样的嵌套。</p>
<p>在产品层面，也有不同的支持方式。例如，我们一直在尝试云端执行：智能体不是运行在你的本地电脑上，而是在云端运行。你可以从桌面应用或手机应用里启动它。现在，我有很多编程工作就是通过手机完成的。</p>
<p><strong>Mark：</strong> 我喜欢这个。</p>
<p><strong>Boris：</strong> 它就在云端运行。这恰恰让扩展规模成为可能。我们还在持续迭代，让这种方式更自然，并扩展到成千上万个智能体。</p>
<p>实现这一步的办法，是动态工作流。本质上，就是用 Claude 协调整支庞大的智能体团队，处理最复杂的工作，例如大规模代码库迁移。</p>
<p>我记得 Stripe 最近就用了这种方式。原本可能需要几个月的一次迁移，把大约一万行 Scala 代码迁到 Java，最后只用了四天。很多公司都在用它做大型迁移。我们刚刚把 Bun 从 Zig 迁到了 Rust。Bun 是一个 JavaScript 运行时，代码量很大。</p>
<p>对于那些过去需要几周、几个月甚至几年的巨大工作流，一种办法就是分而治之：给模型很多智能体，告诉它“去想办法完成这个大任务”。</p>
<p><strong>Mark：</strong> 这又回到了我们前面说的：这是一个过程，需要教育，也需要文化改变。如果做对了，我们也有类似的例子。</p>
<p>我们需要一个基于 Rust 的应用，否则就可能出现竞争力缺口。我们的 AI 软件开发负责人用了一个周末就把它做了出来。当然，之后还必须验证，经过所有测试流程，达到可以发布的状态。但一个周末就能做到这一步，过去简直闻所未闻。多智能体能做到的事情，实在让我惊讶。</p>
<p>再回到你原来的预测，听起来，这恰恰就是你预料中的发展。</p>
<p><a id="section-9"></a></p>
<h3>推理时计算：怎样让更多 token 带来更好的结果</h3>
<p><strong>Boris：</strong> 是的，这是我们预期中的事情。你永远无法准确知道它会怎样扩展，但出于某种原因，这些规律一直在延续。</p>
<p>有意思的是，最早那篇缩放定律论文的几位主要作者后来创办了 Anthropic。我想，他们知道事情会走向哪里，也知道安全和信息安全会变得非常重要。</p>
<p>传统的缩放定律讲的是，能力如何随着网络规模、数据量和计算量变化。现在我们看到，它也与测试时计算，也就是推理时投入的计算量有关。说白了，就是你往问题上投入多少 token。</p>
<p>从产品设计和模型训练的角度，我们希望你能更有效地给一个问题投入更多 token，从而得到更好的结果。因为如果只是粗暴地增加 token，花得更多，也未必做得更好。</p>
<p>一个例子是推理投入等级。你可以设置模型的 effort：等级越高，模型愿意为这个问题投入的 token 上限就越高。在我看来，多智能体和动态工作流，也是推理时计算的另一种形式。你投入更多 token，再通过智能体之间的协调，尤其是让模型来协调，就能更有效地利用这些 token，得到更好的结果。</p>
<p><strong>Mark：</strong> Boris，我听你说过，愿意投入这些 token 很重要，否则你甚至不知道自己能够达到的上限在哪里。能跟观众解释一下吗？</p>
<p><a id="section-10"></a></p>
<h3>投资回报：不要只盯着成本</h3>
<p><strong>Boris：</strong> 现在很多企业都在思考投资回报率，以及应该如何衡量。我觉得，有些企业的思路其实错了，因为它们只盯着 ROI 里的 I，也就是投入：这笔投资怎样减少？成本怎样削减？</p>
<p>这些当然重要，也应该做，而且有很多工具。你可以使用 Opus 计划模式、顾问模型、较低的推理投入设置，或者更便宜的模型。不是什么事情都需要 Opus，也许可以用 Haiku，或者 Sonnet。当然，你应该编写评估，判断到底适合哪一种。</p>
<p>但我认为，远远更重要的是 R，也就是回报：怎样提高你从模型中获得的收益？</p>
<p>我们从成功客户身上看到的最大经验，是要给工程师自由实验的空间。其实应该给每个人这种自由，让他们发现新的使用场景。你需要鼓励试验，营造让人们敢于尝试的文化，他们会让你大吃一惊。</p>
<p>想出绝妙主意的，未必是最资深的工程师，也可能是一个刚毕业的新人。找到营销流程自动化办法的，未必是工程师，也可能是组织某个角落里、你从未见过的一位营销人员。正因为他们在试验，才会产生好想法。</p>
<p>所以，首先要鼓励的是实验。如果一个内部用例或产品真正发展起来，虽然消耗很多 token，但确实成功了，那时再去优化。没有前面的探索，你根本发现不了机会。找到机会之后，再像解决其他工程问题一样优化它。</p>
<p><strong>Mark：</strong> 我喜欢这个说法。你强调的另一点，是机会正在变得更加普及。</p>
<p>我们遇到过一个芯片设计中的缺陷。一个工程团队研究了好几周，也没能解决。后来，一位初级工程师说：“我觉得我可以解决。”他用一组智能体流程去处理，最后解决了这个极其罕见的问题。要让那个芯片缺陷出现，需要大约二十件事情同时发生。</p>
<p>当然，那是在产品出货之前，还处在调试和测试阶段。这件事让一些资深工程师从根本上受到了震动，也推动了 AMD 对这些方法的采用。</p>
<p>你必须亲身体验。光是谈论、嘴上认同是一回事，但一旦亲眼看到一个原本解决不了的问题被解决，或者真正体验到巨大的生产率提升，我见过一个又一个领导者当场转变，开始相信这些方法。</p>
<p><a id="section-11"></a></p>
<h3>放下旧经验，像与资深工程师一样合作</h3>
<p><strong>Boris：</strong> 对。你也需要带着一定的谦逊进入这个过程。我自己反复学过这个教训。在我终于放手、让 Claude 来主导之前，我总想按自己的方式手工去做。</p>
<p>大概一年前，我也在调试一个问题。我手工运行性能分析，想查明发生了什么。团队里一位新加入的同事，直接让 Claude 做同样的事情。我当时说：“不，不，不，不可能。Claude 肯定查不出来。”</p>
<p><strong>Mark：</strong> 连你都这么说？</p>
<p><strong>Boris：</strong> 连我都这么说。某种程度上，我有偏见，因为我经历了 Claude 的每一代模型。在我的脑海里，某个角落仍然停留在老一代模型上，而模型不断进步，当时的能力早就不是那个水平了。</p>
<p>结果，不到二十分钟，那位同事就找出了正确的解决方案，我却没有。</p>
<p><strong>Mark：</strong> 哇。</p>
<p><strong>Boris：</strong> 我一次又一次地学到这个教训。随着模型越来越先进，我和模型的关系也在改变。我越来越不需要手把手带着它，不需要微观管理，而是更像在和一位资深工程师合作：我信任它，给它背景、给它目标，定期看看进展。</p>
<p>如果我还不太信任它，或者它对这个问题比较陌生，我就更频繁地检查。真正的重点，是设置合适的护栏，然后让模型去完成工作。</p>
<p><a id="section-12"></a></p>
<h3>评估与直觉各有什么作用？</h3>
<p><strong>Mark：</strong> Boris，我有个问题。这确实让团队能力变得更加普及。但我们也看到，不同的人会并行工作，可能出现五种改善同一流程的方法。你们怎么看这个问题？如何衡量，如何选择最后采用哪一种？基准测试和测量在智能体时代扮演什么角色，才能帮助我们作出决策，不至于在解决问题时产生大量分叉、各行其是？</p>
<p><strong>Boris：</strong> 正是如此。我认为，有两种工具：一种是评估，也就是基准测试；另一种是直觉感受。两者都有自己的位置。</p>
<p>如果一个工作流会重复几千、几万、几十万乃至上百万次，你肯定需要评估。例如，一个新模型发布了，你把它换进运行框架，就得确认它真的带来了改善。评估提供了测量办法。</p>
<p>对于其他事情，比如产品体验，直觉感受其实相当有用。编写评估有成本，你不应该事事都写。你要判断：什么时候亲自使用后的直觉已经足以告诉你一些东西，什么时候才确实需要正式评估。</p>
<p>至于各种不同产品与实现方案，拥有模型的一大好处，是代码迁移和合并变得非常容易。一旦选定你想要的方法，通常只需让 Claude 把其他调用位置迁到这个工作流上，就可以了。</p>
<p><a id="section-13"></a></p>
<h3>信任、模型对齐与多层安全机制</h3>
<p><strong>Mark：</strong> 我想稍微换个话题，谈谈我们所有人都必须关注，而且一直处于 Anthropic 做事方式核心的东西：信任与验证。</p>
<p>我在此前一期节目里采访过在哈佛任教的 Kathy Fam。我们谈到了治理，以及如何把治理纳入流程。一方面，你要通过治理确保 AI 安全；另一方面，你要进行验证，确保达到所需的准确性。两者共同构成信任，也是部署 AI 的基础。</p>
<p>我知道这对你很重要，从我们对话一开始你就提到了。你们究竟如何把这些要求落实进去？靠一张检查清单，还是直接融入每天运行的工作流程？</p>
<p><strong>Boris：</strong> 这是很多层的事情。正如你所说，这就是 Anthropic 所做一切的核心。随着模型越来越强大，越来越深入业务流程，它必须安全、可靠、值得信任，并且与使用者的意图保持一致。</p>
<p>我们从很多不同层面入手。最基础的是模型对齐。我们有一支很大的团队在做这件事，发表了大量研究，也通过很多博客文章分享所学到的经验。这背后是多年的研究。</p>
<p>对齐包含很多方面，比如真实性：模型应该说出正确的东西。另一个方面是不盲目附和。模型的一种失败模式，是用户说什么，它都同意。但我真正愿意合作的好模型，会提出异议。</p>
<p>在一些较新的模型中，比如 Opus 4.7，尤其是 Opus 4.8，我们在这一点上取得了很大进展。如果模型训练得好，我提出一个糟糕的想法时，它会反对。这反而让我更信任它。</p>
<p>还有其他层面。“信任”里包含很多东西，其中一个是信息安全。这也进入了模型训练，比如抵抗提示注入的训练。我们发布的每一个模型都有系统卡，说明它对提示注入等常见攻击的抵御能力。</p>
<p>Opus 4.7、Opus 4.8，以及 Fable，是行业里最不容易受到提示注入影响的一批模型。我记得差距可能达到五倍或十倍，是很大的差距。</p>
<p><strong>Mark：</strong> 所以，这必须从架构上就纳入考虑？你们是怎么做的？</p>
<p><strong>Boris：</strong> 背后有大量训练。这是模型训练流程的一部分，我们训练模型抵御这些攻击。尤其是配合运行时的提示注入分类器，而我们确实也这样做，实际中的攻击成功率如今已经接近零。</p>
<p>这显然非常重要。模型做得越多，与越多系统交互，对这些常见攻击的抵抗力就越重要。</p>
<p>随着模型能力增强，我们还需要一种办法，让它能安全地运行更长时间。现在已经有持续运行数天、数周、数月的工作负载，显然不可能一直让一个人坐在那里看着。</p>
<p>差不多在同一时期，我们还意识到：如果每一步都让人决定是或否，到了某个时刻，人就会停止阅读，只是不断点击“是”，因为实在厌倦了反复确认。我自己也发现了这个问题：我会不再仔细阅读 Bash 命令，只是说“可以”。我们的安全团队也看到了同样的现象。</p>
<p>于是，他们开始研究：能否把这些决策交给一个分类器，让它判断？这项工作花了很多个月才成熟。最终，通过评估、红队测试和渗透测试，我们能够证明，这种方式实际上安全得多。</p>
<p>因此，在 Anthropic，我们使用自动模式，也向所有客户推荐这种方式。</p>
<p><a id="section-14"></a></p>
<h3>规模扩张、算力与 AMD 的芯片设计</h3>
<p><strong>Mark：</strong> Boris，你们正在每个阶段消除瓶颈。但对于未来的规模扩张，你怎么看？每次发布，你们所承担任务的复杂性都在急剧增加。怎样管理这样的规模，又怎样保持这样的速度？</p>
<p><strong>Boris：</strong> 很大程度上，就是继续沿着缩放定律前进，并且在规模扩大的过程中不断重新发明产品。也需要找到优秀的合作伙伴，共同支持规模扩张和所需的计算资源。</p>
<p>另一个关键，是找到合适的护栏来确保安全。因为模型越来越成为我们工作的核心，我们必须保证它做的是对的事情。</p>
<p>不过，Mark，我也很好奇你怎么看。你对规模扩张并不陌生，经历过多代 CPU 和 GPU 的发展。你的看法是什么？</p>
<p><strong>Mark：</strong> 对 AMD 来说，扩展规模是根本问题。旧的摩尔定律意味着，你可以让晶体管密度翻倍、性能翻倍，同时把功耗和成本保持在相同范围内。很多年里，这都非常美好。</p>
<p>但大约十年前，这种趋势开始减弱。并不是说每一代新的半导体工艺节点都不再带来生产率和密度提升，而是成本正在上升，而且正如你肯定看到的，功耗也在上升。</p>
<p>因此，我们必须重新思考如何优化，才能继续保持增长。说到底，我们需要在半导体物理不再支持旧摩尔定律节奏的情况下，仍然维持那种节奏。这是巨大的挑战，但我们愿意迎接它。</p>
<p>坦率地说，智能体工作流对扩展规模非常有帮助。它们帮助我们管理更大的状态空间、更多变量，也让芯片设计中的更多部分能够被优化。我认为，没有这些智能体工作流，我们就无法继续扩展。它们出现得恰逢其时，是一种完美的汇合，让我们能够继续前进。</p>
<p>你还提到伙伴关系。那同样是 AMD 的核心，包括与你们的合作，以及整个行业中的合作。这也是我们扩展规模的基础。我们希望开展深入合作，确保采用最好的方法。</p>
<p>就像你今天分享的那些故事，我们希望成为 Anthropic 最佳实践的第一批采用者。对 AMD 和整个芯片行业来说，不断创新以维持规模扩张，是至关重要的。</p>
<p><a id="section-15"></a></p>
<h3>未来六个月：更长运行时间、更强自主性</h3>
<p><strong>Mark：</strong> 我还必须问一个问题。你提到，我们正在沿着你预测的曲线前进。那么，未来两三年你看到了什么？在 AI 的时间尺度上，两三年简直像永恒一样漫长。</p>
<p><strong>Boris：</strong> 两三年真的太长了。不如我想想未来六个月吧。否则，我的预测很可能偏得太远。</p>
<p><strong>Mark：</strong> 六个月，当然。</p>
<p><strong>Boris：</strong> 我认为，六个月后，智能体平均会运行更长时间，人们平均会同时运行更多智能体。它们也会更好地与人的意图对齐，需要的方向纠正更少，手把手指导更少，自主性更强。</p>
<p>对大多数人来说，至少对大多数工程师来说，希望也能超出工程师群体，让智能体一次运行数天或者数周，会变成一件很正常的事，而不再只是少数工程师在做的特殊实践。</p>
<p>到今年年底，我认为我们会开始看到 Claude 构建越来越大的东西。不只是功能，而是产品。甚至可能开始看到由 Claude 构建的整个初创企业。</p>
<p>进步仍在继续。我们很兴奋，希望让这一切既安全，又成为人们乐于使用的体验。</p>
<p><strong>Mark：</strong> Boris，非常感谢。谢谢你分享洞见，谢谢你的愿景，以及你对整个行业产生的影响。天哪，未来真令人兴奋。非常感谢。</p>
<p><strong>Boris：</strong> 谢谢你，Mark。</p>
<p><a id="section-16"></a></p>
<h3>节目结语</h3>
<p><strong>Mark：</strong> 与 Boris 的对话让我非常愉快。我觉得，他让我们提前看到了在 AI 智能体时代，工作将如何变化。</p>
<p>有几点尤其令我印象深刻。首先，招聘非传统背景的人很有价值，他们能带来新的视角与热情。其次，在 Anthropic，Claude 已经处在员工体验的中心。再者，智能体 AI 让机会更加普及，让任何层级的人都能作出有影响力的贡献。</p>
<p>最后，考虑投资回报时，不要只关注投入，也要关注回报。由此带来的实验自由，会孕育最大的成功。</p>
<p>感谢大家今天收看。我期待继续带来更多深入对话，与行业中最聪明的一些头脑一起，讨论前沿技术、行业洞察和富有远见的观点。</p>
<p>你可以在 AMD 的 YouTube 频道观看视频节目，也可以在 Spotify、Amazon Music 和 YouTube Music 等平台收听音频。技术总是在向前发展，我已经迫不及待，想在下次与你们分享更多洞见。</p>
