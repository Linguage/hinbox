内容概述

本期内容是一门关于如何高效使用 AI 编程智能体（Coding Agents）构建软件的进阶教程。讲解人以当前流行的 AI 代码编辑器 Cursor 为例，系统阐述了智能体的工作原理及其核心运行机制。课程内容涵盖了编写高质量提示词与上下文管理的方法、如何在庞大的代码库中进行精准与语义搜索、利用“计划模式”（Plan Mode）开发新功能的标准流程、遵循调试基本原则解决复杂 Bug（如使用 Debug 模式和 MCP 服务器），以及如何通过引入 Bugbot 进行代码审查与自动化测试。最后，讲解人还分享了如何通过配置“规则”（Rules）和“技能”（Skills）以及集成 CLI 工具，为团队量身定制 AI 智能体，从而全方位提升软件工程的开发效率与代码质量。

访谈/课程正文

引言与核心概念

讲解人： 如今，开发人员正广泛使用智能体（Agents）来编写代码。大家不再亲手敲下每一行代码，而是与智能体交流，让它代为编写。在上一节课中，我们学习了智能体的核心行为逻辑：赋予它们强大的工具，并让它们在一个循环中自主运行。在本节课中，我们将探讨与编程智能体高效协作以构建软件的策略。让我们开始吧。

Cursor 是一款内置了编程智能体的 AI 编辑器。这个智能体运行在一个被称为“运行环境（Harness）”的架构中。该架构由三个部分组成：首先是你向模型下达的指令（Instructions），比如系统提示词或任何引导其行为的规则；其次是你提供给模型的工具（Tools），比如编辑文件、搜索代码库或运行终端命令的能力；第三是该运行环境所使用的模型（Model），在 Cursor 中，用户可以在多种前沿模型之间进行选择。

基于你设定的目标，这些编程智能体能够承担非常复杂的任务，而且每个运行环境都有细微的差别。不过，你不需要过多考虑这些底层细节，Cursor 会为你处理好这一切。更重要的是，你要学习如何高效地使用这些模型，而这一切都要从你提供的提示词（Prompts）开始。

提示词编写与上下文管理

讲解人： 让我们来比较两种与模型交互或编写提示词的方法。你可以写一个非常简单的提示词，但这需要智能体去猜测你想要的页面布局、组件或样式方案。这有时候能行得通，但通常情况下，你需要向模型提供非常明确的意图。

相比之下，如果你提供一个细节丰富得多的提示词，其中引用了代码库中现有的模式，或者提供了日志等附加信息，那么你获得高质量输出的概率就会高得多。在后续讲解开发新功能和使用“计划模式（Plan mode）”时，我们会深入探讨这一点。但需要记住的是：你通过提示词传达给模型的意图，真的会决定你最终获得的代码质量。

在与智能体协作的过程中，你们的对话会不断积累“上下文（Context）”。比如你们来回发送的消息、智能体发起的工具调用，或者被读取的文件内容。这些上下文就像是智能体的“工作记忆”，它非常强大，但也存在一些限制。因此，你需要留意智能体占用了多少上下文。

我通常建议：如果你要开始开发一个新功能，最好开启一段新的对话；或者如果你发现智能体开始偏离轨道并频繁犯错，这也是开启新对话的一个好信号。最新的模型在为你寻找正确的上下文方面变得越来越出色。当你为它们配备了高质量的工具（比如允许它们搜索整个代码库）时，它们就能根据需要调取所有相关的文件。所以，如果你明确知道要修改哪个文件，你可以在提示词中直接@标记它；如果你不知道，现在的智能体也相当擅长替你找到正确的文件。

搜索与理解代码库

讲解人： 软件工程师最重要的工作之一，就是在脑海中构建出代码库的“心理映射（Mental map）”，并深刻理解系统的运作方式。随着项目的扩大，找到正确的代码以及梳理这些复杂系统变得越来越困难。在过去，要梳理代码意味着你需要掌握正则表达式（Regex）的编写模式，或者学习新的工具才能高效地搜索代码库。但现在有了编程智能体，你可以用自然语言描述你要找的东西，然后让智能体利用工具帮你找到准确的信息。

Cursor 为智能体配备了非常具体的搜索工具。了解这些工具的工作原理，有助于你提出更好的问题并获得更准确的结果。

寻找一段代码最精确的方法是进行“精确匹配（Exact match）”。无论是函数名、变量名，还是代码中的其他片段，智能体都可以使用诸如 grep 这样的工具来帮你找到这些精确的字符串匹配，它们还能帮你编写复杂的正则表达式。后来出现了比 grep 更好的工具，比如支持递归搜索的 ripgrep，两者都很棒。但在 Cursor 中我们更进了一步，使用了一种叫做 instant grep 的技术，它能在极其庞大的代码库中进一步加速这种基于智能体的搜索。你不需要学习或配置任何东西，Cursor 的智能体会自动使用它们。你只需用自然语言与智能体交谈，它就会在后台使用这些工具来搜索你的代码库。

当你不知道确切的关键词时，“语义搜索（Semantic search）”可以通过你提供的文本含义来帮你找到代码库中的对应部分。比如，如果你问智能体：“我们在哪里处理用户认证？”，语义搜索能帮你找到像 middleware（中间件）这样的文件，即使该文件中并没有直接出现“认证（authentication）”这个确切的字符串。这之所以可能，是因为 Cursor 会使用一个嵌入模型（Embedding model）将你的代码库转化为可搜索的向量数据。说白了就是，Cursor 对你的整个代码库和所有代码符号有深刻的理解，然后能将它们与你使用的自然语言映射起来。根据我们的研究，当你在代码库中将精确匹配（如 grep）和语义搜索结合使用时，可以显著提高响应质量，在处理超大型代码库时效果尤为显著。同样，你不需要配置任何东西，Cursor 会在启动应用程序时在后台自动索引你的代码库。

智能体还可以生成“子智能体（Sub agents）”来更高效地完成任务。Cursor 内置了一个“探索子智能体（Explore sub-agent）”来帮你搜寻代码库。这个子智能体在自己独立的上下文窗口中运行，与父智能体隔离开来，因此它既快速又高效，不会使主对话变得臃肿。正如我们在课程第一部分所讲的，理解并管理你的上下文至关重要。如果你在一个包含大量文件的庞大代码库中进行搜索，会消耗大量的上下文和 token。因此，我强烈建议使用子智能体来优化上下文管理，它们只会返回搜索结果，从而让主对话保持高度专注。

对于庞大或陌生的代码库，你还可以要求智能体为你生成架构图。一个很受欢迎的工具叫做 Mermaid 图表，它可以帮你把整个代码库可视化。这些图表对于新人入职培训文档，或者审查数据在系统中的流向非常有帮助。

我经常看到的一个常见错误是：开发者要求智能体修改代码，但他们自己还没有完全搞懂这些代码的运作原理。于是智能体可能会去创建一套新的工具函数，或者在代码库中引入一种全新的设计模式，而实际上代码库中原本就有现成的代码可以复用。在这里，你的“意图”非常关键。编程智能体会非常字面地理解你的请求。如果你不提供明确的意图，它们就会基于自己的判断行事。这有时或许可行，但遵循代码库中现有的模式是非常重要的，否则你将会制造大量的技术债务（Tech debt）。

所以，在进入下一环节之前，我强烈建议先使用编程智能体来加深对代码库的理解。

开发新功能与计划模式（Plan Mode）

讲解人： 现在你能找到代码并对代码库有了更好的理解，是时候进入下一章了。我们将学习如何把想法转化为新功能，如何从制定计划开始，如何验证其可行性，并最终将想法变成真正运行的软件。

借助编程智能体高效开发新功能的关键在于：将工作拆解为智能体可以自行验证的步骤。 因此，我建议在开发任何新功能时，都先制定一个计划，并设置好护栏，以便智能体能够验证并修复自己的错误。实际上，在你真正去生成所有代码之前，编程智能体非常擅长帮你梳理在计划阶段需要做出的各种决策。

在 Cursor 中，我们有一个名为“计划模式（Plan mode）”的功能，它可以帮助你调研代码库、提出并回答澄清性问题，然后生成一个你可以编辑和修改的分步计划，最后再去生成代码。让我们实际看一看。

现在我打开了 Cursor，针对我们的文档系统，我有一个好主意：我想为我们支持的每一个 AI 模型添加专门的页面，以便用户能看到更多细节。在智能体输入框中，我按下 Shift + Tab 键进入计划模式，然后输入：“让我们在应用文档中为我们支持的每个模型添加专属页面。”

我故意把这个提示词写得有些模糊。我希望与模型进行交互，共同弄清楚这里的需求，并反复打磨这个计划，以确保它的质量。智能体开始工作了，你可以看到它实际上启动了我们刚才提到的“探索子智能体”去理解文档站点的结构、现有代码库的工作原理、哪些代码可以复用，以及我们需要在代码库中添加或修改哪些内容。查看日志，我们能看到模型正在使用诸如 grep 这样的工具来精确匹配文件。它正在阅读特定的文件，并思考实现我们目标的最佳方案。此外，它还可以运行 Shell 命令去寻找更复杂的代码模式。

接着，它会向我提出一些问题，希望能明确我们的需求。我们收到的第一个问题是：“哪些模型应该有专属页面？” 我回答：“只包含未隐藏的模型。”因为我们支持的模型很多，初期我们尽量保持一个小而聚焦的集合。

Cursor 界面的一个优点是，我们可以创建非常互动的 Markdown 计划，我们可以在其中直接编辑并根据需要进行修改。当准备就绪时，我们就可以点击“构建（Build）”按钮。 让我们一起通读一下这个计划，确保它大体上是正确的：

  • 我们有一个列出所有模型的模型页面。
  • 模型建议针对我们支持的所有不同页面使用动态路由（Dynamic route），这看起来很合理。
  • 它会在我们的配置文件中通过 ID 查找模型。
  • 它将创建一个新组件来展示模型的能力，这也不错。
  • 它会在侧边导航栏中连接这些页面，并列出了可能需要修改的文件。
  • 这里甚至还有一个我们之前提到的 Mermaid 架构图，帮助我们将数据在应用程序中的流向可视化。

如果我想的话，我可以在这里直接进行修改，但为了节省时间，我们就直接点击“构建”。好了，计划启动，代码开始生成了。

我们可以点击查看代码差异（Diff）。但我想先对智能体说：“启动本地开发服务器来测试这些修改。”我们现在可以告诉智能体，既然代码写好了，它实际上知道该如何启动我们的软件。因为我们正在为这个文档应用开发 Web 程序，它可以直接在后台运行开发服务器，监听端口，然后在 Cursor 内部打开集成浏览器，这样我们就可以去验证修改了。

文档页面已经在 localhost 上打开了。让我把它放大一点。在左侧导航栏中，现在有了一个“模型”下拉菜单。我们看到了一些新模型，可以点击其中一个页面。它正在编译新页面……结果报错了，这其实太好了！ 这是一个很好的例子，向我们展示了如何向模型提供反馈。在这种情况下，看起来是一个函数错误，提示“这个 manifest 不是一个函数”。我会复制这个错误，把它粘贴给模型，然后按下回车。使用强类型语言、代码检查工具（Linters）或其他能向模型提供报错反馈的工具，好处就在于此：你可以迅速把错误扔回给它，它知道该如何修复。

现在我们的应用正在编译，它进行了热重载（Hot reloads），我们可以看到新版本正常工作了。我们计划的第一个版本已经完成！

在审查模型的输出时，我们可能会想对某些地方进行微调和迭代。目前的设计还过得去，但我认为可以做得更好。所以，我直接截了一张图粘贴进去，并说：“实际上，让我们把特性的胶囊标签（Pills）做得更好看一些，换上更好的图标。” 向模型提供图片或其他上下文的绝佳之处在于，它为模型理解你当前看到的内容提供了极其丰富的信号。在 Cursor 的集成浏览器中，我们也有一些很好的功能，比如可以直接点选页面上的特定元素，或者像使用外部 Chrome 浏览器一样打开开发者工具。

模型正在进行修改。我们看到它决定为我们的标签使用一些花哨的颜色，我觉得还可以。我也喜欢它选的图标，图标肯定好多了。 但现在我可能想换一种方式，这次我使用语音输入：“让我们保持颜色更符合我们设计系统的品牌调性。”然后提交。因为我们的文档中其他地方并没有太多紫色或绿色，接着它就会去修改。

从制定计划开始，然后通过与智能体反复沟通来迭代设计细节——这就是我构建绝大多数新事物的工作流。 说实话，我对目前的成果非常满意。现在我们可能已经把这个功能做到了可以发布的状态。

我们构建了一个新功能，但软件总是有 Bug，而且有些 Bug 很难被发现和理解。在下一章中，我们将学习如何使用智能体，以系统化的方法来寻找和修复 Bug。

使用智能体进行代码调试

讲解人： 随着智能体为我们编写了越来越多的代码，工程师们花在审查代码、寻找并修复 Bug 上的时间也越来越多。即使有编程智能体的帮助，温习一下如何进行高效调试的基本原则也是很有价值的。无论是人类还是智能体来执行这项工作，出色的调试都遵循相同的原则：

  1. 你需要有办法复现这个问题。 如果你无法复现，就很难验证它是否已被修复。
  2. 你需要将问题精简到最核心的情况。 其他所有多余的信息只会干扰你和智能体。
  3. 你要隔离你正在修改的代码。 如果你一次性修改了三个地方，就很难确切找出根本原因。
  4. 你要带着关于根本原因的具体假设进行排查。 这有助于你快速隔离并发现问题。
  5. 为你的代码添加观测手段（Instrument your code）。 添加日志或使用调试器，来弄清楚数据在系统中是如何流动的。
  6. 最后，一旦你找到并修复了问题，要通过编写测试来防止未来出现回归（Regressions）。 这能确保这个 Bug 未来不会再次出现。

如果你能遵循这些调试基本原则，你就能在排查修复 Bug 时游刃有余。

对于一些错误信息非常明确或相对简单的 Bug，智能体通常可以直接修复。比如我们在上一章中看到的那个错误，你可以直接把报错信息粘贴给智能体并说：“嘿，请修复这个问题。”它基本上就能通过提供的堆栈跟踪（Stack trace）准确地找出所需的信息。所以，在这种情况下，智能体发挥了作用，页面重载，问题修复。这对于简单的 Bug 非常有效。

然而，当你需要调试一个更系统性的问题并寻找其根本原因时，这种方法就行不通了。对于最困难的 Bug，我们推荐使用 Cursor 中的**“调试模式（Debug mode）”**。

与简单地粘贴一段堆栈跟踪不同，调试模式会首先去收集运行时证据，并遵循我们刚才讨论过的那些调试原则： 首先，它会针对到底哪里出错了生成一些假设；其次，它会插桩你的代码，尝试添加一些有针对性的日志，以便智能体后续读取；接着，它会回来要求你实际重现这个问题。所以你在应用中点击操作，触发 Bug，然后智能体就会收集并读取这些日志数据。最后，它会分析日志，试图找出根本原因，并基于收集到的证据进行极其精准的修复。 我们发现，相比于让你手动粘贴大量信息或做大量苦力活，这种方法在寻找和修复最困难的 Bug 时非常有效。

我个人在调试时还发现了一些其他有用的技巧：

  • 你可以让多个模型来修复同一个 Bug，然后比较它们的结果。 每个模型可能会采取稍微不同的方法。当你拥有多次射门机会时，你就能从几个选项中挑出最好的一个。
  • 你可以让智能体使用工具去为你收集证据。 如果你在处理数据库时发现了一个慢查询，你可以让智能体去分析那个查询。在底层，它可能会使用 explain analyze 语句等工具，找出查询缓慢的原因，然后建议你修改数据库 Schema，或者添加索引来加速查询。
  • 智能体还可以从外部工具中提取数据。 你可以安装并使用 MCP 服务器来引入丰富的外部数据。例如，你正在调查一个错误，你可以使用 Sentry MCP 服务器将真实的运行时错误信息直接引入智能体的上下文中，以帮助你发现并修复应用程序中的根本原因。

但我最核心的建议是：务必确保你真正理解了智能体提出的解决方案。 如果你不理解修复方案，你就很难验证这段代码是否真的正确。举个例子，如果你在使用 TypeScript，智能体可能会图省事直接加上一个 any 类型，但这显然不是你理想的解决方案。因此，当智能体提出修复方案时，你应该不断提问，直到你完全理解它。你可以问：“还有没有其他我们没有考虑到的边界情况？”或者“这真的是问题的根本原因吗？”

正如我们在本课程第一部分所讨论的，智能体有时会产生幻觉（Hallucinate），生成一些听起来很有道理的解释或代码片段，但实际上并没有解决根本问题。因此，你需要建立起自己的判断力，确认你拿到的是真正能修复问题的正确代码。

现在你了解了调试方法，以及编程智能体如何帮助你加速排查过程。接下来你需要确保这些修改是正确的，并且不会在未来引入倒退（Regression）。因此在下一章中，你将学习如何使用编程智能体来审查和测试你的代码。

代码审查、测试与优化

讲解人： 编程智能体能够编写大量代码，这也意味着它们同样可能制造技术债务，或者无意中引入 Bug。无论代码是由智能体写的还是人类手写的，你对“什么样的代码能够被合并（Merge）”的标准都应该保持一致。

AI 生成的代码可能看起来是正确的，但却存在细微的差错。它可能遵循了你现有的所有代码模式、成功编译、通过了测试，但仍在代码库的某个角落埋下了隐患。这就是为什么代码审查（Code review）如此至关重要。你需要建立起正确的流程，以维持一个高质量的代码库，并在问题触达生产环境之前截获它们。作为一名工程师，做好代码审查是你的本职工作。

在请其他人看我们的代码之前，我们应该先自己进行一次彻底的自审。在 Cursor 中，基于上一章的内容，我点击了“查找问题（Find issues）”，让智能体浏览我们刚刚生成的代码。 它确实发现了一个问题。它说，对于侧边栏中的模型列表，我们使用的是纯字符串，而不是本地化的翻译文本。因此，如果我们用另一种语言查看这些文档，它仍然会显示英文版本。我认为这确实是个 Bug，我同意这个判断。我点击“使用智能体修复（Fix with agent）”，它会在代码修改的具体行数上打上标记，我们可以直接让智能体去修复这个问题。在请团队里的任何人看 PR（Pull Request）之前，我会在本地完成所有的这些检查与平衡。

如果你一直让智能体编写了大量代码，那么审查和理解这一大段代码可能会很困难。所以我推荐的一个技巧是，（我这里直接使用语音模式）对智能体说：“把我现在的工作变更拆分成更小的、更具语义化的提交（Semantic commits），然后把这些变更推送上去，帮我创建一个新的 PR。” 我发现，当你把它拆分成更具语义化的提交记录时，对于人类审查者来说，逐步查阅提交记录并理解代码逻辑会容易得多，尤其是当他们有疑问的时候。事实证明，智能体在分离出模板化的样板代码与真正需要审查的业务代码方面，做得相当不错。接着，我们把代码推送到 GitHub 上生成 PR，开始让团队成员审查这些变更的流程。

现在我们在 GitHub 上打开了 PR。在让团队其他人审查之前，我喜欢做两件事： 第一件事是，我自己先在 PR 上审查一遍代码，这本来就是一个很好的最佳实践。 第二件事是，我使用 AI 代码审查工具再做一次复查，以确保我没有引入任何回归问题或逻辑错误。Cursor 可以使用一款名为 Bugbot 的产品来审查我的 PR 并发现错误进行评论。市面上有很多工具可以做到这一点，它们作为防止代码倒退的另一道防线非常有用。

好的，看起来 Bugbot 确实在我们的 Pull Request 中发现了两个问题。第一个被定性为中等严重程度的逻辑漏洞：这个信息图标被遮挡了。第二个问题是跨两个文件出现了重复的函数。像重复函数这种问题，绝对能在人工代码审查中被发现。能在请团队成员看这个 PR 之前就把它修复掉，真是太棒了。

Cursor 还可以自动修复这些问题。只需一行命令，你就可以直接在 PR 上进行评论并推送修复。如果需要，你甚至可以点击查看预览中的具体代码差异（Diff）。这超级有帮助。我一直用它来确保在让团队介入之前，我的代码拥有极高的质量。

防止代码回归的另一种方法是：要求智能体帮我们编写测试。 过去，构建覆盖率极其全面的测试需要做大量的工作，大多数团队只有在系统崩溃后才会添加测试，或者需要制定一套繁重的流程来确保达到一定比例的测试覆盖率。但我发现，智能体让编写测试变得更加平易近人。你不仅可以要求智能体为新功能编写测试，还可以让它自己验证这些测试是否正确。当你拥有这些高质量的测试用例后，你就能拥有更多的信心，放手让智能体更自主地工作、修改代码，而不必担心未来会引入回归问题。

回到 Cursor，我打算让智能体“为我们刚添加的独立模型页面的新功能编写一些测试，你可以使用我们现有的测试基础设施。”在这个例子中，我的应用程序里已经设置好了一些测试。但即使你还没有设置测试框架，智能体也非常擅长帮你从零开始。你可以让它配置单元测试、Playwright 集成测试，或者任何你喜欢的测试框架，它可以帮你着手构建高质量且健壮的系统。

我让 Cursor 里的智能体编写一些新测试，它去检查了我们应用中测试的配置方式，然后决定编写几个单元测试来防止未来的回归。现在，在我后续提交的每一个 PR 中，这都可以作为我们 CI（持续集成）流程的一部分，以确保我们没有破坏任何现有功能。

我确保代码保持高质量的另一种方式是：我使用智能体对应用程序的许多不同交互路径进行测试和模糊测试（Fuzz testing）。 在这个例子中，我要求智能体从头到尾测试一遍，确保文档页面中的一切都在正常工作：搜索、复制页面、分享反馈、页面间导航、切换主题……基本上就是测试所有的功能。它足足跑了近 45 分钟到一个小时，最后带回了非常高质量的测试产物、视频和截图，确保一切都按预期运作。所以，当我在开发新功能和进行代码审查时，我经常会启动几个智能体去替我彻头彻尾地测试一遍。

随着你越来越多地使用编程智能体，你的开发速度就会受限于系统中“最慢的那一环”。那一环往往是：等待测试套件运行完毕、在整个代码库中运行类型检查或 lint 检查，或者是 CI 管道中的其他步骤。如果你能在这些地方做出改进，它将在你或你的队友与智能体的每一次交互中得到回报。所以，你可以要求智能体去优化这些事情，比如加速你的测试套件、精简依赖树、优化 CI 管道、加快类型检查，或者只是单纯地减少构建时间。 过去，这些事情可能被排在了低优先级的待办事项里。但现在，既然智能体每天要运行这些命令几十上百次，优化它们所带来的时间节省绝对会产生巨大的复利。最棒的是，智能体可以直接替你完成这项工作。你可以要求智能体分析你的测试性能，或者审计依赖项并剥离未使用到的代码。因为这些都是范围非常明确、结果可验证的任务，所以智能体可以做得非常出色。我强烈推荐这样做，这能提升你整个团队的速度。

现在你已经掌握了如何发布新功能、在出错时进行调试，以及审查代码以确保高质量。最后一块拼图是：通过定制你的智能体，使其完美契合你的代码库，从而进一步加速你的工作流。

自定义智能体：规则（Rules）与技能（Skills）

讲解人： 编程智能体即使不做任何定制化也已经非常智能了。它们对软件工程有着深刻的理解，通常能做出正确的决策。然而，它们并不了解你的团队喜欢用什么规范编写软件，也不了解你们业务的具体背景。这就需要用到自定义功能了。

你可以对智能体进行定制，以帮助它们更高效地工作并产出更高质量的结果。Cursor 提供了两个层次的定制方案，这就好比你引导一名新队友入职一样： 一是**“规则（Rules）”，用于规定他们应该永远牢记的事情； 二是“技能（Skills）”**，用于赋予他们在必要时可以调用的专业知识。

规则（Rules） 是智能体在每次对话开始时都能看到的 Markdown 文件。你可以把它们看作是“永远包含在内”的指令，用于塑造智能体处理你代码的方式。一个好的 Rules 文件应该是简短的、具体的，并明确指出你希望智能体参考的代码库中的优秀范例。 我发现 Rules 最适合用来记录诸如：智能体需要知道的构建或测试命令、我希望智能体遵循的代码约定，或者是指向我们代码库中经典模式的指针。当我梳理出这些内容时，我会把它们放进一个 Rules 文件里，然后把它提交到 git 仓库中，这样我的整个团队都能从这份共享知识中受益。

你可能会有一种冲动，想要为所有事情都编写 Rule。但请你务必克制这种冲动。过多的规则会消耗不必要的上下文空间，而且老实说，可能会让智能体感到困惑。因此，我建议你的规则要保持精简且高质量。这是一个你和你的团队不断更新的共享库，它们会包含在每一次对话中。所以，如果有些东西你只是偶尔需要用到，你应该把它放进“技能（Skill）”中。

技能（Skills） 通过引入专业知识和工作流，扩展了智能体的能力。与永远加载的 Rules 不同，Skills 是动态加载的，由智能体来决定什么时候使用它们。在最基本的形式下，Skills 就是一个 Markdown 文件，但它们也可以包含自定义资产，甚至是可以让智能体执行的脚本。 你还可以像运行工作流一样运行 Skills。例如，我有一个 /pr 技能。当调用时，它会指示智能体：为我提交代码（Commit）、推送到分支（Push），并创建一个 Pull Request。这真的非常非常有帮助。

我们的社区已经创建了许多非常有用的规则、技能以及其他扩展 Cursor 能力的插件。我们构建了一个插件系统（Plug-in system），让你可以轻松安装所有的这些功能。所以，我们目前讨论过的所有东西——规则、技能、MCP 服务器、子智能体——都可以很好地打包在一起，并通过我们的市场分享给你的团队或更广泛的 Cursor 社区。你可以直接在我们的应用内或网页端浏览并安装新插件。

我关于定制智能体的最后一个建议是：你可以要求智能体使用终端里安装的几乎任何命令行工具（CLI Tool）。 比如 GitHub CLI，或者是 AWS、Kubernetes、Docker 的命令行。智能体非常擅长使用这些工具，你只需直接要求它们使用即可。 我发现这在调试问题时特别有用。比如，我不用切出去打开 GitHub 网页，只需直接对它说：“嘿，去查一下为什么这个 PR 的 CI 失败了。”它就会使用 GitHub CLI 调取信息。这实在太方便了。

好了，现在你已经用规则、技能或者你安装的插件对智能体进行了全副武装。在最后一章中，我们将把我们在课程中学到的所有知识融会贯通。

实战演练与总结

讲解人： 恭喜你！你已经掌握了如何与编程智能体协同工作。你现在知道如何使用智能体来理解代码库、快速创建功能、搜索和排查 Bug、审查代码，以及根据自身需求定制智能体。现在，我想把我们学到的所有东西串联起来。

让我们想象一下：你刚刚加入了一个负责运营电商平台的团队。在你的第一周，你接到了一项任务——在结账流程中添加“折扣码（Discount codes）”功能。你对这个代码库还很不熟悉，因为你刚入职。所以，在我们写任何代码之前，你需要做的第一件事就是理解代码库。

因此，你的提示词可能会这样写：“我需要在我们的结账流程中添加折扣码功能。但在我做任何修改之前，你能给我讲解一下现有的结账流程是怎样的吗？涉及哪些服务？你能给我展示一下数据流向吗？” 你可以阅读它的输出，然后提出一些跟进问题来填补知识盲区：“价格计算的逻辑是怎样的？我们具体在哪里计算订单总额的？” 如果你观察它的输出日志，你会发现智能体结合了我们在课程前面提到的 grep 精确匹配和语义搜索，追踪了代码库的特定部分，以帮助你理解它的工作原理。

现在你理解了代码库，我们就可以创建一个计划并开始开发该功能。我们按下 Shift + Tab 切入“计划模式（Plan mode）”，审视它生成的计划。这时候我们需要进行审查。我们剔除掉那些对第一次迭代来说过于庞大复杂的步骤，将重点放在我们试图实现的核心逻辑上——即应用折扣码计算折扣金额，并在订单摘要中显示。准备就绪后，我们点击“构建”，创建出该功能的第一个版本。

功能初步完成后，我们发现有一个测试总是失败：当你输入一组不同的折扣码时，根据输入的先后顺序，它会得出不同的计算结果。这是一个相当棘手的 Bug。这时候，我们就可以切换到“调试模式（Debug mode）”，让智能体去调查根本原因。它将运用我们在“寻找和修复 Bug”那一章中学到的所有调试原则，来帮助我们找到根本原因并完成修复。

在将代码推送到 GitHub 并打开 PR 之后，我可以使用 AI 代码审查工具进行新一轮的代码 Review，在合并代码之前，确保没有出现任何新的倒退。

现在，代码已经合并，功能已经完成。在这个过程中，我们学到了一些经验，我们希望能将其反哺到我们的共享知识库中，让整个团队受益。于是，我们回到 Rules 文件中，将在这次任务中学到的特定注意事项添加进去，并提交到 git 仓库。这样一来，将来如果团队里有其他人需要处理折扣码相关的逻辑，他们就能从这份共享知识中直接受益。

希望这个完整的实战例子能对你有所帮助，它涵盖了我们在课程中讨论过的所有核心内容。但说实话，我能给你的最好建议是：把你今天学到的东西付诸实践，去真正地构建点什么。

这些工具和模型进化得如此之快，以至于所有具体的细节都会随着时间而改变。但是，你正在学习的这项核心技能——“如何与编程智能体进行协同”，正在迅速成为软件工程领域最重要的一环。只有不断突破这些编程智能体能力的边界，你才能在最新工具和模型不断演进的过程中获得最大的收益。

祝你好运，保持好奇心，继续创造！
