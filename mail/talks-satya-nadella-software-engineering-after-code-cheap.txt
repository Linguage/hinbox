<p>代码生成成本下降，软件工程的重心正在转向需求表达、系统设计与验证。微软 CEO Satya Nadella 与 Gergely Orosz 从开源、VS Code 和编程智能体聊起，讨论软件工厂如何改造既有产品，企业为什么要掌握自己的 AI 基础设施，以及工程师怎样面对岗位、团队和学习方式的变化。</p>
<h2>概述</h2>
<p>Nadella 把“软件工厂”描述为一套围绕规格说明、智能体、小任务和验证循环组织起来的生产方式。工程师不再只负责写出代码，还要设计流程，让生成结果经得起测试，并把生产环境中的问题反馈到修复环节。对 Windows 这样的成熟产品，这不是推倒重来，而是逐步改造源码管理、构建、CI/CD 和运维。</p>
<p>这场变化也在改写企业的技术边界。Nadella 主张将模型、运行框架、上下文和记忆分开，让公司能够替换供应商、保存自身知识，并用内部评估检验真正重要的结果。他同时强调，模型能力提升不等于可靠性或对齐问题已经解决；权限与智能必须分离，智能体需要独立的监督和防护。</p>
<p>谈到职业前景，他没有承诺工作方式保持不变。团队规模、岗位职责和人员配置都会调整，但深厚的工程经验仍有价值。比起只讨论行业变化，他更看重亲手使用新工具，在实际团队中重新学习。本地模型、云端模型与决策引擎的组合，则为工程师打开了另一批需要构建的新系统。</p>

<h2>开场</h2>
<p><strong>Satya Nadella：</strong> 当生成代码变得便宜，验证就成了难事。我觉得自己得重新学习，因为我没有在如今这种主要把代码当作产出的团队里工作过。不过，把代码当作产出也有特定的操作顺序，并不是说每个人都可以随意生成一大堆代码。</p>
<p><strong>Gergely Orosz：</strong> 2025 年，Claude Code 突然出现了。我第一次觉得，你们没有立刻拿出应对办法。</p>
<p><strong>Satya Nadella：</strong> 当模型能力出现非线性跃升时，产品形态就必须改变。从这个意义上说，构建 AI 优先的产品容不得迟疑。大约六个月间，IDE 就逐渐淡出了中心位置。</p>
<p><strong>Gergely Orosz：</strong> 我在想，开源运动与现在的开放模型之间，有没有相似之处？</p>
<p><strong>Satya Nadella：</strong> 先放下这样一个想法：会有一个前沿模型，掌握全世界的知识。如果你不相信这个说法，那么从某种意义上说，世界上有多少家公司，就应该有多少个前沿模型。因为归根结底……</p>
<p><strong>Gergely Orosz：</strong> 当生成代码变得非常便宜，软件工程意味着什么？今天的嘉宾是微软 CEO Satya Nadella。他是少数以软件工程师身份开始职业生涯的大型科技公司 CEO 之一。今天我们会聊，他所说的“软件工厂”是什么，微软内部的软件工厂如今是什么样子；OpenAI 模型、本地模型，以及“不按用量计费的智能”；开发者面对 AI 时真切的焦虑；微软的自愿离职方案；还有初级岗位招聘放缓为何可能只是暂时现象，等等。</p>
<p>如果你想知道，在 AI 时代怎样才能成为出色的软件开发者，也想了解 Satya 用什么思考框架理解这一连串变化，这一期就是为你准备的。</p>
<p>本期节目由 turbopuffer 赞助。这是一款基于对象存储构建的混合搜索引擎，扩展能力强、速度快、价格低，Anthropic、Linear、Ramp 等前沿公司都在使用。许多改用 turbopuffer 的公司，将搜索账单减少了一半甚至更多，同时获得了快得多的搜索结果。详情可访问 turbopuffer.com/pragmatic。Satya，欢迎来到节目。</p>
<p><strong>Satya Nadella：</strong> 非常感谢你邀请我，Gergely。</p>
<p><strong>Gergely Orosz：</strong> 很高兴来到这里。不知道你知不知道，我以前也在微软做开发。</p>
<p><strong>Satya Nadella：</strong> 你是在这里，还是在别的办公室？</p>
<p><strong>Gergely Orosz：</strong> 我在伦敦。这是我第一次来到总部。那大概是十二年前的事了，我想先回到那个时候。2014 年你出任 CEO 时，我还在微软。我印象很深，当时微软对开源的态度正在转变；你上任之后，微软开始拥抱开源。后来有了 Visual Studio Code，微软收购了 GitHub，还全面转向 Git，此前我们用的是 TFS。</p>
<p><a id="talk-section-2"></a></p>
<h2>微软为什么转向开源</h2>
<p><strong>Gergely Orosz：</strong> TypeScript 也开源了。我想回头问问，为什么会这样？当时大家都很惊讶，我在微软以外的朋友很惊讶，连我自己也很惊讶。微软为什么全面拥抱开源？</p>
<p><strong>Satya Nadella：</strong> 有时候，一种叙事或者印象一旦形成，要改变它就得花很大力气。实际上，如果你看看代码提交，甚至在我成为 CEO 之前，微软就已经为 Linux 做了大量贡献，而且认真投入了这件事。</p>
<p>我们真正希望确保的一点，是让公司内部和外界都明白：微软致力于开源。不论是把 SQL Server 这样的工作负载带到 Linux 上，为 Linux 作贡献，还是将 TypeScript 等项目开源，都是其中的一部分。当然，成为 GitHub 的管理者，也让我们站到了这个生态的中心。</p>
<p>我们想通过真正对社区有益的行动，赢得开源社区的信任。有件事很有意思，我一直在想：如果认真算一算，哪些公司使用了开源，哪些人为开源作了贡献，我想微软即便不是排在第一，也一定在最前列。有些从开源中受益最大的公司，实际上几乎没作什么贡献。你当然不能抱怨，但世界往往就是这样运转的：人们一直在叙事与事实之间拉扯。</p>
<p><a id="talk-section-3"></a></p>
<h2>VS Code：不只是开源，更是在公开中构建</h2>
<p><strong>Gergely Orosz：</strong> 确实，叙事与事实是两回事。我想，20 世纪 90 年代 Windows 留下的印象，也影响了大家怎么看微软。不过在我的记忆里，对开发者社区影响最大的，不只是开源这件事，而是 Visual Studio Code。</p>
<p><strong>Satya Nadella：</strong> 是的。</p>
<p><strong>Gergely Orosz：</strong> 它当然是开源的，但它还是免费的。我以前做开发时使用 Visual Studio，它非常出色，Visual Studio 2003 至今仍是一款了不起的软件。后来，微软决定把免费的、开源版本的开发工具带给更广泛的开发者。五年、十年过去，它几乎无处不在，人人都在用。这是有意为之的吗？</p>
<p><strong>Satya Nadella：</strong> 是的。Erich Gamma 和当时团队里的其他人，就是有意识地这么做，连开发过程也是与社区一起进行的。这也是我第一次真正接触到如今人们所说的“公开构建”。我们第一次理解了公开构建意味着什么：让社区围绕产品聚集起来，建立那种反馈循环。</p>
<p>我记得当时还专门和 Amanda Silver 等人交流，了解那个团队如何工作。比如，在这样的团队里做产品经理意味着什么？他们每天都查看社区反馈，并以此推动开发，而不是只接受自上而下的指令。不是“我听副总裁的”，而是“我听社区的”。所以，公开构建带来的文化变化远不止开源，很多变化是根本性的。有时我会想，我们从那段经历中学到了很多好东西，但本该学得更深，并把这些经验传播到更广的范围。</p>
<p><a id="talk-section-4"></a></p>
<h2>从 Copilot、Cursor 到 Claude Code</h2>
<p><strong>Gergely Orosz：</strong> 说到学得更深、更广，当时 VS Code 已经到处都是，GitHub 也发展得很好。再看 Copilot，直到今天回头想，我都惊讶于微软那么早就看到了 AI 的潜力。那还是 ChatGPT 3.5 出现之前，我想大概是 GPT-3 那一代，Copilot 用起来已经像魔法一样。至少一年里，它几乎没有真正的竞争对手，直到 2023 年 Cursor 出现。</p>
<p>Cursor 出现后，我仍然觉得你们对 VS Code 的布局很聪明。Cursor 基于 VS Code，有熟悉的界面。GitHub Copilot 与 Cursor 并行竞争，彼此追赶。接着，2025 年 Claude Code 突然出现了。对我自己、对初创公司乃至大型科技公司里的人来说，不过六个月，大家似乎就把 IDE 忘了。</p>
<p>这仍让我非常意外。开发者工具一直流淌在微软的血液里。你怎么看，你们为什么没预见到这次突变？我第一次觉得，你们没有立即拿出应对办法。</p>
<p><strong>Satya Nadella：</strong> 这个问题很值得拆开来看。就像你说的，我们很早就开始做，那是在 GPT-4 之前。当时，仅仅是代码补全，就已经让人觉得不可思议。GitHub Copilot 起初做的就是这个。我们做 IntelliSense 很多年，也取得了不错的进展，然后突然发现，原来这种方式真能奏效。</p>
<p>坦率地说，最初很多人怀疑它到底能不能行，但它开始奏效了。看到那一幕，我自己对缩放定律的信心也得到了根本性的巩固。我觉得我们把那款产品做得不错。不过，围绕模型构建产品有一个关键：模型能力一旦出现非线性跃升，产品形态就必须迅速改变。</p>
<p>这正是 AI 优先的产品开发容不得迟疑的地方。你得围绕某个模型来构建整个产品，同时随时准备好，迎接下一个模型涌现的新能力，并据此重新组织产品。不要迷恋自己已经做出来的东西。后来，智能体编程、让模型执行任务开始变得可行。它不再只是补全代码，而是可以接手一些小任务。Cursor 在这里做得很好：它基于 IDE 做了分支，但真正出色的是智能体模式。</p>
<p>于是，我们也追上了智能体模式，因为在 OpenAI 模型之上，我们也可以实现这些能力。随后真正冲击我们的，是 Anthropic 在模型上做出的出色工作。它让 CLI 真正成为一种可行的产品形态，你可以把整个任务交给它处理。代码实际上从输入变成了输出。</p>
<p>我觉得，这就是大约六个月里发生的转变。就像你说的，IDE 逐渐淡出了中心位置，我们对代码的理解发生了变化。如果看新的 IDE，重点更多是怎样输入规格说明、Markdown，以及围绕软件工厂的各种材料。</p>
<p>有趣的是，我们现在正好在谈这个话题。我最近的一个想法是，有了这些决策引擎模型，我又回到了 IDE。它们有点像函数，是嵌入软件内部的智能函数。因此，当我们考虑怎样以更节省 Token 的方式嵌入智能时，IDE 甚至可能迎来重生。我不认为这是一条不可逆的单向转变。我们现在需要多种产品形态，让它们分别发挥模型的能力。</p>
<p><a id="talk-section-5"></a></p>
<h2>决策引擎：智能时代的新基础组件</h2>
<p><strong>Gergely Orosz：</strong> 我正想问这个。你提到决策模型，也说自己对此很兴奋。最近我们分别在不同场合和 Diogo 聊过。你对决策模型的看法有什么变化？对于 LLM 的局限，特别是在编程任务、写代码和可靠地构建软件方面，你又怎么看？</p>
<p><strong>Satya Nadella：</strong> 对，这就是问题所在。LLM 非常出色。我们都是工程师，可以直接切入重点，谈谈它怎样帮助我们构建软件工厂，这里面有很多东西值得展开。但我喜欢决策引擎，是因为它是一种新的基础组件。Diogo 在谈这个，我们自己的决策引擎团队、Achint 等人也在谈。</p>
<p>我喜欢这个方向，因为它有点像 Excel 宏。宏曾经给电子表格带来的变化，也可能发生在代码中：把智能作为一种基础组件嵌进去。比如，我看到 Xbox 团队构建了一套管理社区反馈的系统。社区反馈进来，系统据此做出一组决策，这是一个很典型的流程。我不想为这件事反复让 LLM 生成代码，只想让系统能够做决策。那么，把这种组件嵌进去就更合适。</p>
<p>它具有一个分布，你可以调用它，不需要一遍遍重新生成，而且很省 Token。所以，我认为软件工程在这样的地方依然充满活力，只是形态在变。Diogo 的想法有一点我特别喜欢：他希望把它变得像数据库一样平常。</p>
<p>在我成长的年代，开发工具链中，除了编译器、Lex、Yacc 之类，我最喜欢的产品就是关系数据库。它让我们能够可靠地存储和查询信息，于是各种各样的应用都成为可能。我想，在智能时代，决策引擎也会发挥同样的作用。</p>
<p><strong>Gergely Orosz：</strong> 实际上，数据库就是核心。我们常说软件公司的本质是业务逻辑，但再往下看，这些逻辑往往就在数据库里。过去，很多业务逻辑直接写在数据库的存储事务等机制中。所以我在想……</p>
<p><strong>Satya Nadella：</strong> 这个比喻很好。这就像智能时代的存储过程。</p>
<p><strong>Gergely Orosz：</strong> 对。我在想，这是不是一种类比，或者一种希望？因为我觉得，我们还没有找到合适的基础组件。我们知道 LLM 能生成代码，也可以让它做一些不那么可靠的事情，但仍然缺少这些基础组件，对吗？</p>
<p><a id="talk-section-6"></a></p>
<h2>代码生成便宜以后，难的是验证</h2>
<p><strong>Satya Nadella：</strong> 对，所以我很兴奋。这只是个开始。另一个挑战是，我们不妨回到软件工厂：看看如今 Cowork 或 GitHub Copilot runtime 是怎样构建的，有人已经写过相关博客，很值得看。当代码生成变得便宜，验证就变难了。</p>
<p>有时候我会想，真希望能参加 Mark 和 Scott Hanselman 他们组织的那种带教项目，不管他们具体叫什么。因为我确实觉得自己需要学习，我没有在如今这种以代码为输出的团队里工作过。但代码作为输出，也有特定的操作顺序，并不是说大家都可以随意生成各种代码。验证体系要怎么搭？怎样把每一次失败转化成测试用例，再确保这些测试本身真的得到了验证？</p>
<p>在管理复杂软件项目方面，大家正在积累大量新的实践经验。比如他们那次 Rust 迁移，就曾经非常棘手，还不得不回退。这种工作方式既带来了巨大的优势，也带来了一些严重的缺点。因此，就像你刚才说的，再增加决策引擎这样的基础组件，是件好事。</p>
<p><strong>Gergely Orosz：</strong> 作为这样一家公司的 CEO，你能看到各种事情，得到各种信息。但如果可以，你还是想回到某个团队亲自工作？</p>
<p><strong>Satya Nadella：</strong> 当然。如果我能再回到一个团队中，那就是我梦想中的下一份工作。有意思的是，我还想给 Scott 和 Mark 发封邮件，告诉他们，他们在微软内部创建的这个带教项目做得非常出色。我想，他们还和卡内基梅隆大学有合作。</p>
<p>我很在意的一点是，能不能让职业生涯刚起步的人进入这样的团队，沿着学习曲线成长。以前，大家来微软实习，会去看 Dave Cutler 的代码，看看 malloc 是怎么实现的。现在，能替代这种学习经历的新形式是什么？这正是我们必须探索的。所以，是的，我希望有一天还能再这样做一次。</p>
<p><strong>Gergely Orosz：</strong> 我现在开始理解，为什么那么多 CTO、工程副总裁、高级副总裁愿意降一级，进入小团队，亲自学习怎样用这些新工具构建产品。变化确实很多。</p>
<p><strong>Satya Nadella：</strong> 完全是这样。整个组织背景都在变。在多个方面都发生巨变的时候，更深入地亲手参与非常重要。而且不仅是技术：贴近客户、公开构建，成功的产品与技术所涉及的各个方面，都有很多东西要学。所以，机会很多。</p>
<p><a id="talk-section-7"></a></p>
<h2>软件工厂究竟是什么</h2>
<p><strong>Gergely Orosz：</strong> 我们已经说了好几次“软件工厂”，不妨认真聊聊。我觉得这个词有些模糊，但越来越常见。对你来说，它意味着什么？</p>
<p><strong>Satya Nadella：</strong> 我也还在理解它。我在观察今天的软件团队究竟做什么，从中寻找规律。我建议观众看看 Bas 写的博客。实际上，有两篇很好的文章，分别来自 Cowork 团队和 GitHub Copilot 团队。GitHub 那篇讲的是，一名开发者能够独自维护整个 runtime，而且还做了迁移。我忘了，应该是从 Python 迁到了 Rust。</p>
<p><strong>Gergely Orosz：</strong> 总归是迁到 Rust。</p>
<p><strong>Satya Nadella：</strong> 对，迁到 Rust。不管怎样，那是一个很好的案例，展示了一名开发者能达到怎样的生产力，以及以这种方式进行维护意味着什么。另一个案例则是一支团队，大概九名、十二名工程师，具体数字我记不清。整个团队、整个软件工厂居然只有那么多人，确实惊人。他们也写了很好的博客，其中有很多地方我非常喜欢。如果可以，我真想直接加入那个团队亲身学习，而不仅仅是读博客，或者和 Bas 及团队聊天。</p>
<p>据我理解，根本的变化是：代码从输入变成了输出。那么，规格说明和意图就更重要了。它们过去当然也很重要，设计文档一直很重要，但现在尤为关键。</p>
<p>还有一件让我觉得有意思的事。我和一个刚进入职场、加入这种团队的年轻人聊过，现在熟悉一个代码库反而容易多了。因为经营软件工厂的时候，一切都要写成文档。</p>
<p><strong>Gergely Orosz：</strong> 对。</p>
<p><strong>Satya Nadella：</strong> 而且你还可以向它提问。</p>
<p><strong>Gergely Orosz：</strong> 就像一个耐心的导师、入职伙伴。</p>
<p><strong>Satya Nadella：</strong> 所以，熟悉代码库比过去容易得多，不用到处寻找只存在于别人脑子里的经验。另一个我正在学习的方面，就是验证。你应该怎样开展智能体编程？把一些小任务交给它，然后确认它确实完成了。怎样安排独立评审？这里面，使用另一个模型家族很有价值。</p>
<p>我一直担心的是，如果只用一个模型家族，而它又存在对齐问题，你该怎样通过评审，避免把这个模型家族的问题变成自己的问题？</p>
<p>总之，我看到一种全新的构建方式正在出现。这是新的软件工程，它仍然需要软件工程师，只是交互的层级变了。也许这就是我喜欢编译器那个类比的原因：从自己写汇编，到发现有了编译器，突然可以把意图变成代码，而不必再懂汇编。现在也有一点类似。</p>
<p>抽象层级提高了，但团队的工作方式、产品的构建方式也都变了。还有一点让我很兴奋，就是把生产环境的跟踪数据送回来。我们一直有可观测性，但现在机会更多了。当大家说起 RSI，也就是递归自我改进时，这就是我理解的 RSI：利用生产日志，找到修复方式，再验证修复。</p>
<p>这个可验证的循环非常好。你可以部署修复，让它通过所有测试，一路推进到上线。这确实很有帮助。这些团队学到了很多，经验也正在微软内部传播。看到它成为团队组织工作的新方式，很令人高兴。</p>
<p>我还喜欢 Azure 网络团队的例子。过去，这是我最爱讲的故事。微软为了全球网络，要管理世界各地大约五百家光纤运营商。网络是实体资产，总会有这样那样的问题。管理这些事，时髦一点的叫法是 DevOps，但实际工作往往就是处理邮件，以及各种临时拼凑的流程。</p>
<p>于是他们构建了一整套智能体系统来处理运维，而且把运维连接到了代码仓库。现在不再只是单独考虑仓库或代码库，也把围绕它们的运维纳入其中。你会发现，技术团队的工作正在变成：构建一座结合软件与运维的工厂，让它完成工作，而不是直接去做每件事。当然，团队仍然在工作，只是工作内容有所不同。</p>
<p><a id="talk-section-8"></a></p>
<h2>已有产品如何引入 AI</h2>
<p><strong>Gergely Orosz：</strong> 在 AI 实验室里，这种做法很常见，他们也愿意分享：软件工程师的工作正在变成，让智能体和循环运作得更好。也就是你刚才说的。但回到微软这种公司的实际情况，有些团队可以实验，构建新的工厂；有些是平台团队，可能有余力，可以做各种探索。但你们也有产品团队，有实际的产品和真正的客户。</p>
<p>我看到很多拥有真实业务的公司正在为此苦恼。他们看着 AI 实验室展示那些令人向往的东西，或者听着你刚才说的话，可能会想：等一下，我不能把一切放下，跑去建一座工厂，那现有产品怎么办？你怎么考虑这种平衡？尤其在微软内部，你会怎么对工程师说？如果他们维护的是一个优秀、盈利、客户依赖的产品，工作应该怎样改变？</p>
<p><strong>Satya Nadella：</strong> 这是个很好的问题。首先，我们没有权利去做那些不能为客户增添价值的事。应该从这里开始。我们也犯过错误，仅仅因为一些 AI 项目看起来很酷，就去做了各种尝试。</p>
<p><strong>Gergely Orosz：</strong> 我想所有人都干过。</p>
<p><strong>Satya Nadella：</strong> 所有人都干过，我自己也没少做。希望我们从中学到了东西，以后会更好。不过，再看一个实际例子：Windows 的 CVE。今天，AI 模型已经能够找出严重漏洞，我们就需要把它们修好，因此出现了一条新的处理流水线。Windows 团队正在把崩溃跟踪一路连接到修复，本质上是在构建一种新的软件工厂。</p>
<p>但这是在已有系统上改造。Windows 的构建系统，仍然是原来的 Windows 构建系统。在这些既有项目中，最困难的部分往往就是构建，以及 CI/CD。再看 GitHub 底层发生的变化：突然之间，一大批编程智能体开始在 GitHub 上工作，规模猛增。</p>
<p><strong>Gergely Orosz：</strong> 到了超出人类工作量的程度。</p>
<p><strong>Satya Nadella：</strong> 对。所以，我们必须从根本上调整整个 Git 协议、存储系统。我们在每一部分都投入工作，确保自己能适应已有系统，而不只是从零开始。全新的项目当然会一直做，但现实世界主要是既有系统。改造这些系统，需要一步一步加固，重新思考核心基础组件，从源码管理到构建，再到能在既有项目中运行的 CI/CD。</p>
<p>这些都需要时间、投入和思考。操作的次序非常重要。我喜欢这次转型的一点是：它不是“这里来了一个闪亮的新东西，由某支新团队去做，其他人继续活在旧世界”。全公司的每个人，都可以用新的工具链和工作方式，处理自己面前的挑战，不管做的是 Windows、SQL Server，还是云原生服务。我们正在看到这种变化。</p>
<p><a id="talk-section-9"></a></p>
<h2>采用 AI 与采用 React 有何不同</h2>
<p><strong>Gergely Orosz：</strong> 说句公道话，这听起来和过去的做法并没有那么不同。比如 React 这种新前端技术出现时，大家都想用。但没有谁能得到许可，把手头工作全部停下，直接迁移到 React。通常是构建新产品、增加新功能时，逐渐把它加入进去，和原有系统混用。所以，采用方式可能并没那么不同。这一次真正不同的是什么？</p>
<p><strong>Satya Nadella：</strong> 问得好。有时候我也会想，这些情形我以前见过。不过，我确实觉得这次有一点不同：我们做事的基本规律、操作顺序、抽象层级都变了。</p>
<p>我开始工作时，正赶上一轮转变。大学里，我主要用的是 VAX，配一台 VT 终端。</p>
<p><strong>Gergely Orosz：</strong> 也就是大型机？</p>
<p><strong>Satya Nadella：</strong> 或者说小型机，是 VMS 系统。后来，我在 Sun 工作了两年，用工作站，再后来到了微软。之后，这个世界大体稳定下来：我们主要在 IDE 里写代码。整个职业生涯中，这件事并没有真正改变。</p>
<p>当然，新技术一直在出现，但主要是新的框架、新的 runtime，基本概念并没有剧烈增加。即便移动计算，也像一台微型 PC，配上新的用户界面和新的框架。</p>
<p>而这一次，所有东西都需要重新思考：runtime 是什么？框架是什么？IDE 是什么？</p>
<p><strong>Gergely Orosz：</strong> 整个技术栈是什么？</p>
<p><strong>Satya Nadella：</strong> 对，每一个部分都在变。思考方式的变化更大。而且别忘了，随时可能有一个新模型出现。不论是新的前沿模型，还是决策引擎这样的新东西，都可能让这一切再变一次。因此，我们得随时准备好，整个局面都可能彻底转变。</p>
<p>至少有两件事值得记住。一方面，向过去学习：我们个人、公司、团队在什么时候最擅长应对变化？这始终很重要。另一方面，也要保持开放，承认这一次可能确实不同。</p>
<p><a id="talk-section-10"></a></p>
<h2>软件工程师的角色如何改变</h2>
<p><strong>Gergely Orosz：</strong> 对软件工程师来说，还有一个特别大的变化。微软的大部分员工，可能都是软件工程师，或者从事与代码很接近的工作。过去，我们大部分时间都在写代码，大学学习和之前工作中的很多努力，也都是为了把这件事做好。</p>
<p>现在，这部分工作突然消失了。包括以前的我在内，很多人都很难接受，因为过去的技术变化从没这样发生过，通常只是增加一种新工具。那些非常优秀、花了几十年磨炼编码能力的工程师，要怎么理解这件事？你和微软内部或外部的人交流时，看到了什么？把代码写好，毕竟很难。</p>
<p><strong>Satya Nadella：</strong> 是的。我观察到的情况是，那些过去非常优秀、如今在新生产方式下也很高产的软件工程师，仍然需要同样的能力。改变的是操作顺序和工具链。</p>
<p>因此，我不认为这是在贬低专业能力，而是要把这些能力用好，让新的杠杆放大它们。这要求你改变工作方式，而不是认为软件工程已经不重要了。我们正在学习怎样评价新的东西；在理解新事物的价值时，可能也会重新认识旧能力的价值。</p>
<p>当然，会有原生适应这套工具链的人。很有意思，上一次 GitHub Universe 上，我去见了一群大学生。那是第一批在 AI 时代成长起来的大学毕业生。他们上大学时，GitHub Copilot 已经出现了。他们根本没经历过没有 Copilot 的 IDE 世界。这让我很震撼。</p>
<p>但我在微软也看到了，凡是在某个方面拥有深厚经验、同时保持好奇心并愿意学习新工作方式的人，都能在这里发展得很好。我希望确保公司能为大家创造这种机会。毕竟，对个人而言，职业生涯能够带来怎样的经济回报很重要。因此，我们要让员工既能发挥现有技能的价值，也能掌握市场认可的新技能。</p>
<p><a id="talk-section-11"></a></p>
<h2>微软为什么推出自愿离职方案</h2>
<p><strong>Gergely Orosz：</strong> 我很喜欢你看待这个问题的方式，也喜欢你刚才说的，初级工程师、新毕业生和刚入行的人能够作出贡献、快速进入状态。不过开发者圈里还有一个大家都在讨论的问题，我就直说了：微软为什么推出自愿退休方案？这意味着什么？大家担心，这会不会是 AI 提高团队效率后，进一步裁员的前奏？我想直接问你。</p>
<p>微软以前从没做过这样的事，这是我特别注意到的一点，另一点是它属于自愿选择。你和公司是怎样形成这个想法的？</p>
<p><strong>Satya Nadella：</strong> 这是一个非常重要的问题。我们进行了很多讨论，觉得应该承认两点，或者说三点。首先，未来仍然有大量机会，只是机会的形态，可能与过去不同。就算只谈我们刚才说的软件工程，也是如此。应该从这里出发。</p>
<p>接下来，就是在公司内部创造更多这样的新机会。不论你在做 Windows，还是 AI 训练，都应该能够学到新技能，这些技能既在微软内部有价值，也在市场上有价值。</p>
<p>但是，新工作呈现出的形态，将与以前不同：团队、团队规模、工作流程都会改变。不是说我们不希望微软这二十万名员工都发展得好，甚至继续增加员工。只是这二十万人，以及未来加入的人，需要以不同的方式组织起来。</p>
<p>再看微软内部的经济回报：系统工程师、基础设施人才的薪酬涨得很高，负责模型训练的研究人员也是如此。一些专业能力竞争非常激烈，市场给出的价值很高。因此，我们希望给大家更多自主权。这个自愿方案，主要就是为了让每个人更有能力选择一个符合自己长期职业回报的位置。</p>
<p>我做 CEO 很久了，在那之前也做过高管，但归根结底，我是从一名个人贡献者一步步走到今天的。所以，我常常会从自己当年做工程师、团队负责人，或者管理多个负责人的角度，考虑公司应该怎样创造机会。我不想困在一个没有转型的团队里。</p>
<p>即便是在微软，我也不能坐在这里说，每个部门都已经理解了变化，并且都以相同速度转型。如果你在某个团队里觉得职业发展停滞，你可以用脚投票。我不希望你离开公司，因为坦率地说，微软内部本身就有很多地方可以去。我们也希望创造这样的机会。</p>
<p>因此，我们想在这个动荡时期，给员工更多自主权。我也希望能坐在这里说，一切都不会变，但我不能这样说。我希望尽可能透明地谈变化，也希望自己真正下功夫，在公司里创造各种机会，让员工能够在这里实现职业成长。</p>
<p><strong>Gergely Orosz：</strong> 你说得很周全，也很体贴。如果用更直白的话说，我理解的是：世界已经发生了巨大变化，比如 Claude Code 带来的变化就很快。团队如果在这种时候打瞌睡，是承受不起的。你必须跟上，承认软件工程师的工作、工具都会改变。</p>
<p>你可以选择投入其中，找到热情，看到机会，以及构建软件工厂、新工作流程时的各种工程挑战；也可以决定，自己不想这样做。在多数公司里，后一种情况会让人进退两难，但你们给了员工一个选择：如果想退出，现在可以离开，彼此不必心存芥蒂。</p>
<p><a id="talk-section-12"></a></p>
<h2>面对 AI 焦虑，岗位也要重新组织</h2>
<p><strong>Satya Nadella：</strong> 我想是这样。而且归根结底，有一点我非常在意：我们制造了巨大的焦虑，让人觉得自己失去了对命运的掌控。</p>
<p>大家谈论 AI 革命的方式，常常是“奇点已经来了”“未来也许只剩一家公司”“以后不会再有工作”。这些说法，连那些愿意改变的人都会感到焦虑和压力。</p>
<p>微软有二十万名员工，我知道我们每个人的工作都会发生很多变化。想想看，微软增长最快的岗位之一，是 FDE，也就是前沿部署工程师。</p>
<p><strong>Gergely Orosz：</strong> 微软也是这样。整个行业现在都这样。</p>
<p><strong>Satya Nadella：</strong> 对，整个行业都是。比如，我们有非常重要的客户经理；在他们旁边，还有面向客户的技术人员，以及我们称为 CSU 的客户成功团队；此外，还有技术支持人员和 FDE 团队。</p>
<p>这些人都需要参与彻底的转变。某种意义上说，他们应该和软件工程师参加同样的带教项目，因为每个人都能参与构建。我知道 LinkedIn 内部也做过调整，把一些岗位合并，称为“全栈构建者”。这些变化中存在机会。</p>
<p>但你必须真正做那些困难的工作：调整组织结构，把人安排到合适的位置，给他们机会和薪酬支持，学会评价他们在新岗位上的生产力与出色表现。这是每一家成熟公司都必须面对的艰苦工作。</p>
<p>我们当然应该欢迎新事物，竞争市场本来就是这样运转的。微软已经是一家五十一岁的公司，我们可以坦然接受自己的身份。我们希望好好服务客户，让员工在这里做好工作，获得出色的职业回报，并继续践行赋能个人和组织的使命。</p>
<p><a id="talk-section-13"></a></p>
<h2>初级工程师招聘</h2>
<p><strong>Gergely Orosz：</strong> 从另一面说，我想请你明确一下。刚才说到应届毕业生，微软还在招应届生、招初级工程师，也还在投入资源培养他们，对吧？很多其他公司和创业团队有个顾虑，已经放慢甚至停止招聘了。他们觉得，用 AI 最有效率的，还是我们前面说的那些有专业积累、能把 AI 用起来的人，所以很犹豫要不要招刚入行的人。</p>
<p><strong>Satya Nadella：</strong> 这个问题问得好。我们正经历很多变化，所以我觉得，有些趋势得拉长时间观察，不能只看一年。眼下第一件事，是先把内部人员调整到合适的位置。哪怕在同一个团队里，也得先把人配对了。</p>
<p>之后才谈得上，这个团队该再招一个有行业经验的人，还是招一个刚毕业的人？所以我想，现在招人变慢，可能只是因为大家要先把这些所谓的新「软件工程工厂」搭起来。等新配置跑顺了，新的投入才能发挥更大的作用。投入不只是 Token，也包括人。想想一家 AI 原生公司怎么起步：先有一个人，再给他一笔 Token 预算。</p>
<p>这个人把 Token 预算用满了，就说，我们再加一个人吧。下一个人也分到一笔 Token 预算，这样他们那座工厂就有了自己的预算。</p>
<p><strong>Gergely Orosz：</strong> 对。</p>
<p><strong>Satya Nadella：</strong> 这就是从头搭建的办法。这些公司要是做成了，有一天也会变大，有些已经是这样。以后每家公司都会开始像它们，每个项目团队或产品团队也会这样。重新组织、摸索新的做法、重新配人，都得花时间。现在就把各种迹象连成线，说这是长期趋势，我觉得为时尚早。</p>
<p><strong>Gergely Orosz：</strong> 回到访谈之前，先介绍本季赞助商 Linear。直到不久前，我还以为 Linear 只是个规划和组织工作的工具，但它能做的远不止这些。</p>
<p>很多团队用 Linear 推进变更，从提出想法到在 GitHub 合并，全程不用离开 Linear。我找了 Linear 的工程师 Dima，看看他们内部是怎么用 Linear 来做整个 Linear 产品的。这里有个真的问题：在提交评审时，如果还有没发出的评论草稿，Linear 会提醒你，却不告诉你草稿在哪儿。</p>
<p>有客户反映了这个问题，Dima 决定修一下。他没打开 IDE，只在 Linear 里向智能体描述问题。智能体做好了改动，创建了 PR，还附上 Storybook 截图，方便检查。截图上可以看到，修复后那些评论草稿有了链接。你也可以在 Linear 里从 PR 一键打开预览，试试改完的效果。我最喜欢的是他们正在开发的引导式评审。</p>
<p>引导式评审是一种新的代码评审方式，重要的东西一眼就能看到。评审顶部有摘要和变更示意图，PR 则分成几节，带你看都改了什么。</p>
<p>这些区块把关键变更挑出来，让人更容易理解和审查。Dima 看完以后，自己批准代码，变更就合并到 GitHub 了，整个过程都没离开 Linear。</p>
<p>要是只记住一件事，我希望你记住：Linear 已经不只是个规划工单、安排工作的地方。建工单、启动智能体、查看预览、评审、合并到生产环境，实际工作都能在里面做。Linear 是给团队和 AI 智能体用的产品开发系统，我很喜欢它现在的发展方向。它是一套面向团队和 AI 智能体的产品开发系统，我很喜欢这个变化。去 <a href="https://linear.app/pragmatic">linear.app/pragmatic</a> 可以试用六个月。</p>
<p>做过 B2B 软件的人都熟悉这一幕：客户喜欢你的产品，接着安全团队发来一份清单，单点登录、SCIM 账户配置、基于角色的访问控制。你原本没打算做这些，但这笔生意就卡在这上面。</p>
<p>WorkOS 的认证基础设施能把这些包下来，不用团队里的人再去调试客户的配置。现在，智能体又带来了一版新的问题：一旦智能体能在客户的系统里做事，企业就会想知道它到底能做什么。这是 WorkOS AirLock 要解决的问题。它按意图控制访问。多数访问控制只问你是谁；AirLock 还会在智能体尝试执行动作的时候，问它想做什么。</p>
<p>像「智能体不得删除云资源」这样界限清楚的规则，可以直接写成代码；模糊一些的情况，则由 AI 在运行时判断是否符合政策。策略可以用普通英文写，Claude 还能把 Notion 和 Jira 里已有的规则提取出来，替你导入。无论是 Claude 还是 Devin，智能体都接入同一个入口，MCP 服务器放在入口后面。</p>
<p>AirLock 在现有权限上再加一层，所以智能体拿到的权限不会超过调用它的人。遇到有风险的请求，可以转交人工批准，比如在 Slack 里。这个思路是把规则写一遍，把人的注意力留给确实需要人判断的情况。每次请求和决定也都有记录。详情见 <a href="https://workos.com/airlock">workos.com/airlock</a>。</p>
<p><a id="talk-section-14"></a></p>
<h2>开放模型</h2>
<p><strong>Gergely Orosz：</strong> 搭建自己的软件工厂会改变工作方式。我们往下聊一点具体怎么做。我看到一个行业趋势，我想你肯定也看到了：很多科技公司开始转向开放模型。许多公司在自己搭推理服务；像 Replicate 这样的公司则自己买算力，买来 B200，直接在上面跑模型。</p>
<p>他们各有各的理由。从你的角度看，微软也在做开放模型服务，比如 Foundry。这个趋势有多大？它是必然的吗？我一直在想，开放模型运动和过去的开源运动有没有相似之处。</p>
<p><strong>Satya Nadella：</strong> 肯定有相似之处。闭源模型会存在，彼此也会竞争；开放模型显然提供了另一种选择，给人更多灵活性。我有时是这么想的：前沿模型的生态到底会长什么样？先放下一个假设，也就是会有一个前沿模型，把全世界的知识都装进去。如果你不接受这个假设，那么在某种意义上，有多少家企业，就该有多少个前沿模型。</p>
<p>回到哈耶克对经济的描述，他讲的就是知识如何分布在各处。他对价格的解释很妙：经济中的知识是隐性的，分散在各处，价格由此产生。每家企业都需要把自己的知识掌握在手里。要是这么看，我甚至会说，每家企业既有人力资本，也有 Token 资本。</p>
<p>既然每家企业都会有这两种资本，那么 Token 资本可以放在一个融入了自身知识的开放权重模型里，这是一个办法；也可以放在上下文层里。你甚至可以同时用几种闭源模型，收集使用这些模型的运行轨迹，再用这些轨迹基于开放权重模型训练一个供自己使用的小模型，把几种办法组合起来。</p>
<p>即便是 Copilot，不论是 GitHub Copilot 还是 Copilot，本身也都是按多模型系统设计的。没准下次我们聊天时，大家都不会再纠结到底开放还是封闭了。每个人都有一套模型系统。一开始就有个决策引擎，根据任务选模型。</p>
<p>然后，上下文、记忆、行动空间都要和单个模型分开，否则就会被彻底锁定。我有时会想，要是运行框架、模型和记忆全绑在一起，你以后怎么脱身？你到底在做什么？其中哪些是你自己的，哪些又掌握在模型手里？</p>
<p>模型基本会把它见到的东西都吸收进去。我觉得，人们越来越理解这种关系了。很多人觉得这不过是科技公司之间的竞争，但别忘了，智能没有上限。</p>
<p>每家银行、医疗公司、保险公司，每一位分析师，都需要认真想一套架构：怎么掌握自己的学习过程和知识，怎么保住自己和别家不一样的地方。在这样的背景下，我看好开放权重模型这条路。</p>

<h2>把 AI 基础设施掌握在自己手里</h2>
<p><strong>Gergely Orosz：</strong> 这一点很有意思。我和不少中等规模的科技公司、创业团队聊过，他们几乎都在搭你刚才提到的东西：自己的运行框架、上下文层、上下文图谱、推理服务。一开始我觉得这也说得通，工程师就喜欢做东西，要积累 AI 工程经验，风险最小的办法就是先做个内部项目。</p>
<p>但我以前没想到，不管这些工程师自己是不是出于战略考虑，他们可能的确从战略上帮了公司。你的意思是，大多数公司应该考虑掌握整套系统，同时让各个基础组件可以替换。</p>
<p><strong>Satya Nadella：</strong> 对。你观察到的现象很有意思。要是你在一家银行，不妨看看那些想在这个生态里走到前沿的软件公司是怎么做的。</p>
<p><strong>Gergely Orosz：</strong> 他们没有把控制权让出去。</p>
<p><strong>Satya Nadella：</strong> 所以在某种意义上，银行也该这么做。银行在哪些地方能占主动？举个例子，我们做的那层叫 IQ。我们把 Copilot 和 GitHub Copilot 底下的运行框架单独拿出来，在 Foundry 上做成托管服务。假设你在做供应链系统，可以直接从我们的框架起步，也可以带上 Pi 或其他开源运行框架。</p>
<p><strong>Gergely Orosz：</strong> 我们很喜欢 Pi。</p>
<p><strong>Satya Nadella：</strong> 你可以直接把它当托管服务用。微软自己在实际使用、已经经受过检验的运行框架，就在那里。Foundry 上的各类模型也都可以用。这样，你有了运行框架，可以接多个模型端点，同时把上下文层整个分开。记忆和上下文是你自己的。到这一步，就是一套模型系统了。</p>
<p>还有行动空间，插件、技能和连接器都在这里。它们独立于任何一个模型，每个模型只看得到让它看到的部分。我觉得，面向模型优先的开发，一种很像传统中间层的平台正在成形。你不会被锁死，也能评估所有环节。你可以做自己的评估，而且自己的评估更重要。</p>
<p>公开基准当然很好，但你需要一套内部评估，衡量真正对自己重要的结果，在自己的强化学习环境中看各个模型实际表现如何，再持续优化。我看到即使是我们的客户，通常也是先从前沿模型开始。</p>
<p>然后他们会说，好，运行轨迹都有了。现在我要换一种做法：这其实是条确定性的工作流，不必等下一代大模型，我现在想把成本降下来。那就换上一个 MAI Flash 模型，用已有的轨迹微调一下，就可以了。这些都可以在 Foundry 里做。我觉得这类工作会越来越多。</p>
<p><strong>Gergely Orosz：</strong> 也就是说，你已经看到很多公司除了评估，还搭了强化学习环境。这样能保住控制权，控制定价，也不会把业务数据漏给那些可能想用它来训练模型的 AI 公司，对吧？</p>
<p><strong>Satya Nadella：</strong> 可以这么想。我脑子里有个很简单的类比。过去，不管是保险公司、银行还是医疗公司，都会说，我要上一个关系数据库。</p>
<p>好，我部署个关系数据库。也可能买一套运行在数据库上的软件，它自带业务逻辑。然后我写自己的业务逻辑，把它扩展到适合我的业务。控制权在我手里，数据库里的数据从头到尾也不会交给别人。就算数据库厂商说不给你更新了，你也还是可以迁出去。</p>
<p><strong>Gergely Orosz：</strong> 对。</p>
<p><strong>Satya Nadella：</strong> 现在就得问同一个问题：如果你的记忆放在某个模型的嵌入里，模型公司哪天告诉你，很遗憾，我没办法再给你更新了，你的记忆怎么迁出去？</p>
<p><strong>Gergely Orosz：</strong> 还有我们前面聊过的，新组件出来了，你怎么把它们接进来？太依赖一个或几个供应商的话，你只能等他们也许哪天替你接好。</p>
<p><strong>Satya Nadella：</strong> 也是。</p>
<p><strong>Gergely Orosz：</strong> 我们做工程的，擅长的就是这个。</p>
<p><strong>Satya Nadella：</strong> 对。我觉得企业有两个架构决策值得谈，希望大家能开始讨论。正如你所说，看看软件行业的团队就行了，他们都在想办法保住自己的独立性。</p>
<p>我觉得商业领域也需要把这变成常态。第一个问题是，怎么避免这种反向的信息悖论，也就是别把自己的价值漏出去？企业得掌握自己的学习循环。你的架构是怎么设计的？你怎么确保上下文和模型分开，又能同时用多个模型？</p>
<p>运行框架也得和上下文、模型分开。我认为这是确保随时可以换掉任何一个模型的唯一办法。我的硬标准是：你应该能换掉任何一个模型，然后仍然可以在自有的内部评估中继续把成绩往上提。</p>
<p><strong>Gergely Orosz：</strong> 对。</p>
<p><strong>Satya Nadella：</strong> 要是做不到，你就得问自己，这家公司究竟还能不能自主？</p>
<p><strong>Gergely Orosz：</strong> 对，那就意味着你没法控制自己的产出。</p>
<p><strong>Satya Nadella：</strong> 是。</p>
<p><strong>Gergely Orosz：</strong> 这大概就是第一个问题：等于坐在一颗定时炸弹上。</p>
<p><a id="talk-section-16"></a></p>
<h2>怎么信任 AI 智能体</h2>
<p><strong>Satya Nadella：</strong> 对，那就完了。这是我想说的。接下来，你需要一套信任架构。现在我们知道，规模定律是管用的，可规模变大带来的是新能力，不是对齐。</p>
<p>我们对其运作机理也还没有理解。希望有一天科学上能有突破，但现在系统越来越有能力，却越来越不可靠，这是最危险的处境。所以架构上必须把权限和智能分开。让一个不可靠的智能系统掌握权限，你就有大麻烦了，相当于给自己引入了巨大的内部风险。得把这些智能体当作内部风险管理，也就是说，你需要建立一套信任体系。这涉及很多事。</p>
<p>就连思维链也一样。思维链不能是一种只有神经网络懂的语言，得用人能读懂的语言，能够审计，也要记录下来，确保不会被篡改。问题不只发生在预训练或强化学习阶段。</p>
<p>模型在推理时也会出问题，因为它可能会钻奖励机制的空子。所以运行时必须加上严格的防护。这就是我说的信任架构：把模型和智能体作为内部风险来管理，要能监测它们、看清它们的行为，同时还要保证学习循环始终掌握在自己手里。</p>
<p><strong>Gergely Orosz：</strong> 作为工程师，我听到、看到的，就是有太多新的工作要做，有太多新的系统要搭，而且手上并没有现成的图纸。也许最好的办法就是先做起来，再和也在做这些事的同行交流。我相信五到十年之后，可能就会有蓝图、认证之类的东西了。但现在，这就是我们的工作。</p>
<p><strong>Satya Nadella：</strong> 没错。下周就是我们的 Ignite 大会，我很期待。我希望我们能把一件事讲清楚：这些都做得到，也有可以参考的做法。</p>
<p>各家公司在做法上已经有很多创新。我觉得我们正在走到这样一个阶段：大家不再只是追逐新鲜玩意儿，而是要坐下来问问，我到底在为公司创造什么价值？把这个问题多聊几层，有效的做法自然就清楚多了。</p>
<p><a id="talk-section-17"></a></p>
<h2>本地模型与混合智能</h2>
<p><strong>Gergely Orosz：</strong> 作为工程师，我总觉得少了一样东西：这些 AI 模型要么跑在别人的云服务器上，要么得用贵得离谱的 B200，我自己买不起，公司也不见得肯买给我。能用上的人算是走运。要是就在我的笔记本上跑，不是挺好吗？</p>
<p><strong>Satya Nadella：</strong> 问得好。</p>
<p><strong>Gergely Orosz：</strong> 到目前为止，本地 AI 挺难用的，得靠各种土办法。有意思的是，现在倒是微软在做新的尝试。Scott Hanselman 给我演示了新的 Surface Ultra 笔记本，我自己也想上手。它有一块芯片，可以跑本地编程模型。你觉得本地模型会在 AI 循环里发挥什么作用？</p>
<p>作为开发者，我觉得我们特别缺这个。不过是不是只有我这样想？你接触的人比我多得多。</p>
<p><strong>Satya Nadella：</strong> 这个问题很好。我们的确很想在 AI 时代继续革新 PC 这种设备形态。我的想法和我们一直在做的事都源于一点：分布式计算始终会是分布式的。既然如此，为什么不把各处的算力和 Token 都用起来，而只用云端的呢？</p>
<p>这也是 Ultra 的灵感之一。NVIDIA、AMD、高通、还有出色的英特尔都做了很多创新，芯片和系统层面都有很好的进展。其实现在已经是这样了：去年的前沿模型可以在笔记本上跑，上一季度的前沿模型可以在台式机上跑。大致就是这样的能力。PC 以前不也是这么演进的？</p>
<p><strong>Gergely Orosz：</strong> 正是。</p>
<p><strong>Satya Nadella：</strong> 这很好。有了这个基础，又回到了我说的决策引擎和路由。我记得我们有个叫 Hydra Fusion 的东西，名字我有点记不清了。GitHub 那边有一套做路由的办法。我很喜欢这一点。现在我上一次在 Copilot 里手动选模型是什么时候？对，Copilot Fusion。我们想做的，就是让路由器为每个任务挑选合适的模型。</p>
<p>有时我在 Ultra 上突然听见风扇转起来，就是本地模型在工作了。特别是多个子智能体一起工作时，有些子智能体可以调用多个本地模型，同时其他地方还在用云模型。这么做从架构上说得通，从经济上也说得通。我们正处在我所谓「混合智能时代」的开端。云还会继续增长，Token 的需求会是无限的，但我们也可以把边缘设备看成一座座 Token 工厂。我觉得这有点像「不按用量计费的智能」。</p>
<p><a id="talk-section-18"></a></p>
<h2>微软的模型策略</h2>
<p><strong>Gergely Orosz：</strong> 对，因为你不用担心用了多少。</p>
<p><strong>Satya Nadella：</strong> 没错。</p>
<p><strong>Gergely Orosz：</strong> 说到这里，我觉得前面几件事总算连起来了。老实说，MAI Code 那个 Flash 1.1 模型没太打动我，我看也没多少人被它打动。但它有一点让我印象深刻：我原来以为，能在笔记本上跑的本地模型一定是开放模型。MAI Code 却是个闭源模型，照样能下载到 Windows 电脑上运行，基础设施已经有了。我就想，今后是不是也能在笔记本上挑别的闭源模型来用？也许可以免费下载，也许只需要付一点钱。</p>
<p><strong>Satya Nadella：</strong> 就像你刚才说的，让 MAI Code Flash 这类模型能在笔记本上跑，是我们的工作重点，我们也很期待这件事。我看 Copilot 里的 Code 标签页，即便不用 GitHub Copilot，无论是写文档还是写应用，都可以很方便地在 PC 上用这些模型。这很让人兴奋。退一步讲，我们究竟在用 MAI 模型做什么？</p>
<p>首先，通过和 OpenAI 合作，我们有 OpenAI 的模型，而且会继续使用。在此之外，我们想从零做出一个新的模型系列。</p>
<p><strong>Gergely Orosz：</strong> 真正从零？是你们从头训练的意思吗？</p>
<p><strong>Satya Nadella：</strong> 是。我们公开了新的 MAI-Base-2 的预训练细节。这大概是对预训练方法和流程披露得最充分的资料之一。听众有兴趣的话可以去看看。外面也有人跟我说，这可能是业内最细的预训练说明了。很少有地方能查到这样的材料，而且这次预训练是完全独立做出来的，可以说是一次洁净室实现。所以我们会继续做下去。</p>
<p>我们还可以依托自己的产品，在能力前沿曲线上找到新的位置。无论是网络安全、知识工作还是编程，问题都是一样的：怎么在训练时用好浮点运算算力，又让部署时的 Token 用得高效？当你把高层意图交给许多子智能体时，它们用的可以是不同系列的模型。</p>
<p>所以只要有得选，就未必会被一个模型系列绑死。智能体会根据任务，聪明地选出效率最高的模型组合。我觉得这就是我们想做的事：提供更多选择，而不是只给一个模型系列。</p>

<h2>给软件工程师的建议</h2>
<p><strong>Gergely Orosz：</strong> 我很喜欢你强调选择。做开发的就喜欢有得选，这也能带来竞争，让价格更合理。最后我想问，变化来得实在太快了。我遇到的业内人士都说，他们可能见过类似的变化，规模也许没这么大，但从没见过变化来得这么快。</p>
<p>你经历过好几轮变革，刚入行时又是完全不同的年代。如果有个软件从业者说，我想在一两年内成为 AI 时代一名出色的软件工程师，你觉得他该怎么面对这轮变化？</p>
<p><strong>Satya Nadella：</strong> 还是我们前面谈到的那些事。说真的，我自己也是一样，首先得弄明白这轮变化究竟在变什么。别只看新闻标题，也别停留在「我很喜欢 X」这类表态上，别跟着炒作走。</p>
<p>大家总想谈这件事，我在播客里这么说有点好笑，但还是应该多做、多学、亲手试，看看实际是什么样。说实话，这话我也想说给自己听。要是能调整自己说和做的比例，我也会这么做。</p>
<p>如果只有一条建议，不论你已经工作多年，还是像我这样当 CEO，又或刚大学毕业，这时候都应该尽量抽时间学习、动手做，加入正在做这些事情的团队。这比别的都重要。我有时也会想，自己什么时候状态最好？</p>
<p>就是把自己当学生的时候。那就回到学校吧。</p>
<p><strong>Gergely Orosz：</strong> Satya，非常感谢。</p>
<p><strong>Satya Nadella：</strong> 谢谢，很高兴能来聊。</p>
<p><a id="talk-section-20"></a></p>
<h2>主持人结语</h2>
<p><strong>Gergely Orosz：</strong> 这次聊得很过瘾，我们和 Satya 谈了很多事。</p>
<p>有个问题反复出现：AI 把写代码变便宜之后，软件工程中的哪些工作更重要了？</p>
<p>我们谈到，写代码之前和之后的事，也就是规划和验证，都更重要了。工程师会花更多时间做这些。我还发觉，许多科技公司正在搭自己的编程智能体运行框架、上下文层和 AI 基础设施。起初我以为，这不过是因为工程师喜欢拿新技术做东西。</p>
<p>但 Satya 指出，对一家公司来说，不掌握自己的 AI 基础设施和 AI 知识产权，是一种自取灭亡的策略。他认为，成功的公司都会搭建自己的 AI 基础设施；依赖单一供应商或 AI 实验室，是重大的战略错误。我们搞开发的人爱做新东西，这回还真派上了用场。</p>
<p>眼下有许多机会，等我们去做这类新的 AI 基础设施和公司内部的软件工厂。最后，软件工程师的岗位和工作要求也在变。Satya 提到，微软增长最快的岗位之一，是前沿部署工程师。几年前还没有这个岗位。</p>
<p>他预计微软内部会有许多重组，团队会变小，岗位职责也会变。自愿离职计划，让那些不想经历这段变化的人有个离开的选择。接下来的变化很可能比以前剧烈得多。我想，重组和岗位调整比以往来得更密集，大概不只会发生在微软，很多科技公司也会遇到。聊完以后，我反倒更有干劲了。</p>
<p>没错，行业在变。不过从这场谈话里，我明白了 Satya 为什么觉得还有这么多软件工程工作等着人去做：有了决策模型之类新的 AI 基础组件，还有些组件根本没被发明出来。我们这些工程师得拿这些组件去做新系统，决定什么放在哪儿、该怎么改、什么做法合适、怎么部署，再从实践中继续学。节目说明里还有关于 AI 工程的延伸阅读，包括模型评估、推理工程和循环工程等，欢迎去看看。</p>
